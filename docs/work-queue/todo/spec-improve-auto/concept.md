# spec-improve-auto: Workflow-Driven Autonomous Spec Refinement

## Situation

The spec family pipeline runs `mg:spec-draft` → `mg:spec-improve` → `mg:spec-create-milestone`. The middle step, `spec-improve` (`spec/commands/spec-improve.md`), refines a concept spec through rounds of fresh-eyes subagent review:

- One reviewer subagent per round, carrying 10 review dimensions in a single prompt (contradictions, missing pieces, assumptions, engineering calibration, examples↔text, decision quality, simpler alternatives, over-specification, verification coverage, citation discipline).
- Triage caps fixes at **10 per round**; remaining issues "surface in subsequent rounds."
- Every round ends in a hard stop: report → wait for user approval → user re-invokes for the next round.
- All modifications happen on a working copy (`concept-auto-improve.md`, managed by `spec/scripts/improve_files.py`); the original is untouched until explicit `approve`. A `concept-NON-GOALS.md` sidecar accumulates approved scope exclusions that suppress future reviewer flags.

In practice a spec takes **10–20 rounds** to refine, each requiring manual re-invocation, and the session ends when the user judges the remaining findings too minor to continue — not when the tool decides it is done.

Relevant existing infrastructure:

- The Claude Code **Workflow tool** — deterministic JavaScript orchestration of subagents. No tool in this repo uses it yet: the documented API is not in doubt, but behavior in practice (relay fidelity, queue throughput) is unproven — which is what the capability spike validates. Its documented contract covers every capability D2 leans on:
    - **Invocation & control flow:** `scriptPath` invocation with an `args` value exposed to the script; schema-validated structured JSON returns from `agent()`; plain-JS loops terminating on runtime-computed conditions; conditional stages; fan-out sized from a prior stage's output (`pipeline()`, `parallel()`); a workflow-level return value.
    - **Concurrency cap:** concurrent agents are capped per workflow (min(16, cores−2)) with excess calls queued, not failed — a cap that degenerates toward zero on ≤2-core hosts, so the drain assumes a ≥4-core host for its 40–80-agent sweep to run with meaningful concurrency.
    - **Agent ceiling:** a 1000-agent lifetime ceiling per workflow (the documented figure; whether *exceeding* it throws or silently drops calls is **not** documented — the docs state only the cap, unlike the 4096-per-call limit they call an explicit error — so the drain conservatively treats reaching it as fatal either way and must stay under it, not merely near it).
    - **Fan-out width:** up to 4096 items per fan-out call.
    - **Net drain shape:** a first sweep of 40–80 micro-agents queues through the cap and, because later rounds re-verify only dirty atoms (D13), a healthy drain's cumulative agent count is one wide sweep plus much smaller later rounds, well below the ceiling. The pathological non-converging case — a sustained large dirty set — is bounded by the round cap and its cumulative-agent trigger (D4), not left to chance.
- `spec/scripts/milestone_checks.py citations <spec-path>`: the only deterministic check that runs standalone against a working copy (D-block citation discipline; never a vacuous pass).
- In-repo precedents for the mechanics this concept needs: codebase-health's adversarial verify step ("the scanner is fallible; don't rubber-stamp"; "prefer false negatives" for fixes), auto-doc auditv2's convergence assessment (trend-based stop recommendation, "default to CONTINUE if unsure") and dismissed-entity memory (persistent lists preventing re-flagging).
- `improve_files.py init` **unconditionally overwrites** an existing working copy from the source (create-once backup, always-reset working copy).

## Problem

1. **Artificial serialization.** The per-round fix cap (10 today) forces a spec with more mechanical findings than the cap into extra rounds even when nothing depends on anything — 25 findings become 3 rounds. Each round costs a full human gate (report, approval, re-invocation) even when every fix is cosmetic-safe.

2. **No self-termination.** The reviewer is a relative grader: "be harsh, flag everything" plus a critical/major/minor scale with no external anchor means severity normalizes to whatever remains in the current spec. On a near-final spec, the worst remaining nit is that round's "major." The loop structurally never returns empty, so a human must judge "relatively major vs. actually done" and abort manually — the observed 10–20-round pattern (Situation).

3. **Decisions surface as a drip, under-prepared.** Genuine decisions (intent/scope/architecture) arrive mixed into each round's batch and get discussed one round at a time, without dedicated research. Empirically these decision points are highly relevant and need real back-and-forth — but the current shape spreads that discussion across re-invocations instead of concentrating it.

4. **A pause-and-resume hazard.** Any flow that pauses for discussion and later re-runs `init` silently destroys unapproved fixes in the working copy (`improve_files.py` always resets it from the source). Today this is latent; an autonomous tool that brackets discussions with multiple runs makes it acute.

## Solution

### Overview

A new command `mg:spec-improve-auto` drives the refinement loop through the Workflow tool. One invocation executes a **drain run** in three phases. **Horizontal first:** whole-document agents find gaps, disconnects, contradictions, and simpler-whole-design alternatives, and those are fixed before anything else — macro fixes invalidate micro work, so the skeleton stabilizes first (D12). **Then the verification pyramid:** the spec is decomposed into typed atoms (claims, citations, contracts, scope items, examples); a swarm of micro-agents verifies each atom — small, narrow tasks with near-lookup accuracy — per-section aggregators compose the verified verdicts into evidence-chained findings, and the judge gate plus deterministic tally dispose of them; fixes mark atoms dirty, and only dirty atoms re-verify, so the swarm shrinks as the spec stabilizes (D13). **Finally an exit exam:** coverage-complete ledger, a dry gate, and a fresh whole-document read. Decision-shaped findings do not stop the run: they are researched and **auto-taken** (the recommendation — conservatively on near-ties), written into the spec as D-blocks, and logged as decision records; only a decision that contradicts explicit user intent or exceeds a blast-radius threshold blocks (D5, D9). The deliverable is a fully refined spec plus a **decision briefing** — a deterministic, dependency-ordered rendering of the decision records with computed blast radii. The user reviews decisions, not rounds: an override re-drains that decision's blast radius plus one closing whole-document exam — never a full restart; acceptance approves the spec.

The division of labor: micro-agents do small verifiable things (one atom, one narrow question), holistic agents do what only whole-document reading can (macro coherence), aggregation composes conclusions from verified premises instead of raw impressions, the workflow script does what determinism is good for (looping, branching on tallied outcomes, terminating), and the user does the one thing agents cannot: judge intent. Internal soundness — consistency, true premises, coverage — is machine-assured; intent soundness — is this the thing the user actually wants built? — is only user-assurable, and the briefing is that check, not a courtesy summary. The existing safety net survives intact: all edits land on the working copy, the original changes only on explicit approve, and fixes and non-goals are approved independently.

### Command flow (outer loop)

The command .md orchestrates; the workflow script executes one drain run per invocation.

1. **Setup.** Parse target path; run `improve_files.py init <target>`. If a working copy already exists, `init` fails loudly (D7); the command then runs the read-only `improve_files.py paths <target>` to obtain the resolved-paths JSON, surfaces the leftover state, and asks the user: **resume** (continue with the existing working copy) or **discard and restart** (`init --fresh`).

2. **Drain run.** Invoke `Workflow({scriptPath: <installed workflow>, args})`.
    - **Absolutize `scriptPath` — and every path passed to the drain — first:** `{MG_INSTALL_WORKFLOWS_DIR}` is project-root-relative in `--project` mode like every other placeholder (keeping a clone portable), and the command prepends its cwd — the project root, reliable in the main session where the command runs — to that relative form (a no-op on the already-absolute `--global`/`--target` form). This is because the Workflow tool's resolution of a *relative* `scriptPath` against the caller's cwd is undocumented — as is a workflow-spawned agent's cwd (the paths in args, below); absolutizing in the command, the one context whose cwd is known, removes both assumptions rather than betting the drain on them.
    - **Args carry:** the resolved file paths (the `init`/`paths` JSON); the run number (`next_run` from `init`/`paths` — the script threads run and round numbers into the fixer/recorder's prompts); `scripts_dir` and `template_path` — the command's sed-resolved `{MG_INSTALL_SCRIPTS_DIR}` and `{MG_INSTALL_CONCEPT_TEMPLATE}` values — all **absolutized by the command** (prepending its cwd, exactly as with `scriptPath`) before being passed, so the JS interpolates absolute paths into agent prompts and every `uv run` invocation and template read inside the drain resolves regardless of the spawned agent's cwd (the workflow script itself is copied verbatim; no sed pass on the JS); and, on later runs, the overrides and directives from the previous briefing review or blocked discussion.
    - **Why absolutize rather than rely on the drain's cwd:** these values are whatever `install.sh` substitutes — **project-root-relative** in `--project` mode (the default, so any clone of the target project works) and absolute in `--global`/`--target`. Rather than bet the drain on its script-running agents inheriting **cwd = the project root** (undocumented for workflow-spawned agents, unlike the main session's reliable cwd), the command resolves each path against its own cwd before passing it — the same absolutization it applies to `scriptPath`, a no-op on the already-absolute `--global`/`--target` forms. The installed command's own `uv run {MG_INSTALL_SCRIPTS_DIR}/...` calls stay relative because *they* execute in the main session; only the paths crossing into the drain are absolutized.
3. **On return** the workflow reports one of three statuses:
   - `converged` — present the **decision briefing** (rendered deterministically from the decision records: dependency-ordered, blast-radius-ranked, `review_first` items on top) plus the changelog summary and scorecard. Accepting it approves fixes and proposed non-goals independently via `improve_files.py`, as in `spec-improve` today; overriding any decision turns the override into a structured `overrides` entry carrying that decision's id for a scoped re-run — the overridden decision's post-take radius is re-drained (scoped phases plus one whole-document exit exam), not the whole spec. A briefing review may equally raise a non-decision editorial change ("section 4's approach is wrong, redo it"); that is collected as a free-form `directive` (args) routed to the same directive channel `round-cap` uses, triggering the same scoped directive re-run.
   - `blocked` — the run hit one or more decisions it may not take (D5's graded gate: reversing an explicit user directive or a NON-GOALS entry, or blast radius over the threshold). Present the blocked cards (from the command's own `spec_checks.py decisions summary`, the status-`blocked` records) alongside the accumulated briefing for context (the auto-taken decisions so far), discuss them in prose in the conversation (dependency-ordered), collect resolutions as structured `overrides` entries (each carrying its blocked decision's id), and invoke the workflow again. A `blocked` stop is a discussion, not an approval opportunity — no fixes or non-goals are approved here (that waits for a `converged` acceptance or a round-cap partial approve/reject). Expected to be rare — most decisions auto-take.
   - `round-cap` — the drain did not converge within the cap. Present an honest non-convergence report (what kept churning, which atoms never verified, which decisions are still pending); this is itself a signal the spec has a structural problem. The user then chooses: re-run — carrying overrides or directives if decisions were discussed, or bare to keep draining the carried dirty set (a **continuation run**, defined in the drain's directive/continuation rules; the ledger persists across invocations, D4) — or approve/reject the partial work via `improve_files.py` (the working copy, changelog, ledger, and history are intact and auditable either way). **Invariant:** the briefing — rendered from the decision records accumulated so far — accompanies *every* approval opportunity (a `converged` acceptance or a round-cap partial approve/reject; a `blocked` stop is a discussion, not an approval). Auto-taken decisions are never approved unseen.
4. Repeat until a run exits `converged` and the user accepts the briefing.

Only the **return** crosses back from the drain, and it is a thin control-flow signal: `status`, `rounds`, `fixed`, and `below_bar`, all the workflow's own loop variables. `status` is the one value only the workflow can supply — it alone knows whether the exit exam came back clean; the three counts are accumulators (`fixed` counts auto-fixable findings applied — *not* decision-take D-block writes, which the scorecard counts under decisions taken, from `decisions summary` — so a taken decision is never double-counted even though it also gets a changelog entry). Everything the user sees about *decisions* and *atoms* the command derives **itself** after the workflow returns.

- **Why command-side derivation is race-free:** unlike the filesystem-blind workflow, the command has Bash and the sidecars sit on disk, and nothing writes between workflow-exit and command-read (the workflow has exited; only the command runs next).
- **The three derivation commands:**
    - `spec_checks.py briefing` — the human-facing decision view (as `spec-improve` does today);
    - `spec_checks.py decisions summary` — structured decision data whenever it must partition (the blocked discussion, the round-cap pending list, the scorecard);
    - `spec_checks.py atoms coverage` — the atom counts (the round-cap report's never-verified list).
- **Coverage-completeness** stays checkable straight from `atoms coverage` output — the command re-renders `verified + unverifiable == total` from the counts for the scorecard, while the drain itself branched on the same call's script-computed `complete` verdict at round close (D2):
    - an atom counts as `verified` only when its verdict `state` is `verified` **and** was computed against the atom's current text hash; a `dirty` atom falls out of `verified` whether its text changed (hash mismatch) or only its input set changed — where `mark-dirty` flips the `state` to `dirty` while the text hash still matches, so the `state` field is consulted, not the hash alone; an `unverified` atom carries no settling verdict — the equality thus forces zero dirty and zero unverified atoms;
    - `total` is the **coverage denominator** — extracted atoms minus heading atoms and all *vanished* atoms (both retired and lineage-succeeded: a vanished atom's hash is gone from the document, so it carries no present-hash verdict and sits outside the denominator per the pyramid's Retirement/Lineage and Loop rules), not the raw ledger inventory — so a converged run holding an unverifiable, heading, retired, or succeeded-vanished atom still satisfies the equality.
- **`decisions summary` projection and status derivation:** it reads DECISIONS.json and emits the thin projection — id, `kind`, derived `status`, title, confidence, `review_first`, the two radii, `depends_on` — as JSON on stdout; the command groups it by `status` for presentation (status `taken` → the taken decisions, `blocked` → the blocked cards, `pending` → the still-undecided, `proposal` → proposed non-goals). `status` is derived, not stored:
    - kind `non-goal-proposal` → `proposal` (or excluded from the active `proposal` group when marked `dropped` — the finding has been un-parked to re-enter the gate, step 3);
    - kind `decision` with a `taken` field → `taken`; without one, `untakeable` set (written at block time) → `blocked`, else → `pending`, a gate-time record whose research or take has not yet completed.

    The fat records never cross into the return at all — the command reads them from the sidecar via `briefing` and `decisions summary`, deterministically, never paraphrased.
- **The scorecard** shown at every approval opportunity is likewise command-derived, not a summarizer's prose: the return's `rounds`/`fixed`/`below_bar` counts, plus decisions taken/blocked/pending and proposed-non-goal counts from `decisions summary`, plus atoms verified/unverifiable/total from `atoms coverage`. **Mixed scopes are labeled, never silently merged:** the return's three counts are *this-run* (per-invocation) values, while the decision and atom counts read the persistent sidecars and are therefore *session-cumulative* across a multi-run refinement — so the scorecard tags each block accordingly rather than letting a last-drain `fixed: N` read as a session total beside cumulative decision counts; a cumulative `fixed` is available command-side by counting CHANGELOG entries when a session total is wanted.

Workflow return (interface) — a thin control-flow signal; decision and atom data are derived command-side from the sidecars (see above), never carried here:

```json
{
  "status": "converged | blocked | round-cap",
  "rounds": 4,
  "fixed": 23,
  "below_bar": 6
}
```

Decision record (one DECISIONS.json element — created at gate time by `append-decision`, enriched and resolved by `update-decision`, rendered by `briefing`):

```json
{
  "id": "R1",
  "kind": "decision | non-goal-proposal",
  "title": "…",
  "finding": "what surfaced the decision",
  "finding_atoms": ["lineage ids of the atoms the finding stands on — written at gate time so `atoms radius` is recomputable in any later round or invocation; empty for a macro-derived finding, whose radius the researcher declares instead"],
  "research": "codebase context gathered for it",
  "options": [{"option": "…", "tradeoff": "…"}],
  "taken": "which option was taken, and why (absent on a blocked, pending, or non-goal-proposal record)",
  "taken_by": "auto | user (user when a directive resolved or overrode it)",
  "untakeable": "present only on a decision blocked by D5's graded gate; a later user resolution writes taken, which wins in derived status",
  "dropped": "present only on a non-goal-proposal the user declined at a briefing (written by update-decision, D7); the record is retained (D11) but the dedup pass stops folding its re-emissions so the parked finding re-enters the gate — derived status excludes it from the active proposal group",
  "superseded": ["a replaced taken moves here on override — never erased (D11)"],
  "confidence": "high | low",
  "near_tie": false,
  "review_first": false,
  "pre_take_radius": {"sections": ["## Solution / ### Overview", "## Design Decisions / ### D3"], "atoms": 14},
  "post_take_radius": {"sections": ["## Design Decisions / ### D3"], "atoms": 9},
  "semantic_depends_on": ["stored semantic edges only — a dependency the radius rule cannot see; mechanical edges are recomputed at render, never stored (Decide). The briefing / decisions-summary output field depends_on is the union of these with the recomputed mechanical set"]
}
```

Args contract for run N+1: the same shape, rebuilt — the command re-runs `paths` before **every** workflow invocation, so `next_run` is freshly derived from `history/` and a run number is never reused (a reused number would land run N+1's snapshots in `history/run-N/`, overwriting exactly the audit trail D11 exists to preserve) — plus two override channels: `"overrides": [{"decision_id": "R7", "directive": "free-form override text"}, …]` — the decision id is known at collection time (the command presented that specific blocked card or overridden decision), so it is carried structurally, never re-inferred from prose — and `"directives": ["free-form editorial instruction tied to no decision record", …]`.

### Drain run (inner loop)

A run executes three phases; rounds live inside phase P. The workflow script itself has no shell or filesystem access; agents execute all script commands.

**Relay contract, pinned.**
- **Raw stdout only:** any agent that runs a script returns the script's raw JSON stdout verbatim in a dedicated `script_output` field of its structured return, kept separate from the agent's own reasoning.
- **Keyed list for multi-call agents:** when one agent makes more than one branch-driving script call — the decision-taker runs `atoms radius` then `block-gate` once per decision (N decisions → N verdicts), and the fixer/recorder runs `tally` plus the `reanchor`, `mark-dirty`, and round-close `atoms coverage` calls whose results size the next round or gate phase-E entry — `script_output` is a **keyed list**: one entry per branch-driving call, tagged with the call it relays (e.g. `block-gate:R7`) and carrying that call's raw JSON stdout, so the JS validates and branches on each independently. Purely side-effecting calls the JS never branches on (the `append-*` writes, `snapshot`) need not be relayed.
- **Branch only on parsed relays:** the workflow script branches only on parsed `script_output` entries, never on an agent's paraphrase — otherwise every "deterministic" branch point is silently mediated by LLM transcription.
- **Binds script-computed values, not agent-authored plans:** the fixer's fix plan — which findings it will fix, and whether a fix replaces a whole anchor unit (the phase-H competitive-rewrite trigger and the Loop's structural-edit trigger, both branch-driving) — is original agent output, like the finding set itself, not a transcription of a script's stdout, so the JS branches on it directly; the relay contract governs only values a script actually computed (`tally`, `block-gate`, coverage, `radius`), which must reach the JS byte-for-byte.
- **Enforced, not merely contracted:** the Workflow schema-retry checks only that `script_output` is a well-typed field, not that it equals the script's real stdout, so the JS `JSON.parse`s each relayed value and validates it against that script's declared output shape *before* branching; a malformed or off-shape relay is a failed call routed to the failure policy's one retry, so a corrupted transcription fails loud instead of silently flipping a branch.
- **The reverse path (JS→script) is named and guarded, not assumed lossless:** the workflow JS has no filesystem access, so any value the JS holds that a script must consume — the round's marshaled verdicts/findings/votes/tally for `record-verdicts`, the two candidate sets for `atoms merge`, the section sets for `block-gate` — reaches disk only via an Edit/Write agent transcribing it from its prompt into a scratch file: the mirror of the forward relay, and the same LLM-transcription hazard. Two guards apply. First, the receiving script `JSON.parse`s and shape-validates each marshaled file before acting — the forward contract's validate-before-branch rule enforced at the read end. Second, because the round-close verdict marshal is the highest-volume transcription (100–160 entries) and feeds the `complete` branch, `record-verdicts` echoes the count of verdict entries it applied and the JS asserts it equals the number it marshaled in — so a transcription that drops or duplicates an entry fails loud rather than silently thinning the round's delta and satisfying coverage over an atom that was never really persisted. Per-entry *content* fidelity beyond the count is the reverse-direction analogue of the residual below, spike-gated by the ledger-fidelity leg (Verification).
- **Irreducible residual:** a paraphrase into valid-but-wrong JSON that passes structural validation — in **either** direction (an agent's `script_output` forward, or a marshaled scratch file back) — is what the relay-fidelity legs of the capability and ledger-fidelity spikes falsify (Verification) — a residual the design names and spike-gates, not one it hides.

**Tool grants, pinned.**
- **Bash** (runs a script under the relay contract): the decompose agent, the floor agent, the fixer/recorder, the decision-taker, and the directive apply agent.
- **Edit/Write** (additionally — mutate the working copy or sidecars, or marshal relayed returns to scratch files for a script, since a CLI cannot read an agent's in-memory return): the fixer/recorder, the decision-taker (it writes D-blocks), the apply agent, and the decompose agent (it marshals the two prose extractors' candidate sets to files for `atoms merge`, step 1).
- **Read/Grep/Glob only** (no script): every read-only agent — the two prose extractors, the verifier swarm, the per-section aggregators, the dedup agent, the three judges, the decision researchers, the implementability-probe pair and comparator, the competitive-rewrite agents, and the phase-H and phase-E whole-document readers.
- **No drain agent is granted Agent/Task/Workflow** — only the workflow script spawns agents. These are the per-role `agent()` tool sets the workflow sets; the command `.md`'s own `allowed-tools` frontmatter (Registration) is separate.

**Phase H — Horizontal (macro first, D12).**
- **Who & what:** two to three whole-document agents — context-free, reading the working copy, the concept template, the NON-GOALS and IMPLEMENTER-NOTES sidecars, and any code the spec references — hunt only macro classes: gaps (undefined flows, missing connective tissue), disconnects (sections that do not compose), contradictions, and the simpler-whole-design alternative — which subsumes **over-engineering**, any component more elaborate than its job requires (the manual reviewer's engineering-calibration dimension at whole-design scale; its under-engineering counterpart is the per-scope-item implementability probe, phase P step 2).
- **Routing:** their findings go through the same gate and tally as everything else; decision-shaped ones route to phase P's decision machinery.
- **Competitive structural rewrites:** structural rewrites are competitive when the remedy replaces at least one whole anchor unit (the `###`-or-enclosing-`##` grammar) rather than editing within one. A competitive rewrite splits the fixer/recorder across two invocations, because an agent cannot spawn siblings mid-call (only the workflow script spawns agents — Tool grants):
    - a first (plan) invocation emits the fix plan flagging each whole-unit fix;
    - the JS then spawns, per flagged fix, two independent rewrite agents that each produce the replacement section from the finding and its evidence chain, plus a head-to-head vote by the three-judge gate panel whose 2-of-3 majority is computed by `spec_checks.py tally` in a head-to-head mode (vote math stays in Python per D2 — never JS- or agent-counted; votes recorded in the round's verdict log);
    - a second (apply) invocation of the fixer/recorder lands each winner as an ordinary fix — changelog entry, captured in the round-close snapshot — the loser surviving only in the verdict log.

  A round with no whole-unit fix (the common case) needs only the single steps 5–6 invocation.
- **Reuse & loop:** fixing and recording reuse phase P's mechanics (steps 5–6) — the same fixer/recorder, changelog, snapshots, and decision machinery, the ledger simply still empty. Phase H loops until a pass produces no substantive macro finding; its passes count against the run's round cap.

**Phase P — Pyramid (micro, D13).** Decomposition (step 1) is a one-time full pass at phase entry; every later round maintains the ledger *only* incrementally — `reanchor` plus the region-scoped incremental extraction it triggers (step 1) — and never re-decomposes the whole document — that cross-round atom-identity stability is the ledger's entire purpose (D3, D13), so a literal "re-extract each round" reading is explicitly wrong. Each round:

1. **Decompose (layer 0) — a full whole-document pass once, at phase entry against an empty ledger; never re-run on later rounds. Later rounds instead mint atoms only from edited regions via the *incremental extraction* below — `reanchor` (a script) identifies the regions; the same extractors decompose uses then mint the new atoms, scoped to those regions rather than the whole document — so "no-op on later rounds" is true only of the whole-document extractors, not of atom-minting itself.**
    - **Extraction:** mechanical atoms (headings, D-blocks, citations, code-fenced contracts) are extracted deterministically via `spec_checks.py atoms extract`; prose atoms (claims, assumptions, scope items, examples) by two redundant extraction agents whose outputs are union-merged deterministically by `spec_checks.py atoms merge`.
    - **The decompose agent owns both deterministic calls** under the relay contract — it runs `atoms extract`, then marshals the two prose extractors' relayed candidate sets to files and passes their paths to `atoms merge` (a CLI script cannot read an agent's in-memory return — the same marshal-to-file step the fixer/recorder uses for the verdict log, step 6), and relays the merged ledger state as `script_output` (the extractors themselves return only their candidate sets).
    - **The persisted ledger is the union of both paths:** `atoms extract` and `atoms merge` **default to emit-only** — each returns its candidate atoms on stdout (relayed) and writes nothing, the mode the incremental path (below) uses so its atoms persist through the round-close `record-verdicts` delta rather than double-persisting; a single-behavior `atoms extract` built to always-write would double-persist on that path. The **one-time decompose entry pass** instead runs them in a `--write` mode that persists directly — this is the `decompose` writer of the two-writer rule (step 2, Verdict persistence): `atoms extract --write` persists the mechanical atoms and `atoms merge --write` the merged prose atoms (both also echoing their state for relay), so the relayed "merged ledger state" spans mechanical and prose alike — not the prose-only set the merge contract's prose-only inputs might otherwise suggest to an implementer (who would drop the heading atoms the whole anchor grammar rests on).
    - **Merge contract** (in: the two prose extractors' candidate sets — any candidate whose span overlaps a mechanically-extracted span is dropped by `atoms merge`, so mechanical spans are excluded *at merge time*, not merely by extractor prompt scope, D13; out: the merged atom set): same-type candidates under the same section path with overlapping spans collapse to one atom, disjoint candidates survive as distinct, and the load-bearing invariant is that no flagged text is ever dropped — the span tie-break that realizes it is pinned as policy in D13. Near-duplicates with different span boundaries thus never double-verify or duplicate findings; and a span two extractors typed *differently* (one "claim," the other "assumption") reconciles to a single atom by the type-precedence pinned in D13 rather than surviving as two, so the no-double-verify invariant holds across types, not only within one.
    - **The atom ledger** (session sidecar, script-managed) records each atom's id, type, anchor, text hash, input set (the spec sections and external files its check reads), and verdict state.
    - **Anchoring, pinned:** atoms are anchored by section path — the deepest heading enclosing the atom: `###` where one exists, the enclosing `##` section in heading-free regions (Situation, Problem, Verification) — plus content hash; never line numbers, which go stale on the first edit.
    - **Canonical serialization, pinned:** one form everywhere — the `##`-to-deepest-heading chain joined by ` / ` (`## Design Decisions / ### D3`; a heading-free region is its bare `##`, e.g. `## Verification`) — and the *script* is its sole canonicalizer: agents report the raw heading(s) they read or touched, and every `atoms` subcommand and `block-gate` normalize each reported string to this form (resolving a bare `### D3` to its full chain from the current heading tree) before any set operation. This is load-bearing because section-path strings cross the LLM boundary and are then compared byte-for-byte — a verifier's recorded input set against a later fixer's touched-section report in `atoms mark-dirty`, and the two pre-take section sets in `block-gate`'s union — so without one canonical form an input-set-dependent atom whose referent changed could silently fail to re-dirty (a stale verdict satisfying coverage) and the block-gate unit count could drift; canonicalizing script-side closes both.
    - **Reanchor (after each fixer pass):** the fixer/recorder runs `spec_checks.py atoms reanchor` (relaying its result), which re-walks the document keying on content hash, not section path:
        - an atom whose content hash is still present keeps its verdict, with its anchor rewritten to the current enclosing heading — so a **relocated** atom (unchanged text, changed section path: the common case after a phase-H section move or rename reorders the skeleton, D12) carries its verdict with its text;
        - an atom whose hash is gone entirely is *vanished*;
        - text matching no known hash is an edited region routed to incremental extraction (identical-hash atoms — repeated mechanical tokens — pair to their nearest prior anchor).

      "Only edited regions produce new atoms" is thereby computed, not judged.
    - **Incremental extraction owns the atoms `reanchor` only *flags*:** `reanchor` computes *which* regions are new but cannot type prose (it is a script), so the new atoms are minted by the same two-track extraction decompose uses, scoped to the flagged regions: mechanical atoms via a region-scoped `atoms extract`, and prose atoms — the claim/assumption sentences a decision-take's new D-block or a directive's added paragraph introduces (D13) — via prose-extractor agents whose relayed candidate sets the merge reconciles. Because no agent may spawn agents (Tool grants), **the workflow — not the fixer/recorder — spawns these scoped prose extractors** (read-only, returning candidate sets) whenever the relayed `reanchor` result reports new regions, and skips them on a round that edited nothing extractable (a conditional stage, D2). The merged new atoms are persisted through the round-close `record-verdicts` delta (step 6), which already carries *incrementally-extracted atoms* — so `record-verdicts` stays the sole round-close ledger writer — and they enter the ledger `unverified`, so the next round's swarm verifies them and coverage-complete cannot pass over un-atomized new prose. This closes the gap the recall caveat (D4) would otherwise widen: the exit exam catches new prose that is *wrong*, but only per-atom verification counts new prose as *covered*.
    - **Retirement, pinned:** a vanished atom whose edited region yields a successor lives on through lineage (below) — its coverage obligation **transfers to the successor**, so the vanished predecessor also leaves the coverage denominator (its hash is gone from the document; it can never re-verify); one with no successor — a deletion fix removed its text outright — is **retired**: also dropped from the coverage denominator, lineage retained in the ledger. Both exits are load-bearing: a vanished atom of *either* kind counts toward coverage nowhere, so `verified + unverifiable == total` stays reachable after the *common* case — an edit-succession fix — not only after a deletion. Without the successor-transfer exit, the first prose-edit fix would leave a permanently-dirty ghost exactly as an un-retired deletion would, and coverage-complete — the termination invariant — would be unreachable.
    - **Lineage, pinned:** a fixed atom's hash changes, so incremental extraction records succession — a new atom extracted from an edited region inherits the lineage id and churn counters of a **specific** vanished atom, matched by *anchor locality*: the vanished atom that shared the successor's post-reanchor section path and sat nearest it in document order. This succession key is computed deterministically by `atoms reanchor` from the pre- and post-edit ledgers, never judged, so the region↔predecessor mapping is total and reproducible. Two boundary cases are pinned so no lineage is lost:
        - a **split** (one vanished atom's region yielding several successors) forks the ancestor's lineage — every successor inherits its id and churn counters, so a twice-fixed atom that splits still escalates;
        - a **merge** (one successor spanning several vanished atoms' regions) inherits from the **highest-churn ancestor**, preserving the worst churn history.

      Identity survives fixes; without a pinned succession key, "verdict flip" and "fixed twice" would be undefined the moment the first fix split, merged, or moved an atom, and churn escalation (step 7), which tracks along lineage, would silently reset.
2. **Verify (layer 1).**
    - **Who & what:** one micro-agent per unverified or dirty atom, each answering one narrow question with minimal context and returning a structured verdict, evidence, and the exact inputs it consulted — the spec sections and external files actually read. The ledger records these as the atom's input set (produced by the act of verification, not guessed at extraction), external files stored as path plus content hash.
    - **Cross-run external-input staleness has a named owner:** the continuation-load `atoms reanchor` (run by the decompose agent when a non-empty ledger is loaded — §Continuation runs) re-hashes each atom's recorded external-input paths alongside its document re-walk and dirties any atom whose cited code changed between invocations; external files change only between runs, never mid-drain, so one re-hash at load suffices.
    - **Verdict persistence, pinned:** verifiers only *return* their verdicts and input sets under the relay contract — they never write the ledger, so the 40–80-verifier swarm never races on `concept-ATOMS.json`. The ledger has exactly two writers: `decompose` (the one-time entry pass) and `record-verdicts` at round close. `reanchor` (step 1) and `mark-dirty` (step 5) are **pure compute-and-relay** — they return the rewritten anchors, the reanchor delta (relocated / vanished / new-region flags — `reanchor` *flags* new regions but does not itself mint their atoms; the scoped extractors do, step 1), and the dirty set, and write nothing — so on every round after entry `record-verdicts` is the *single* serialized ledger write and the 40–80-verifier swarm still never races. At round close the fixer/recorder persists the whole round's delta — incrementally-extracted atoms, rewritten anchors, dirty flags, verdicts, and input sets — in one `spec_checks.py atoms record-verdicts <target> --verdicts <file>` call (the same marshal-to-file step that feeds `snapshot`, step 6). Within-round aggregation composes from the relayed returns; round-close `coverage` reads the ledger immediately after `record-verdicts` persists this round's delta (step 6's reordered close), while cross-round dirtiness is read by the *next* round's verify swarm from the persisted dirty flags.
    - **Unverifiable verdict:** a verifier that runs to completion but cannot settle its atom from the spec-plus-cited-inputs alone returns an **unverifiable** verdict — distinct from a null/dead return, which the failure policy retries. An unverifiable atom counts as **covered** for coverage-complete (it will never resolve, so re-running it every round would only livelock termination) and is recorded to IMPLEMENTER-NOTES via `append-note` — an atom the design could not settle, advisory for the implementer beside the below-bar notes — and named in the round report.
    - **The checks:**
        - claims are checked against the code they cite;
        - assumptions against whether the spec states them explicitly and either grounds them in cited evidence or, when the assumption is itself a design choice, promotes them to a D-block — an unstated or ungrounded assumption is a finding (the manual reviewer's assumptions dimension, applied per-atom);
        - citations against whether the D-block actually motivates the item;
        - examples against the adjacent contract text;
        - scope items against the Verification section;
        - D-blocks against whether the Why discriminates between choice and alternatives;
        - contracts against 3–5 enumerated edge and lifecycle questions answerable from the spec alone, plus over-specification — a code-fenced block that is a function body (an algorithm implementation) rather than an interface/contract (CLI flags, JSON/XML schema, data flow) is a finding, the manual reviewer's over-specification dimension applied per contract atom.
    - **Heading atoms carry no micro-check:** they are the anchor substrate the section-path grammar is built on, their presence and level asserted by the floor's `structure` check, so — like retired atoms — they sit outside the coverage denominator rather than awaiting a per-atom verdict that would never arrive (leaving them in it would make coverage-complete permanently unreachable).
    - **Implementability probe (scope items only):** scope items additionally get two independent agents each answering "what would you build for this one bullet, and which decisions would you have to make yourself" — a comparator diffs the answers, and divergence is an underdetermination finding.
    - **The deterministic floor** is the mechanical slice of this layer, run by a floor agent concurrently with the swarm via `spec_checks.py floor <spec-path>` — a wrapper that runs `milestone_checks.py citations` and the `structure` check and re-emits their results as one JSON verdict on stdout (per-check status, each violation a structured finding), because the underlying checks report human-readable stdout, `Error:` lines on stderr, and exit codes, which the pinned relay contract (raw JSON stdout) cannot carry; `milestone_checks.py` itself stays untouched. Because `citations` exposes **no** structured violation list — verified against source, it returns an exit code and prints one `Error:` line per violation to stderr — the wrapper derives its citation findings by capturing that exit code and emitting one finding per `Error:` line; the new `structure` check, living in `spec_checks.py`, returns its findings as structured data natively. This stderr-line capture is the floor's pinned adapter for the untouched `citations` check — an implementer must not expect a JSON list from `citations`. Floor failures are definitionally substantive and join classification like any finding.
3. **Aggregate (layer 2).**
    - **Per-section aggregators** receive only their slice's structured verdicts — never the raw dump — and compose evidence-chained candidate findings from *within-section* patterns: unanswered contract questions clustering in one section, several dirty atoms resting on one D-block. Every finding carries the atom ids it stands on.
    - **Cross-section relationships are not composed at this layer** — an isolated per-section aggregator cannot see them; they ride inside individual atoms instead. "A false claim and the D-block resting on it" is the citation atom's own check (step 2: citations against whether the D-block motivates the item) and the claim atom's own check (against the code it cites); each such atom's input set names both sections, so the linkage surfaces as that atom's failed verdict with a two-section evidence chain — not as a cross-slice aggregation.
    - **The dedup pass is a global step, not a per-section aggregator's job:** aggregators are slice-blind and never see DECISIONS.json, so the JS pools all aggregators' candidate findings and hands them, together with DECISIONS.json, to a single **dedup agent** that — *before* the gate, so a re-emission is never re-judged — folds instances of already-recorded decisions and of active (non-dropped) non-goal proposals into their records instead of re-emitting them; a fold is suppress-with-reference: the re-emission is dropped and the record id noted in the verdict log, no record mutation. A proposal the user **dropped** at a prior briefing (marked via `update-decision`, D7) is *not* folded — its underlying finding re-enters the gate as an ordinary candidate, honoring the fair-game promise (step 4) across the multi-run session, not only after a session-ending `approve`/`reject` archives DECISIONS.json.
    - **The match is semantic, not id-equality:** the re-emission dedup handles is the same decision *subject* re-surfacing in a later round, and it stands on **different atoms** than the original finding — a different part of the spec touching the same question, since the original's revealing atoms were resolved or vanished by the take — so its lineage set, and therefore its finding-id (Loop step 7: id = type + the lineage ids it stands on), differ from the original's; id-equality matches only identical lineage sets, so it cannot catch a same-subject re-emergence, and a subject-level match is required.
    - **Two neighbouring cases stay deterministic and do *not* route here:** the *same* finding re-emerging from the *same* atoms after a failed fix (identical lineage, identical id) is caught by id-equality and escalated as churn (step 7), and a below-bar finding whose atoms are untouched keeps a stable id — which is why D6's below-bar memory is deterministic id-equality. So the dedup agent alone matches by decision subject (the same question restated against the now-written D-block) — agent-judged. Its DECISIONS.json read is the decision-side analogue of the gate's IMPLEMENTER-NOTES memory.
    - **Below-bar gate memory is deterministic, not agent-judged:** distinct from the semantic dedup above, below-bar findings are dropped before the gate by a JS **set-difference** — a finding whose computed id (Loop step 7) already appears among IMPLEMENTER-NOTES' recorded finding-ids never reaches the judges. The note-ids reach the JS via a relayed `improve_files.py` call that emits them; the notes are **never** injected into judge prompts (which would re-spend gate budget re-confirming a judged-once finding and could drift as the panel changes), so D6's "matched deterministically by finding-id" is a code filter under D2, not judge attention.
4. **Gate (layer 3).** Unchanged from the prior design.
    - **The panel:** three perspective-diverse judges (*builds-wrong-thing*, *implementer-blocked*, *scope-intent-drift*) vote on the deduped findings — substantive yes/no, needs-user yes/no, and intentional-exclusion yes/no (all three judges cast the exclusion vote, so the ≥2-exclusion threshold below is reachable).
    - **Tally precedence, pinned** (`spec_checks.py tally` computes outcomes): **needs-user** (any single vote — 1-of-3, permissive, D5 — overriding the substantive tally and any exclusion votes; a decision can never be refuted into IMPLEMENTER-NOTES or excluded into a non-goal), then **proposed non-goal** (≥2 exclusion votes), then **auto-fixable** (≥2 substantive votes), else **below-bar** → IMPLEMENTER-NOTES.
    - **Shrunk task:** judges now rule on findings that arrive with verified evidence chains, so their task shrinks to "given these premises, is this substantive or decision-shaped?"
    - **Proposal lifecycle, pinned:** a proposed non-goal is recorded once in DECISIONS.json as a kind-tagged proposal record (via `append-decision`; the global dedup pass folds re-emissions into it — step 3) and is *not* a substantive finding — it parks the underlying finding until the briefing, so pending proposals never block a dry round or convergence. The briefing renders proposals alongside decisions, and `decisions summary` surfaces them (status `proposal`) for the command's approval flow. Approval routes to `append-non-goal` as today; a dropped proposal is marked `dropped` via `update-decision` (the record is retained per D11 but excluded from future dedup folding — step 3), so its underlying finding is fair game to re-enter the gate on later runs, not only after `approve`/`reject` archives the records.
5. **Fix and record.** The fixer/recorder agent is one role, but not one invocation — Decide (step 6) spawns its researchers and decision-taker as siblings *between* the fix work and the round close, and no agent can spawn siblings mid-call (only the workflow script spawns agents — Tool grants), so the role runs as a **step-5 fix-and-record invocation** plus a **separate round-close invocation after Decide** (the fix-and-record invocation splits further into the plan and apply invocations under the competitive-rewrite rule, phase H). In the step-5 invocation it:
    - runs `tally` on the raw votes (vote math is never LLM-computed);
    - appends below-bar findings via `improve_files.py append-note` (D6);
    - creates one decision record per needs-user outcome via `append-decision` — kind, title, finding, and `finding_atoms` (the lineage ids the finding stands on, empty for a macro-derived finding): the fields known at gate time (the record id is allocated by `append-decision` itself, never supplied by the context-free recorder — D7), status deriving to `pending` until Decide enriches it, so a decision that later stalls is already visible to the briefing and `decisions summary`;
    - applies auto-fixable findings, and appends one changelog entry per fix via `append-changelog` (the round snapshot happens once, at round close, step 6).

    The fixer reports each fix as the set of anchor section paths it touched (raw headings — the same `###`-or-enclosing-`##` rule as atom anchoring); `spec_checks.py atoms mark-dirty` canonicalizes those and the recorded input sets (Decompose's canonical-serialization rule) and combines them with the reanchor pass (step 1) via input-set propagation, so an atom whose *check inputs* changed re-verifies even if its own text did not.
6. **Decide.**
    - **Research:** needs-user outcomes route to one researcher per decision (codebase context, options, tradeoffs, recommendation, and a declared edit estimate — the units the recommendation would write or amend).
    - **Blast radius is measured in anchor units** — `###`-level where present (Solution subsections, individual D-blocks, Scope subsections — the granularity of the decision-record contract's radius example), the enclosing `##` section in heading-free regions; the coarse fallback inflates a radius and thus errs toward blocking, D5's safe polarity — and has two pinned measurements:
        - **Pre-take radius (gates the take):** the evidence footprint (the section units of the atoms the finding stands on, computed from the ledger by `spec_checks.py atoms radius` — run and relayed by the decision-taker, the same agent that then invokes `block-gate`; the atom count rides along for precision). **The union with the researcher's declared edit-estimate section set is `block-gate`'s, not the decision-taker's:** the taker passes the two section sets — the relayed `atoms radius` footprint and the researcher's estimate — to `block-gate` as separate inputs, and the script unions them before counting, so no set arithmetic is ever performed by an LLM (D2). A decision that looks local by evidence but whose resolution would rewrite three sections still trips the gate.
        - **Post-take radius:** the actual edit footprint — the section paths the take touched plus the atoms it dirtied, written back into the decision record — and is what `depends_on`, briefing ranking, and override re-drains consume.

      In phase H (empty ledger) the researcher names the units for both.
    - **The graded gate is computed, not judged:** a decision-taker applies D5's graded gate but does not *compute* it — the taker declares the two irreducibly-semantic inputs (whether the decision would reverse an explicit user directive, and whether it would reverse a NON-GOALS entry) and passes them, together with the two pre-take section sets (the relayed evidence footprint and the researcher's edit-estimate), to `spec_checks.py block-gate`, which unions the two sets and returns `takeable | blocked` deterministically (`blocked` iff either boolean is set **or** their union spans three or more distinct anchor units; the ≥3 threshold is D5's tunable constant). The taker relays that verdict, never the arithmetic — D2.
    - **On `blocked`:** the round finishes its bookkeeping (records, snapshot), then the run exits `blocked` carrying every untakeable decision from that round; building further on undecided ground of that size is the cascade risk.
    - **On take (every other decision):** the recommendation by default; on low confidence or a **near-tie** — the researcher-declared `near_tie` boolean on the record, set when its top two options fall within a small value margin — the smaller-blast-radius option with `review_first` set. `review_first` fires on low confidence, a near-tie, or a large but sub-threshold pre-take blast radius (the two-unit maximum below the block threshold) — so the flag rides on an objective, ledger-computed signal (blast radius) as well as the researcher's self-assessment, never on self-graded confidence alone. The take is not separately adversarially reviewed by an agent: every decision is reviewed by the user in the briefing (nothing is approved unseen), so the briefing *is* the recommendation's review. Taking a decision writes or amends the corresponding D-block in the spec (an ordinary fix: changelog entry, atoms dirtied) and completes the gate-time record via `improve_files.py update-decision` — research, options, `taken`, `taken_by: auto`, confidence, `review_first`, radii; a blocked decision gets `untakeable` written instead of `taken`.
    - **`depends_on` is recomputed at render time, not frozen at take time.**
        - **Mechanical edges are directional by record id:** B depends on A when B's post-take radius overlaps a unit that taking A wrote or amended **and A's id orders before B's**. Because ids are a total order, the relation is a **DAG by construction** — an edge only ever points from a later record to the earlier one it builds on, so no overlapping pair can edge both ways and no mechanical cycle can form. (Ids are allocated in gate order and decisions are normally taken in that order, so id order tracks take order; the two diverge only when research stalls a decision across rounds, where the edge direction is then a harmless heuristic — every decision is user-reviewed regardless.) Both `spec_checks.py briefing` and `decisions summary` recompute these edges over *all* records' post-take radii each time they run (the same pure function of radii-plus-id-order, so `decisions summary` and the briefing agree by construction); recomputing at render — rather than freezing at take time — is why a later decision's dependence on an earlier record is never lost even though the earlier record froze first.
        - **Semantic edges are stored:** only *semantic* edges — a dependency the radius rule cannot see, and the only kind that may point against id order — are stored on the record as `semantic_depends_on`, written by the decision-taker (the one party that sees the round's full batch plus the accumulated DECISIONS.json; per-decision researchers are blind to siblings) and unioned with the recomputed mechanical set at render.
        - **Cycles never suppress a briefing:** a stored semantic edge could in principle close a cycle against the mechanical DAG, so `spec_checks.py briefing` still **renders every record unconditionally** — the every-approval-gets-a-briefing invariant is absolute — breaking any residual cycle by a *defined* tiebreak (descending pre-take radius, then id) and flagging the circular edge inline; it never exits without a briefing.
    - **Round close, pinned:** after Decide completes (a no-op on a round with no needs-user outcomes), the round-close fixer/recorder work — a single invocation, or two split around the workflow's incremental-extraction spawn when `reanchor` flags new regions (step 1) — in order:
        - **first re-runs `reanchor` + `mark-dirty` over the working copy** to fold in every edit made *after* step 5 — each decision-take's D-block write or amendment (step 6), and a directive run's apply-agent edits — into the round's ledger delta; the step-5 pass caught the auto-fixes, this pass catches the rest, and without it a decision-take's atoms would never enter the ledger, so `coverage-complete` could pass over unverified decision-take text (the common case — most specs take a decision) and computed termination would break. When this `reanchor` reports new regions the workflow spawns the scoped prose extractors (step 1's incremental extraction) before the round-close agent continues, so their newly-minted `unverified` atoms join this round's delta;
        - **then persists the whole delta first, via `atoms record-verdicts`:** the round-close agent serializes the JS-marshaled round outputs (this fresh context-free agent holds none itself — the verdicts, findings, votes, and tally are relayed in by the JS from the round's other agents) to a structured JSON verdict-log file (per-atom verdicts — each carrying its verdict state, the hash it was computed against, and the input set the verifier reported — tagged with the layer-1 agent that produced it, plus the round's `reanchor` delta and dirty set and any incrementally-extracted atoms, and the deduped findings with their ids, the judge votes, the tally outcome) and passes its path to `atoms record-verdicts`, which applies the round's whole delta to the live ledger — incrementally-extracted atoms, rewritten anchors, dirty flags, verdicts, input sets, and any macro-finding `fix_count` bumps (step 7) — hash-guarded; the sole round-close writer;
        - **then runs `atoms coverage`** — which emits `{verified, unverifiable, total, complete, never_verified}` — relayed; because it runs *after* `record-verdicts`, `complete` reflects this round's just-persisted delta rather than a round-stale ledger, so the drain branches (phase-E entry consumes the verdict) on the current round's state — a real ledger computation, never a JS re-derivation (D2). A fix round is therefore never spuriously `complete`: its just-dirtied atoms and just-minted `unverified` atoms are already in the ledger `coverage` reads;
        - **then snapshots the round** — working copy plus the same verdict-log file — via `snapshot --verdicts` (D11), which archives both into `history/` — so the agent only marshals its own outputs while every `history/` write stays in the script (D11's exclusive-writer rule holds), and a round's layer-1 agent count is recoverable from its atom-verdict entries (the cross-invocation-persistence and swarm-shrinkage checks read it).

      Exactly one snapshot per round, taken after decision-take edits so they land in their own round's snapshot; the bookkeeping named by the blocked exit is this same round-close snapshot, never a second one.
7. **Loop.**
    - **Loop condition:** rounds continue while `atoms coverage` reports `incomplete` — dirty or unverified *live* atoms remain, scoped to the same heading- and vanished-excluding denominator coverage-complete uses (§Command flow), never a raw unverified-atom count that a freshly re-minted heading atom would hold nonzero forever — or the gate yields substantive findings, or a decision is still `pending` (its research or take re-attempted in Decide).
    - **Churn escalation:** an atom whose verdict flips across re-verifications (its ledger `churn.verdict_flips`, tracked along lineage, step 1), or a finding whose lineage atoms have accumulated `churn.fix_count` ≥ 2 yet re-emerges, escalates to the decision machinery (step 6) instead of a third fix attempt — fixes that don't stick are evidence the disagreement is decision-shaped, not mechanical.
    - **Finding identity is deterministic:** at aggregation each finding receives an id computed from its type plus the lineage ids of the atoms it stands on — "re-found" is id equality of that recomputed id, never the workflow's recollection. Both churn signals are read from the **ledger** (drain-readable via `atoms` subcommands); the per-round verdict log records the same ids for audit but lives in `history/`, which the drain never reads (D11).
    - **Macro findings** (phase H and the exit exam) stand on no atoms, so their churn cannot ride atom lineage. Each is instead recorded in a small **macro-finding table inside the ledger** (`concept-ATOMS.json`, managed by the same `atoms` subcommands and drain-readable like the atom churn counters — D10), keyed on the finding's id (macro class plus the *canonicalized* section-path set it names — the Decompose canonical-serialization rule makes the key byte-stable) and carrying its own `fix_count` that `record-verdicts` bumps at round close and the drain reads via `atoms`. Churn escalation thus fires uniformly on both paths — a twice-fixed contradiction escalates whether it surfaced horizontally or from the pyramid — with one bounded residual: a fix that *renames* a section the finding names changes its id and resets the count, but that rename is itself a structural edit (the trigger below) that re-checks the touched slice, so the finding is re-found fresh rather than lost, and the pathological "rename a named section every round without resolving it" case is bounded by the round cap, not silent.
    - **Structural-edit trigger, pinned (D12):** a fix or decision take whose declared fix plan replaces at least one whole anchor unit — the same `###`-or-enclosing-`##` grammar the fixer already declares for competitive rewrites — queues a scoped horizontal re-check of the touched slices; the re-check runs as the next round's opening step (before decomposition), counts against the round cap, and its findings enter the same gate. The competitive-rewrite mechanism fires wherever the whole-unit condition is met — a phase-P fix, a decision take, or an exam finding, not only phase H.

**Phase E — Exit exam.**
- **Entry requires:** ledger coverage-complete (every *live* atom — present hash, non-heading — either verified against current text or marked unverifiable; vanished atoms sit outside the denominator per Retirement/Lineage — a deterministic check), one dry gate round, and floor green.
- **The exam:** a fresh whole-document read by agents that saw nothing earlier, with two targets — what atoms cannot compose into (atoms compose locally, and every brick can verify while the building leans) and what extraction never atomized (since ledger coverage is only as complete as extraction recall, D4).
- **Outcome:** exam findings re-enter phase P; a clean exam ends the run.

**Termination, pinned:**
- **`converged`:** clean exam with no decision still `pending` (a pending record — research or take never completed — re-enters Decide each round via the script's own null-call bookkeeping, so it resolves, blocks, or survives into the round-cap report and briefing).
- **`blocked`:** any untakeable decision, at the end of the round that produced it (step 6 — so an undischarged blocked decision can never coexist with the exam).
- **`round-cap`:** round cap (10, phases H and P combined — a generous safety backstop, not a convergence estimate; D4) reached first.
- **The cap is per drain run (per invocation):** a `blocked` resume or an override re-run is a fresh Workflow invocation with its own cap of 10, not a continuation of the prior run's count — so a spec that blocks once has a 10 + 10 round budget across its two runs, and the cap bounds each drain against non-termination without bounding the multi-run refinement of a hard spec.

**Continuation runs (no directives), pinned.** A `round-cap` re-run or a Setup-step resume that carries no directives is neither a first run nor a directive run, and its phase behavior keys on ledger state — never on scoping, which belongs to directive and structural-edit re-checks alone.
- **Empty ledger** means a prior run never cleared phase H (decomposition waits on a clean horizontal pass, D12), so phase H resumes as a full whole-document pass and phase P is entered only once it clears, exactly as on a first run — this forecloses the empty-ledger livelock (a phase H scoped to nothing is skipped, then the dirty set is empty because decomposition never ran, so the run does nothing and re-exits).
- **Non-empty ledger** means phase H already cleared in a prior run, so the continuation loads and reanchors the persisted ledger and resumes phase P on the carried dirty and unverified set (D4's cross-invocation reuse), re-running phase H only if the Loop step's structural-edit trigger fires.
- **Pending decisions survive the invocation boundary through DECISIONS.json, not JS memory:** a continuation run rebuilds its Decide re-attempt queue from the `status: pending` records on disk — a pyramid decision carrying the `finding_atoms` whose radius `atoms radius` recomputes, a macro decision (empty `finding_atoms`, per the record shape) re-deriving its radius from the re-run researcher instead (Decide) — because the null-call carry bookkeeping that re-enters Decide *within* a run is a loop variable that does not cross invocations (D10); the file is the cross-invocation source of truth.

On a directive-carrying run, an **apply agent** runs first.
- **It executes both channels against the working copy** — the structured `overrides` and the free-form `directives` (changelog entries logged; touched atoms dirtied).
- **Per `overrides` entry** (carrying the `decision_id` known at collection time) it writes the resolution into that record via `update-decision` and re-dirties the decision's edit footprint, differing by case:
    - an **overridden take** (already `taken`) re-dirties the recorded `post_take_radius` — the footprint the prior take wrote, now being redone — and its prior take moves to `superseded`;
    - a **resolved blocked** decision was never taken (`post_take_radius` is null, per the record schema), so the resolution is its first-ever take — the apply agent's own edit dirties the touched atoms as any fix does, there being no prior footprint to re-dirty, and `update-decision` writes the now-known `post_take_radius`.

  Either case gains `taken` plus `taken_by: user` — so no stale `blocked` card and no superseded take can render in a later briefing or `decisions summary` view. (A free-form `directive` names no decision and writes no record — an edit only, e.g. "section 4's approach is wrong, redo it".)
- **Then the phases proceed scoped — but scoping keys on ledger state, never on the presence of a directive alone (§Continuation runs):**
    - on a **non-empty** ledger (phase H already cleared in a prior run) phase H runs as D12's scoped horizontal re-check over the directive-touched slices, not a fresh whole-document pass, and phase P re-verifies only the dirty set — into which the apply agent's edits have already been folded by a `reanchor` + incremental-extraction pass over the working copy, so directive-*added* new prose is atomized and enters the pyramid rather than being left to the exit exam alone;
    - on an **empty** ledger (a prior run blocked or hit round-cap *during* phase H, before decomposition ever ran) the directive run instead runs a full phase H and a full decomposition, exactly as a no-directive continuation does — a phase-H re-check scoped to an empty ledger would decompose nothing and converge vacuously (the same empty-ledger livelock §Continuation runs forecloses);
    - the exit exam alone stays whole-document — the one deliberately unscoped read, because a directive can break coherence anywhere.
- **The bounded-reversal promise is thus precise:** horizontal and layer-1 work scale with the override's footprint, and the fixed cost of any re-run is one whole-document exam. Resolutions create new review surface and must be re-reviewed like anything else.

Cost shape: discovered at runtime, not scheduled. The first sweep is wide — one micro-agent per atom, roughly 40–80 for a ~250-line spec and scaling with length (a detailed 500+-line spec like this concept runs ~100–160, still well inside the agent-ceiling margin, D4) — but each task is tiny; later rounds shrink with the dirty-atom count, and a near-clean round is a handful of agents. Dozens of small agents, never hundreds of heavyweight ones, and never a whole-milestone implementation simulation (a spec can span 30–50 implementation plans; the per-scope-item probe yields the same divergence signal at tractable size).

**Failure policy, pinned.** The Workflow layer already retries schema-mismatched returns; beyond that, an agent call that comes back null (skipped, or dead after the tool's own retries) is re-spawned once by the script. After that one retry, failures degrade by layer, never silently:
- **micro-verifier** that dies (null after its one retry) leaves its atom unverified — distinct from an unverifiable *verdict*, a completed check that cannot settle and counts as covered (Verify step) — so coverage-complete fails deterministically on the dead atom, it re-enters the next round's swarm, and persistent death surfaces in the round-cap report naming the never-verified atoms;
- **prose extractor** that fails degrades the union-merge to the surviving extractor's output (recall drops; the exit exam is the named guard);
- **judge seat** that fails is re-spawned once like every other layer — if the panel still holds fewer than three votes after that retry, the round ends unsnapshotted and the run exits `round-cap` naming the incomplete panel (`tally` rejects vote sets of fewer than three, so a short panel can never be tallied silently);
- **aggregator** that fails leaves its section uncomposed for the round, treated like dirty coverage and re-attempted next round;
- **researcher** that fails carries its decision to the next round untaken rather than taking it un-researched — the script re-spawns it in the next round's Decide from its own null-call bookkeeping, its gate-time record (status `pending`) keeping the decision visible to the briefing and `decisions summary` whatever the exit;
- **fixer/recorder** that fails is re-spawned once with the changelog as reconciliation input — each fix is immediately followed by its `append-changelog` entry, so the successor diffs the changelog against the tally outcomes and resumes without double-applying; on the competitive-rewrite two-invocation path (phase H) this one retry covers the plan and apply invocations independently, the changelog diff making either resumable — and if the retry also dies, the round ends unsnapshotted and the run exits `round-cap` naming the failure.

**Every unenumerated role degrades identically:** the decompose agent (its death leaves phase P with no ledger), the decision-taker, the directive apply agent, the floor agent, the dedup agent, the phase-H horizontal readers, the phase-E exam readers, and the implementability-probe comparator are each re-spawned once and, if still null, end the round unsnapshotted and exit `round-cap` naming the role — so "degrade by layer, never silently" is a property of the whole roster, not only the six layers spelled out above.

### The two gates

The gates answer different questions and deliberately carry opposite default polarities (D5):

- **Termination gate (skeptical, default-refute).** Bar: *name the concrete failure at implementation time if this is not fixed* — the implementer builds the wrong thing, gets stuck, or must come back and ask. No nameable failure → below bar. This replaces the relative critical/major/minor scale with an absolute, falsifiable test that does not drift as the spec improves — which is what makes the loop self-terminating. The bar's third clause ("must come back and ask") is the hand-off guarantee, and it holds by construction, not by judge discipline: the tally escalates on any single needs-user vote before the substantive tally is consulted, so a decision-shaped finding can never be refuted into IMPLEMENTER-NOTES (precedence order pinned in the pyramid gate step).
- **Escalation gate (permissive, default-surface).** Bar: *does resolving this change intent, scope, or architecture?* If plausibly yes, it becomes a decision — researched, then auto-taken and recorded for the briefing, or blocked if it trips D5's graded thresholds. Failure costs are asymmetric: a wrongly suppressed decision becomes an implementer's guess (the 5–10x cost this pipeline exists to prevent); a wrongly surfaced one costs briefing-review minutes. Auto-taking relocates the user's judgment from mid-run to the briefing without weakening it: every taken decision is recorded with its alternatives and blast radius, and overriding one is a bounded re-drain, not a restart.

## Design Decisions

### D1: Separate command; `spec-improve` stays untouched

**Choice:** Build `mg:spec-improve-auto` as a new command. `mg:spec-improve` keeps its current behavior as the manual path.

**Why:** The per-round fix cap and human gate exist on purpose for the manual path — cheap, controllable, appropriate for small specs. The autonomous variant has a different cost/control profile; forcing both into one command means mode flags and conditional behavior in an LLM-interpreted .md.

**Alternatives rejected:** Replacing `spec-improve` (removes the cheap manual option); one command that escalates to the workflow when finding volume warrants (adds a volume-estimation step and conditional orchestration for little gain — the user knows which mode they want).

### D2: Workflow tool for orchestration; JS carries control flow and prompts only

**Choice:** The drain loop is a Workflow-tool script (plain JavaScript — the only language the tool executes). The JS carries *only* control flow and prompts: agent prompt templates, fan-out structure, branching on script-computed statuses, and trivial loop variables (round index, dry flag, result accumulators, and null-call carry bookkeeping — churn state is ledger-owned, per D10). Every deterministic judgment computation — vote tallying, classification precedence, the checks floor — lives in Python under `spec/scripts/` (pytest-covered), invoked by the workflow's agents via Bash.

**Why:** The self-driving property depends on the loop being code, not LLM-followed instructions — round discipline, vote thresholds, and termination must not drift over many autonomous rounds. Only the Workflow tool provides deterministic multi-agent control flow; Python scripts cannot spawn agents. And that control flow is the point, not a scheduler: the drain is adaptive, never a naive fixed-N re-iteration. Rounds continue only while dirty atoms or substantive findings remain (loop-until-dry), fan-out is sized by each round's actual content (one micro-agent per dirty atom, one researcher per decision), stages run conditionally (the apply agent only on directive-carrying runs; aggregation and gate only when there are verdicts to compose), and stuck work changes route (flipping atoms and twice-fixed findings escalate to the decision machinery instead of a third attempt). The implementation must lean on these dynamic primitives — outcome-driven loops, conditional stages, content-sized fan-out — wherever the drain's shape depends on what a round found.

**Alternatives rejected:** Agent-tool orchestration from the command .md (the codebase-health pattern) — zero JS and full repo precedent, but the loop itself becomes LLM-interpreted instructions, reintroducing exactly the drift this concept eliminates. The stronger variant — .md orchestration plus a `drain_state.py` state machine that ingests each round's verdicts and prints the binding next action (LOOP / CONVERGED / BLOCKED / ROUND-CAP), the `milestone_checks.py` "the script decides" pattern — removes decision drift but not execution drift: spawning dozens of agents per round, in order, with correct context threading, for up to 10 rounds remains LLM-followed procedure; every round's outputs pile into the main conversation exactly where discipline must survive longest; and the adaptive behaviors above flatten into a static re-run schedule. With the vote math already in Python (D4, D5), dynamic multi-agent control flow is precisely the residual value the Workflow tool buys. Keeping the JS thin preserves this repo's markdown/Python separation rule with one added clause: JS = control flow + prompts.

### D3: Finding production = horizontal pass + verification pyramid

**Choice:** Macro issues (gaps, disconnects, contradictions, simpler whole design) are found by a small set of whole-document agents in a horizontal phase that runs and settles first (D12). Everything decomposable is found by the pyramid (D13): typed atoms verified by micro-agents, composed upward by per-section aggregators into evidence-chained findings. There is no lens-reviewer fan-out.

**Why:** LLM accuracy scales inversely with task scope — "is this one claim true against this one file?" is near-lookup; "is this 250-line spec sound?" is an impression. Building findings from verified premises means a false premise must survive a nearly mechanical check before it can mislead a judge; false positives carry a traceable evidence chain (the failing atom is named); and coverage stops being "no reviewer found more" and becomes ledger accounting. The irreducibly holistic checks stay with whole-document agents — contradictions across distant sections and the simpler-alternative question (historically the single highest-value finding) do not decompose.

**Alternatives rejected:** Four lens reviewers over the whole document (this concept's own prior design — big open-ended tasks whose impressions the judges then re-litigate impression-against-impression; coverage unmeasurable; findings without evidence chains); one agent per review dimension (same problems with more agents); whole-milestone implementation simulation as the implementability check (a spec can span 30–50 implementation plans — the per-scope-item probe yields the same divergence signal at tractable size); the no-ledger hybrid — Workflow orchestration plus evidence-required whole-document reviewers feeding the same judge panel, tally, auto-take, and briefing machinery. This is the nearest simpler design: it solves all four stated Problems and drops the lineage, input-set, and merge machinery entirely. Rejected with eyes open: what it cannot provide is precisely what the autonomous loop stands on — coverage reverts from ledger accounting to "no reviewer found more" (dissolving D4's deterministic termination clause back into judgment), every round re-decomposes and re-verifies the whole document, and — because LLM extraction is non-deterministic — the atom set jitters run-to-run, so finding-ids drift and the below-bar memory (D6) and churn escalation (D13) that depend on stable identity leak and misfire; over the 10–20 rounds these specs actually take (Situation), that thrash is a convergence hazard, not a cost line. And verification reverts from near-lookup one-atom checks to whole-document impressions with an evidence requirement bolted on. **The ledger's load-bearing purpose is convergence stability at realistic round counts** — stable cross-round atom identity (reanchoring, lineage) keeps finding-ids stable so below-bar memory and churn escalation actually hold across many rounds, which is what lets a deep spec converge rather than thrash to round-cap (D4, D6, D13); shrinking per-round cost is a real but *disclaimed* side benefit (NON-GOALS accept cost), not the justification, and computable blast radii is a minor convenience the phase-H researcher-declared path already covers ledger-free (D9). The hybrid remains the named fallback, and the two bets it hedges falsify at different checkpoints: the **ledger-fidelity spike** (Verification) falsifies the ledger's *accounting fidelity* — spans, hashes, touched-section reports, its LLM-sourced inputs — not its convergence value, which no spike can measure; the **first real run's `history/` record** falsifies the *convergence value* — whether finding-ids stabilize round-over-round so below-bar memory and churn escalation hold, or jitter and thrash toward round-cap. A fidelity failure or an observed thrash fires the fallback; the convergence value is a bet-the-design hypothesis, not a tunable constant (Open Items).

### D4: Termination = coverage-complete ledger + dry gate + exit exam

**Choice:** Finding and judging stay separated; the three-judge panel and `spec_checks.py tally` are unchanged. Convergence is three-part: the atom ledger is coverage-complete (every *live* atom — present hash, non-heading — either verified against current text or marked unverifiable — deterministic), the gate yields one dry round, and a fresh whole-document exit exam finds nothing substantive. The exam replaces the prior rule's second consecutive dry round with a stronger, different-modality guard. **Round cap: 10 across phases H and P per invocation** — a deliberately generous *safety backstop*, not a convergence estimate. A healthy drain converges well below it via loop-until-dry plus the exit exam; the cap fires only on a spec that is not converging, turning what would otherwise be a runaway (up to the Workflow tool's 1000-agent lifetime ceiling) into an honest non-convergence report that is itself the signal *this spec has a structural problem*. Because the cap counts *rounds* while the Workflow ceiling counts *agents* — and the ceiling's exceed-behavior is undocumented (it may throw rather than degrade gracefully) — the same graceful exit carries a second trigger: the JS tracks cumulative agents spawned this run and, before opening a round, **projects that round's width** — across every agent class the round will spawn, not only the dominant dirty-set term: the verifier per dirty or unverified atom, the floor agent, the per-section aggregators, the dedup agent, the three judges, one researcher plus the decision-taker per pending decision, the two implementability probes plus their comparator per dirty scope-item atom, the scoped prose extractors for any regions awaiting incremental extraction, any scoped phase-H re-check, and competitive-rewrite pairs — and fires the identical `round-cap` exit (snapshot intact, honest report) if cumulative-plus-projection could cross 1000, so the guard tracks the *actual* next round's width rather than betting on a fixed headroom: a pathological round can stack all of those together, wider than a first sweep, so a fixed first-sweep headroom could let such a round start just under the line and cross 1000 mid-round. A conservative static floor (initial value 900) backs the projection where it is uncertain — an accepted initial calibration tunable from `history/`, Open Items, lowered if a real round's peak leaves under one round's headroom — so a runaway trips this before round 10 rather than crossing the ceiling mid-round. This is one brake with two triggers, not a new mechanism: a healthy drain trips neither (incremental re-verification keeps cumulative agents far below 1000 — Situation, D13), while a non-converging spec that sustains a large dirty set trips whichever comes first. The agent trigger is crash-safety for D4's own guarantee — without it the runaway case the cap exists for could reach the ceiling mid-round, whose exceed-behavior is undocumented (a throw or silently dropped calls, either destroying the very report the cap promises) — not a cost cap (cost is accepted, NON-GOALS). The number is low-stakes by construction: overshooting costs one cheap resume — the ledger persists across invocations, so a re-run re-verifies only the dirty atoms, not the whole spec — never a failure. The manual tool's 10–20-round pattern (Situation) is not the comparison: those are human-gated re-invocations under a relative grader that never self-terminates. A pyramid drain should need materially fewer rounds (the per-round fix cap is gone; termination is computed, not judged), but a deep spec may still exceed one invocation's cap and continue across runs — the cap is set so most healthy specs finish in one drain while leaving that multi-run path open.

**Why:** Reviewers are relative graders — "reviewer finds nothing" never fires, which is why termination must be computed. The ledger makes the largest share of it *checkable* rather than judged: dirtiness is mechanical over the recorded edges (hash + input set — the edges themselves are declared by the verifiers as the inputs they actually read, the one LLM-sourced input the accounting trusts), so "nothing left to verify" is an accounting fact given honest input reporting. The other caveat is extraction recall: coverage is complete relative to the extracted inventory — a claim both prose extractors missed has no atom, verifies nowhere, and the ledger reports complete regardless; redundant extraction raises recall but cannot prove it, and the exit exam is the named guard for what was never atomized (phase E). What remains judged — the dry gate round and the exam — is guarded against premature convergence by modality diversity (auto-doc's "default to CONTINUE if unsure" precedent): a second identical dry round re-asks the same question of the same kind of agents, while a fresh whole-document read asks a different one. The final human briefing means a wrongly-dropped finding costs a later round, not a bad merge.

**Alternatives rejected:** Loop-until-reviewer-silence (structurally never terminates); two identical consecutive dry rounds (this concept's own prior rule — redundancy without diversity); per-finding refuter trios (the panel already diversifies perspective, and evidence chains shrink what is left to refute); trend-based stop like auto-doc's assess-convergence alone (advisory trends still need a human to call it; the falsifiable bar decides per-finding).

### D5: Two gates with opposite default polarities; escalation is graded

**Choice:** The termination gate is skeptical (default-refute; bar: name the concrete implementation-time failure). The escalation gate is permissive (default-surface; bar: plausibly changes intent, scope, or architecture) — and surfacing has two grades: **auto-take** (the default — research, take the recommendation, record for the briefing) and **block** (the exception — the decision would reverse an explicit user directive or a NON-GOALS entry, or its pre-take blast radius — evidence footprint ∪ declared edit estimate, the two-measurement rule pinned in the pyramid's Decide step — spans three or more anchor units — `###`-level where present: Solution subsections, individual D-blocks, Scope subsections; the enclosing `##` section in heading-free regions, a coarse fallback that errs toward blocking, the safe polarity). The threshold's logic: one unit is a local change, two is a mechanism plus its D-block, three means the decision has crossed into neighboring design territory — architecture-scale, where a wrong autonomous guess cascades. The block decision itself is **computed, not judged**: `spec_checks.py block-gate` unions the two pre-take section sets it is given, applies the ≥3-distinct-unit count over that union, and ORs the two reversal booleans (the only *semantic* inputs, declared by the decision-taker; the union itself is the script's, not the taker's), so the threshold cannot drift across autonomous rounds — D2's determinism rule applied to the design's highest-stakes branch.

**Why:** They answer different questions with asymmetric failure costs. Suppressing a real decision silently converts it into an implementer's guess — the 5–10x downstream cost. Surfacing a borderline one now costs briefing-review minutes, cheaper still than a mid-run stop — the permissive polarity is preserved while the human gate moves to where it is cheapest. The block grade exists because auto-taking an intent-reversing or spec-wide decision would relocate the 5–10x guess rather than eliminate it: everything downstream of a wrongly-taken root decision is cascade rework. The specific cutoff — three anchor units — is an initial calibration, not a validated constant: the design has no runtime data yet. It is fixed at three now, with the error direction chosen deliberately — when the right cut is uncertain, bias toward blocking (a spurious block costs one discussion; a wrong auto-take costs cascade rework — the same safe polarity as the coarse `##` fallback), and `history/`'s per-run decision records (D11) are the substrate for tuning it once the first real runs exist. The tally rules encode the polarities: an auto-fix requires ≥2-of-3 substantive votes (skeptical), while a single judge's needs-user vote escalates — taking precedence over both the substantive tally and any exclusion votes, so a decision can never be out-voted into silence (permissive; full precedence order pinned in the pyramid gate step).

**Alternatives rejected:** One gate for both (forces a single bar that is either too strict for escalation or too loose for termination); blocking on every decision (this concept's own prior design — a dozen mid-run stops for decisions the briefing handles post-hoc at lower cost); auto-taking everything (an intent-reversing decision must never be guessed).

### D6: Below-bar findings persist in an IMPLEMENTER-NOTES sidecar

**Choice:** Gate-refuted findings are appended once to `concept-IMPLEMENTER-NOTES.md` (NON-GOALS-style format) — each bullet tagged with its finding-id as metadata — and filtered out **before** the gate by **id-equality**: a deterministic JS set-difference of each round's computed finding-ids against the notes' recorded ids (the same finding-id used by churn escalation, pyramid step 7; mechanism pinned in the pyramid's dedup step), never a prose comparison and never judge-prompt injection, so re-wording cannot slip a judged finding past the memory and the gate never re-spends budget re-confirming it. The file survives approval as advisory input for the implementer.

**Why:** Without memory, the same minor finding resurfaces every round and burns gate budget (the auto-doc dismissed-entities problem, solved the same way: persistent judged-once lists). A sidecar keeps the frozen spec clean and mirrors the established NON-GOALS convention.

**Alternatives rejected:** Open Items section (leaks into v2-requirements projection — `spec-create-milestone` routes deferred Open Items there); NON-GOALS (wrong semantics — those suppress reviewer flags for *intentional exclusions*, not below-bar observations); an in-spec `## Implementer Notes` section (breaks template symmetry, visible to future reviewers as an unexpected section); report-only (lost after the session).

### D7: `improve_files.py` hardening — init guard (breaking) and sidecar lifecycle

**Choice:** `init` refuses to overwrite an existing working copy (exit 1, loud message); a new `--fresh` flag forces the old reset behavior. A read-only `paths` subcommand emits the same resolved-paths JSON as `init` without touching any file — the resume entry point after a guard failure or session crash. New subcommands: `append-note` (IMPLEMENTER-NOTES, mirroring `append-non-goal`, plus the finding-id recorded as metadata on the bullet so gate memory matches by id), `note-ids` (read-only; emits on stdout the JSON list of finding-ids currently recorded in IMPLEMENTER-NOTES — the relayed input for D6's pre-gate id set-difference, parsed from the id metadata `append-note` writes; emits an empty list when the file is absent), `append-changelog` (per-fix entries — the fixer never writes sidecars by hand), `append-decision` (creates one record in DECISIONS.json — a gate-time decision record, or a kind-tagged non-goal proposal record; **allocates the record id itself** — the next `R{n}` by scanning the live file's existing records, echoed on stdout, so the context-free recorder passes only kind/title/finding and ids cannot collide across rounds or runs; creates the file if absent; the recorder never hand-writes the JSON; D9), `update-decision` (merges enrichment or resolution fields into an existing record by id — research, options, `taken`, `taken_by`, `untakeable`, `dropped` (marks a non-goal proposal the user declined — the record is retained but the dedup pass stops folding its re-emission, so the parked finding re-enters the gate; fair-game across runs, step 3), confidence, `review_first`, radii, `semantic_depends_on`; refuses an unknown id, exit 1; a replaced `taken` moves into the record's `superseded` list rather than being erased — D11 applied to records), and `snapshot` (`snapshot <target> --run N --round M --verdicts <file>`: copies the working copy to `history/run-N/round-M.md` and stores the verdict log; refuses to overwrite an existing `round-M.md` — a collision means a reused run number — exit 1, D11). `init` and `paths` emit the notes and changelog paths, the `source` path itself — the `<target>` argument every `improve_files.py` subcommand keys on; agents inside the drain receive paths only through args, so without this key no sidecar-writing call is addressable — plus `next_run` (derived by scanning `history/`). **Sidecar lifecycle, pinned:** `approve`/`reject` delete the working copy and **move** — not copy — the changelog, atom ledger, and decision records into the latest `history/run-N/` (D11), each move skipped when its sidecar is absent — so the shared `approve`/`reject` invoked from plain `spec-improve`, which writes none of the three, archives nothing and errors on nothing — or, when the run died before any round-close so no `run-N/` exists yet (failure policy), into a freshly-created next `run-N/`, so a live sidecar is never left un-archived; IMPLEMENTER-NOTES stays, per D6, as advisory input for the implementer. `init --fresh` archives harder: it moves those three *plus* IMPLEMENTER-NOTES into `history/` before resetting the working copy from source — the session is being discarded, and a stale DECISIONS.json would render ghost decisions into the next briefing while a stale ATOMS.json would seed reanchor with hashes from a discarded document. NON-GOALS alone always survives: user-approved scoping, not session state.

**Why:** The always-reset behavior silently destroys unapproved fixes in every pause-and-resume flow — acute for a tool that brackets discussions with multiple runs. Failing loudly surfaces leftover state; plain `spec-improve` gets safer for free. All file operations stay in the script per repo convention. Breaking change, per this repo's stated preference over compatibility shims.

**Alternatives rejected:** Orchestrator discipline alone ("only call init once") — protects nothing across session crashes and resumes.

### D8: Deterministic floor = existing `citations` check + a new structure check; verification coverage stays LLM-judged

**Choice:** Per-round deterministic checks are `milestone_checks.py citations` (exists, standalone-capable) and a new `spec_checks.py structure <spec-path>`, both invoked through the `spec_checks.py floor` wrapper so their text/stderr/exit-code reporting reaches the workflow as relay-compatible JSON — the wrapper turns `citations`' exit code plus its stderr `Error:` lines (its only output; it exposes no structured list) into one structured finding per line, while `structure` emits findings natively (pinned in the pyramid's Verify step). **`structure` contract:** it asserts the file is non-empty and that the required template headings are present — the fixed set `## Situation`, `## Problem`, `## Solution` with `### Overview`, `## Design Decisions`, `## Scope` with `### What gets built` and `### What does NOT get built`, and `## Verification`. `## Open Items` is **not** required: the template defines it as a temporary section a mature spec legitimately empties or drops, so requiring it would fail exactly the finished specs this tool produces. The concept-specific subsections (the variable Solution components and the `### Dn:` blocks) are unchecked — their names and counts are not fixed by the template. Because `citations` independently fails when `### What gets built` is absent (it then has no bullets to validate), the `floor` wrapper **dedups** — keying on the **heading name** it parses out of `citations`' `Error:` line, not the full human-readable message string, so a reworded `citations` message cannot silently defeat the dedup: a heading both checks report missing appears once in the merged verdict, attributed to `structure`, with the dependent `citations` failure suppressed. Scope↔verification coverage remains an LLM-judged check — a layer-1 atom check in the pyramid (D13).

**Why:** Deterministic checks cannot be sweet-talked and cost nothing — use them wherever no judgment is needed. But making #9 deterministic requires a citation-like link syntax between Scope bullets and Verification items — a template change rippling through spec-draft, spec-improve, and create-milestone. Wrong blast radius for this concept.

**Alternatives rejected:** Verification link syntax in the template (cross-command contract change; deliberately excluded); no floor at all (wastes gate budget on mechanically checkable failures).

### D9: Decisions are auto-taken and reviewed post-hoc via a deterministic briefing

**Choice:** Each needs-user finding becomes a researched decision: finding, codebase research, options with tradeoffs, recommendation, blast radius per the two-measurement rule (the pre-take radius gates the take; the recorded post-take edit footprint is what the briefing and re-drains consume — pinned in the pyramid's Decide step); dependency edges: the mechanical ones are recomputed by `briefing` (and `decisions summary`) over all records' post-take radii at render time and are **directional by record id** (later depends on earlier) — a DAG by construction, so the "root reviewed first" ordering the Why below relies on is always well-defined and no mechanical cycle can form; the semantic ones are assigned by the decision-taker, which — unlike the per-decision researchers — sees every accumulated record (pinned in the pyramid's Decide step). Below D5's graded thresholds the run **takes** the recommendation — conservatively: on low confidence or a near-tie it takes the smaller-blast-radius option, and it flags `review_first` on any of low confidence, a near-tie, or a large sub-threshold blast radius (pinned in the pyramid's Decide step) — writes the resulting D-block into the spec, and completes the decision's gate-time record via `update-decision` (record lifecycle pinned in D7 and the pyramid's steps 5–6). At `converged` the user receives the briefing: `spec_checks.py briefing` renders the records deterministically, dependency-ordered and blast-radius-ranked, `review_first` items first. Overrides return as free-form prose directives; an apply agent executes them and the run re-drains the overridden decision's recorded post-take radius — scoped horizontal re-check plus dirty-atom re-verification, with one whole-document exit exam as the fixed cost (pinned in the drain's directive-run rule).

**Why:** Internal soundness is machine-assurable; intent soundness is not — only the user can say whether the spec builds the right thing, so human review of the decisions is irreducible. The design's job is to make that review cheap, complete, and reversible. Cheap: reading a handful of decision records once beats 10–20 mid-run stops. Complete: the briefing is a deterministic rendering of structured records — a summarizing LLM could bury decision #7; the renderer cannot. Reversible: the recorded post-take footprint prices every reversal (sections + atom count), and an override re-drains only that slice plus the fixed-cost exam. Dependency ordering mitigates cascades — root decisions are reviewed first, so reversing one invalidates its dependents visibly, not silently. The recommendation is not separately adversarially reviewed by an agent: the user reviews every taken decision in the briefing (nothing is approved unseen), so that review *is* the recommendation's check — and `review_first` fires on an objective, ledger-computed signal (a large sub-threshold blast radius) as well as confidence, so the flag no longer rides on self-graded confidence alone. Prose directives are retained because real resolutions are often editorial ("section 4's approach is wrong, redo it"), which a structured decision→answer map cannot carry.

**Alternatives rejected:** Blocking mid-run on every decision (this concept's own prior design — recreates the serialization the tool exists to remove, and the user decides with *less* context mid-drain than post-drain, when research reflects the finished spec); AskUserQuestion pickers (flattens a discussion into a selection); a free-prose briefing (ordering and completeness must be mechanical); skipping user review entirely (intent soundness is not machine-assurable — see Why).

### D10: All cross-round state lives in files; agents stay context-free

**Choice:** Holistic agents, micro-verifiers, aggregators, judges, fixer, and researchers are spawned fresh every round with no memory. Cross-round knowledge exists only as files (NON-GOALS, IMPLEMENTER-NOTES, CHANGELOG, the atom ledger, the decision records, the working copy itself) plus the workflow script's loop variables (round index, dry flag, result accumulators, and null-call carry bookkeeping — the script's record of its own agent-call outcomes, never judgment). Churn state — per-atom verdict-flip and fix counts, with an atom-backed finding's fix count derived from its lineage atoms' counters rather than stored per-finding (a **macro** finding, standing on no atoms, is the one exception: its `fix_count` is stored by id in the ledger's macro-finding table, pyramid step 7) — is not a loop variable: it lives in the ledger, carried across edits along lineage — or, for a macro finding, keyed by its stable id (pyramid step 1); the per-round verdict log archives a copy to `history/`, but the drain branches only on the ledger's counters relayed via `script_output`, like every other deterministic input. Likewise the null-call carry bookkeeping is a *within-invocation* optimization only: a pending decision's cross-invocation survival rides on its `status: pending` DECISIONS.json record (carrying `finding_atoms`), not on this loop variable, so resumability stays a property of files.

**Why:** Fresh eyes are the founding principle of `spec-improve` — a reviewer that remembers prior rounds starts filtering by memory instead of re-reading. Files-as-state also makes runs resumable and auditable, and matches how the rest of the repo persists pipeline state (JSON contracts, sidecars).

### D11: Run history — every round is recorded, nothing analytical is deleted

**Choice:** A `history/` directory next to the spec accumulates, per run: a working-copy snapshot after every round, a per-round verdict log (atom verdicts, deduped findings, judge votes, tally outcome), and — archived by `approve`/`reject` instead of deleted — the changelog, atom ledger, and decision records. All writes go through `improve_files.py` (`snapshot` subcommand + archival behavior), invoked by the fixer/recorder at round end. The drain never reads `history/`.

**Why:** The design's core bet — the gate actually goes dry, without premature convergence — is unvalidated until trialed; without persisted rounds and verdicts the trial produces no data to judge it with (did findings stop, or did judges drift lenient?). Git cannot cover this: intra-run rounds live on a working copy overwritten in place, and git records *what* changed but none of the judgment metadata (findings, votes, refutation reasons). Direct precedent: auto-doc archives `history/audit-N` per run. Storage is trivial (~30 KB per snapshot). Plain `spec-improve` shares this archival code path but writes none of these sidecars, so `approve`/`reject` there simply no-ops each absent sidecar (D7) — `spec-improve`'s behavior is unchanged, neither gaining a changelog nor erroring on the missing one.

**Alternatives rejected:** Git-only versioning (misses intra-run rounds and all judgment metadata; still recommended for approved states — commit after approve); persisting only the changelog (shows why edits happened but not what was *refused* — verdict data is the gate-tuning substrate); building analysis tooling (history is raw material; hindsight analysis stays ad-hoc).

### D12: Horizontal before vertical — macro settles before decomposition

**Choice:** A run opens with the horizontal phase (whole-document gap/disconnect/contradiction/simpler-design agents, findings gated like all others) and decomposition waits until a horizontal pass comes back clean. Structural edits later in the run trigger a scoped horizontal re-check of the touched slice (detection, scheduling, and cap accounting pinned in the pyramid's Loop step); the exit exam ends with a fresh whole-document read.

**Why:** Fix economics. Macro fixes rewrite paragraphs and move sections — each one invalidates atom verdicts wholesale. Verifying atoms first means paying for verdicts the first structural fix throws away; stabilizing the skeleton first means the pyramid verifies text that will live. Extraction quality also depends on coherent structure. The closing read exists because atoms compose locally: every brick can verify while the building leans.

**Alternatives rejected:** One combined pass (macro and micro findings compete in the same gate while macro fixes churn the atom ledger); horizontal only at the end (the pyramid verifies doomed text all run long).

### D13: Verification pyramid over an atom ledger; dirty-atom incremental re-verification

**Choice:** The spec is decomposed into typed atoms — mechanically where possible, redundant extraction agents for prose whose outputs union-merge under a fixed tie-break: overlapping same-type candidates under one section path collapse to the wider span; overlapping *different*-type candidates reconcile to a single atom typed by section-native precedence (the type native to the atom's section path wins — a bullet under `### What gets built` resolves to scope-item — with a fixed order of claim, then assumption, then example where one region admits several), so no flagged text is dropped and no span is verified twice under two labels. **Prose extractors are scoped to genuinely-prose spans:** they do not re-emit mechanically-extracted regions (D-block frames, code-fenced contracts, citation lines, headings — `atoms extract`'s domain), so the prose and mechanical atom spaces are disjoint by construction — enforced deterministically at merge time, not merely by prompt scope: `atoms merge` drops any prose candidate whose span overlaps a mechanically-extracted span, so an over-reaching extractor cannot double-verify a mechanical region under a prose label — and this cross-type reconciliation is *among prose types only* — a claim sentence inside a D-block's Why is a finer-grained prose atom (checked against its cited code), distinct from, not a duplicate of, the enclosing mechanical D-block atom (checked for Why-discrimination). Each atom is verified by a micro-agent answering one narrow question; per-section aggregators compose verified verdicts into evidence-chained findings. The ledger (`concept-ATOMS.json`, managed by `spec_checks.py atoms` subcommands) records id, type, anchor, text hash, input set, and verdict. Atoms are anchored by section path (deepest enclosing heading — `###` where present, the `##` section in heading-free regions) plus content hash — never line numbers; a post-fix `reanchor` pass makes "edited region" and "overlapping atom" well-defined by content hash rather than path (hash present = verdict kept, anchor rewritten if a section move relocated the atom; hash gone = vanished, then succeeded via lineage or retired from the coverage denominator; unknown text = new region for incremental extraction), and records lineage — a successor atom inherits the replaced atom's lineage id and churn counters (matched to its predecessor by anchor locality, with split and merge pinned in the pyramid's step 1), so identity survives edits. Fixes dirty overlapping atoms; dirtiness propagates along input sets; only dirty or new atoms re-verify.

**Why:** Small tasks are the accuracy floor — a micro-check with one subject and minimal context is close to a lookup, and every layer above it reasons over verified premises instead of raw impressions. The ledger's cross-round atom identity (reanchoring + lineage) keeps finding-ids stable across edits, so below-bar memory (D6) and churn escalation hold over the many rounds these specs take instead of thrashing on extraction jitter — the convergence-stability role D3 pins as its load-bearing purpose. It also makes coverage a deterministic fact (D4) and re-verification incremental (the swarm shrinks as the spec stabilizes — a disclaimed-but-welcome cost side effect, per NON-GOALS, not the justification). Hash-guarded caching coexists with D10's fresh-eyes rule because only facts about *unchanged inputs* are cached — judgment over anything that changed, and every holistic read, is always fresh.

**Alternatives rejected:** Re-verifying everything every round with no persistent ledger (fresh decompose+verify each round) — the tempting simplification, and viable for a spec that converges in 2–4 rounds; rejected because at the 10–20-round counts these specs actually take (Situation), non-deterministic re-extraction jitters the atom set every round, drifting finding-ids so below-bar memory and churn escalation degrade and the loop thrashes toward round-cap — a convergence failure, not merely the loss of a shrinking cost profile; caching by atom text alone (a scope↔verification atom goes stale when the *other* side of the link changes — input sets exist precisely for this); an in-conversation atom table instead of a ledger file (dies with the session; violates D10).

## Scope

### What gets built

- `spec/commands/spec-improve-auto.md` — command orchestrating the outer loop: guarded init, workflow invocations, briefing presentation, blocked-decision discussion, override/directive collection, final approval flow (D1, D2, D9)
- `spec/workflows/spec-improve-auto.js` — the drain-run workflow script: horizontal phase, pyramid layers (incremental decomposition, atom swarm, aggregation), the global decision-dedup pass, gate panel, fixer/recorder, competitive section-rewrite duo (phase H, panel-judged), decision researchers, and decision-taker, exit exam, termination branching; prompts inline; control flow only — all vote math, extraction, ledger, and briefing logic in `spec_checks.py`; built on the Workflow tool's dynamic primitives (outcome-driven looping, conditional stages, dirty-atom-sized fan-out), never a fixed-round schedule (D2, D3, D4, D5, D12, D13)
- `spec/scripts/spec_checks.py` — deterministic core: `structure` (template headings), `tally` (gate vote math — pinned precedence over raw judge votes; plus a head-to-head mode selecting the competitive-rewrite winner by 2-of-3 majority, keeping that vote in Python too — D2), `block-gate` (the D5 block decision — `takeable | blocked` from the union of the two pre-take section sets it is given and the two declared reversal booleans; keeps both the union and the ≥3-unit threshold in Python, not decision-taker judgment), `atoms` (extraction of mechanical atoms, deterministic union-merge of redundant prose extractions, ledger management with lineage, post-fix and continuation-load reanchoring (the latter re-hashing recorded external inputs to catch cross-run staleness), dirty marking with input-set propagation, round-delta persistence — anchors, dirty flags, verdicts, input sets, and incrementally-extracted atoms — via `atoms record-verdicts`, the sole round-close ledger writer, coverage status, blast-radius derivation via `atoms radius`), `floor` (wraps `milestone_checks.py citations` + the structure check into one relay-compatible JSON verdict), `briefing` (deterministic rendering of decision records), `decisions summary` (the thin decision projection the **command** consumes after the drain returns — ids, `kind`, derived `status`, radii, `depends_on`, confidence, `review_first` — grouped by status for the briefing, blocked-discussion, and round-cap presentations); stdlib-only, importable, pytest-covered (D4, D5, D8, D9, D13)
- `improve_files.py` changes — init guard + `--fresh`, read-only `paths`, `append-note`, `note-ids`, `append-changelog`, `append-decision`, `update-decision`, `snapshot`, sidecar paths + `next_run` in init JSON, changelog/ledger/decision-record archival on approve/reject; updated tests (D7, D9, D11)
- `concept-IMPLEMENTER-NOTES.md` sidecar support — written via `append-note` and read back via `note-ids`; its recorded finding-ids are read before the gate for a deterministic id set-difference that drops already-judged findings, never injected into judge prompts (D6)
- `concept-ATOMS.json` atom ledger and `concept-DECISIONS.json` decision records — session sidecars, script-managed, archived to history on approve/reject (D13, D9, D11)
- Decision-record, briefing, and directive contracts — the workflow return JSON (a thin `{status, rounds, fixed, below_bar}` control-flow signal; decision and atom data are command-derived, not carried), the decision-record shape, and the args JSON as the stable interface between runs and the conversation (D9)
- Per-fix changelog sidecar — one entry per applied fix (what/why/which finding), the audit trail replacing per-round human gates (D4, D10)
- `history/` run archive — per-round working-copy snapshots and verdict logs; changelog, ledger, and decision-record archival on approve/reject; written exclusively via `improve_files.py`, never read by the drain (D11)
- `spec/install.sh` registration — COMMANDS entry, workflows/ copy step, `{MG_INSTALL_WORKFLOWS_DIR}` placeholder + sed pair; `spec-help.md` listing (D1, D2)
- `spec/commands/spec-improve.md` resume branch — its Setup step gains guard-failure handling (init exits 1 → `paths` → ask the user: resume with the existing working copy or `init --fresh`) and documents the inherited guard; strictly safer than today's silent reset (D7)

### What does NOT get built

- **Changes to `mg:spec-improve` review behavior** — it remains the manual path; it inherits only the `improve_files.py` hardening plus the minimal Setup resume branch that hardening forces (see What gets built). Its review loop, per-round fix cap, and approval flow are untouched.
- **Template changes** — no scope↔verification link syntax; the concept-spec template contract is untouched.
- **`spec-create-milestone` consumption of IMPLEMENTER-NOTES** — the sidecar is advisory for the human/implementer; projecting it into milestones is a separate concept if ever wanted.
- **Divergence detection for hand-edited originals** — if the user edits `concept.md` during a discussion pause, `approve` still clobbers it; the exposure exists in `spec-improve` today and is unchanged.
- **Token budget mechanism** — cost is accepted at this leverage point (a decision resolved pre-milestone is 5–10x cheaper than at implementation); the round cap is the only brake.
- **Analysis tooling for run history** — `history/` is raw material for ad-hoc hindsight analysis (gate tuning, churn review); no analyzer script or report generator is built.

## Open Items

None — all decisions surfaced during drafting were resolved and promoted to D-blocks.

**Accepted initial calibrations (not blockers — implementation proceeds with these defaults):** the blast-radius block threshold (three anchor units, D5), the per-invocation round cap (10, D4), and the agent-ceiling reserve margin (a conservative static floor, initial value 900, backing a dynamic next-round-width projection against the Workflow tool's 1000-agent ceiling — D4; that ceiling's exceed-behavior is itself undocumented, so the guard errs toward stopping early) are numeric constants carrying no runtime data yet, each deliberately **tunable** from `history/`'s per-run records once the first real runs exist. Distinct in kind is **the design's core convergence bet** — that stable atom identity keeps finding-ids stable so below-bar memory and churn escalation hold and the gate goes dry without drifting lenient (D3, D11): a *bet-the-design hypothesis, not a constant to tune*. Its falsification is the first real run's `history/` record (finding-ids failing to stabilize, or a should-converge spec thrashing to round-cap); its failure response is D3's hybrid fallback — a bounded redesign (the Verification spike-partition), not a numeric adjustment. None of these needs user input before implementation.

## Verification

- **Workflow capability spike (first build step):** a small throwaway workflow validating every capability D2 actually depends on — `scriptPath` invocation, args passing, agent-executed Bash, structured JSON return, an **absolutized-path resolution check** (a sub-agent runs `uv run <absolutized scripts-dir>/…` and the workflow asserts it resolves — confirming the command's path-absolutization (outer loop step 2) holds inside a workflow-spawned agent regardless of that agent's cwd; because the paths are absolutized in the command rather than relying on the drain's cwd, this leg is a sanity check, not a fallback trigger), **a loop that terminates on a runtime-computed condition, a conditional stage, a fan-out whose width (2) is computed from a prior agent's output, relay fidelity** (an agent runs a script emitting known JSON; the workflow asserts the returned `script_output` is byte-identical), **and a scale probe** (a fan-out of ~40 trivial agents — first-sweep width — confirming calls past the documented concurrency cap queue and complete losslessly). No in-repo precedent for the Workflow tool exists; the documented contract covers all of these capabilities (Situation), so the spike falsifies behavior-in-practice — the cheapest possible falsification point for the load-bearing dependency. **If the spike fails on any dynamic capability, the concept falls back to D2's rejected `drain_state.py` variant — an explicit redesign checkpoint, not an implementation-time improvisation.** The pivot is bounded, not a §Solution rewrite: the entire `spec_checks.py` core (structure, tally, atoms/ledger, floor, briefing), `improve_files.py`, and every file sidecar are orchestrator-independent — agents invoke them via Bash under either orchestrator — so only `spec/workflows/spec-improve-auto.js` and the workflow return/args JSON (the *inter-run* interface) are discarded and re-expressed as a `drain_state.py` state machine driven from the command `.md`.
- **Ledger fidelity spike (second build step, before the full `atoms` machinery is built):** real extraction agents over one real spec (this concept is the fixture), one real fix applied, one reanchor pass — asserting span fidelity (reported spans match the actual text), hash stability of untouched atoms across the fix, a fixer's touched-section report matching the real diff, and a **reverse-marshal fidelity** leg — an agent transcribes a known JS-held verdict set into a scratch file, `atoms record-verdicts` reads it back, and the check asserts the persisted entries and the echoed applied-count match what was marshaled in (the JS→script transcription the Relay contract names). This is the early falsification point for the design's second load-bearing bet: the ledger's deterministic accounting trusts three LLM-sourced inputs (extraction spans, touched-section reports, declared input sets — D4 names that trust explicitly), and the fixture pytests exercise none of them against real agent behavior. If fidelity fails here, D3's no-ledger hybrid fallback fires before the ledger machinery is paid for, not after the convergence dry-run.
- **init guard and resume:** given an existing `concept-auto-improve.md`, `improve_files.py init` exits 1 without touching it; `init --fresh` moves all session sidecars (IMPLEMENTER-NOTES, changelog, ledger, decision records) into `history/` and then resets the working copy; `paths` emits the resolved-paths JSON without mutating anything; init JSON contains `source`, `implementer_notes`, `changelog`, `atoms`, `decisions`, and `next_run` keys. `approve`/`reject` **move** the changelog, ledger, and decision records into `history/` — archived copies present, live copies gone, IMPLEMENTER-NOTES untouched. Covered by pytest.
- **Run history:** after a drain run of R rounds, `history/run-N/` contains R working-copy snapshots and R verdict logs (`snapshot` covered by pytest; presence counts asserted in the convergence dry-run); a second invocation allocates `run-(N+1)` — `next_run` re-derived per invocation — and `snapshot` exits 1 rather than overwrite an existing `round-M.md` (pytest). The drain never reads `history/`.
- **Cross-invocation ledger persistence:** after a `round-cap` or `blocked` exit, a second invocation on the unchanged working copy re-verifies **only** the atoms dirtied since the last snapshot — asserted from the verdict logs: run N+1's layer-1 agent count reflects the dirty set, not the full atom inventory — so the persisted ledger carries prior verdicts forward and a multi-run refinement of a deep spec never re-verifies from scratch. This is the mechanism that makes the round cap low-stakes (D4) and multi-invocation refinement affordable.
- **Agent-ceiling backstop:** a non-converging drain that would otherwise approach the Workflow tool's 1000-agent ceiling instead exits `round-cap` gracefully — the JS's cumulative-agent trigger (D4) routes to the same snapshot-and-report exit as the round trigger. The trigger threshold and its routing to the (pytest-covered) round-cap exit are the checked surface; a live over-ceiling fixture is impractical since the ceiling is fixed at 1000.
- **append-note / note-ids / append-changelog / append-decision / update-decision:** given a below-bar finding text, a fix entry, or a decision record, the append subcommand creates/appends the target sidecar; repeated appends preserve prior entries; `append-decision` auto-assigns a unique `R{n}` id (echoed on stdout), so repeated creates never collide across rounds or runs; `update-decision` merges fields into an existing record by id, exits 1 on an unknown id, and moves a replaced `taken` into `superseded`; `note-ids` emits the recorded finding-ids as a JSON list, and an empty list when IMPLEMENTER-NOTES is absent. Covered by pytest.
- **structure check:** given a spec missing a required template heading, `spec_checks.py structure` exits 1 naming the missing section; given the template-conformant fixture, exits 0. Covered by pytest.
- **floor wrapper:** given a spec with a citation violation and a missing template heading, `spec_checks.py floor` emits a single JSON verdict on stdout carrying both violations as structured findings; given a clean fixture, a passing verdict — stdout JSON either way, nothing the workflow must scrape from stderr or exit codes; and given a spec missing `### What gets built` (which both `structure` and `citations` flag), the merged verdict reports that heading once, not once per check. Covered by pytest.
- **Extraction and ledger:** pytest — deterministic extraction of a fixture spec yields the expected atom inventory; the union-merge of two overlapping prose-extraction candidate sets collapses same-type, same-section, overlapping-span near-duplicates into single atoms; a fix at a known location dirties exactly the overlapping atoms plus their input-set dependents, and the successor atom extracted from the edited region inherits the replaced atom's lineage id and churn counters; a deletion fix with no successor retires the vanished atom — coverage reports complete without it, lineage retained; an atom whose recorded external input's hash changed re-verifies on the next run; coverage status reports complete only when every atom's verdict matches current hashes; `atoms record-verdicts` persists a round's verdicts and input sets in one call and overwrites (never duplicates) an atom's prior verdict on re-verification; and a fixer's touched-section report re-dirties an input-set-dependent atom whose *own text is unchanged* (input-set propagation), a bare `### D3` in the report matching that atom's canonical `## Design Decisions / ### D3` input entry (canonical-serialization, Decompose).
- **Briefing rendering:** pytest — given a decision-records fixture, `spec_checks.py briefing` emits every record, dependency-ordered and blast-radius-ranked, `review_first` items first; no record omitted or reordered by content; given a fixture where a later record (higher id) overlaps an earlier record's post-take radius, `briefing` computes the edge directionally — later depends on earlier — and orders the earlier root ahead of its dependent, with no cycle to break (mechanical edges are a DAG by construction, Decide step); given a fixture with a **semantic** back-edge that closes a cycle against that DAG, `briefing` still renders every record — breaking the cycle by the defined tiebreak (descending pre-take radius, then id) and flagging the circular edge inline — and never exits without a briefing, so the every-approval-gets-a-briefing invariant holds even on cyclic records.
- **Gate panel trial (subagent, during build):** given a synthetic finding list with a known substantive/cosmetic split, the 3-judge panel's votes — run through `spec_checks.py tally` — reproduce the expected partition.
- **Atomic check trial (subagent, during build):** given a sample of atoms with known-good and known-broken referents (a true and a falsified claim, a matching and a mismatching example, an answerable and an unanswerable contract question), the micro-checks return the expected verdicts with evidence, the genuinely-unanswerable question yielding an **unverifiable** verdict rather than a guess. A companion pytest asserts `atoms coverage` counts an unverifiable atom as covered, so a spec containing one still reaches `converged` instead of livelocking to round-cap — and that its output is the full shape `{verified, unverifiable, total, complete, never_verified}`: the drain branches on the script-computed `complete` verdict (D2, never a JS re-derivation), the round-cap report reads `never_verified`, and the counts (`verified`, `unverifiable`, `total` — the coverage denominator) let the command re-render `verified + unverifiable == total` as a display/audit check of coverage-complete, which holds for a converged run holding an unverifiable atom.
- **Implementability-probe trial (subagent, during build):** given a scope bullet known to be underdetermined (several defensible builds), the two independent probe agents diverge and the comparator emits an underdetermination finding; given a fully-specified bullet, they converge and no finding is emitted. A companion assertion covers the scope↔verification atom check D8 keeps LLM-judged: a scope bullet with a matching Verification item passes, one with none is flagged.
- **Failure-policy backstops:** pytest — `spec_checks.py tally` rejects a vote set of fewer than three votes, so a short panel (a judge seat still dead after its one retry) can never be tallied silently; `spec_checks.py atoms coverage` reports **incomplete** when an atom has no verdict at all (a micro-verifier dead after its retry), distinct from an unverifiable *verdict* which counts as covered — so a dead atom deterministically blocks `converged` instead of silently satisfying coverage; and a fixer/recorder re-spawned over a partial changelog reconciles against it and does not re-apply an already-logged fix. These are the deterministic backstops of the failure policy, which the design assumes will fire across a 40–80-agent swarm.
- **Exit exam trial (subagent, during build):** given a fixture spec with a planted flaw constructed to evade atomization — a cross-section incoherence whose halves each verify true in isolation — the exam's fresh whole-document read flags it and the finding re-enters phase P. This is the detection-power check for the recall guard: coverage-completeness is vacuous for what extraction never atomized (D4), and the exam is the one component that owns that failure mode.
- **Competitive rewrite trial (subagent, during build):** given a macro finding whose remedy replaces a whole anchor unit, the drain spawns exactly two independent rewrites, the panel's recorded head-to-head vote selects a winner, and exactly one rewrite lands in the working copy — the changelog names it, the loser survives only in the verdict log.
- **Convergence dry-run:** given a fixture spec with planted issues (macro: one contradiction and one gap; micro: false claims and mismatched examples; plus below-threshold and threshold-exceeding decision-shaped issues), one run fixes the macro issues in phase H before decomposition, fixes the micro issues with one changelog entry each, auto-takes the below-threshold decision (D-block written, record appended, `review_first` per the confidence/near-tie/radius rule), and exits `blocked` on the threshold-exceeding one; a follow-up run with directives exits `converged` with a briefing carrying all records — the formerly-blocked decision now rendering `taken` with `taken_by: user` and `decisions summary` showing no status-`blocked` record (resolution written via `update-decision`, asserted from DECISIONS.json); an override re-run re-drains only the overridden decision's recorded post-take radius (asserted from the ledger's dirty set) plus the whole-document exit exam; and the command's post-return presentation reproduces `spec_checks.py decisions summary` over DECISIONS.json exactly (derived command-side, never paraphrased), while the workflow return carries only `{status, rounds, fixed, below_bar}`.
- **Gate memory:** given an IMPLEMENTER-NOTES file containing a previously judged below-bar finding, a subsequent round's gate does not re-confirm the same finding as substantive and does not append a duplicate note.
- **Decision dedup:** given a DECISIONS.json already holding a recorded decision (or a pending non-goal proposal) and a candidate finding that re-emits it, the dedup pass drops the re-emission and notes the record id in the verdict log (suppress-with-reference) — the record is not mutated, the gate never re-judges it, and no duplicate record is appended; and given a proposal marked `dropped`, the dedup pass does **not** fold its re-emission, so the underlying finding re-enters the gate — a user-declined proposal is fair game within the same session, not only after archival; exercised in the convergence dry-run (a decision taken in an early round produces no second record when its D-block re-verifies).
- **Churn escalation:** given a fixture spec with a planted contradiction that survives fixing (any fix satisfying one side re-triggers the other), the run escalates it to the decision machinery after the second failed fix instead of reaching the round cap.
- **Swarm shrinkage:** across the convergence dry-run's rounds, layer-1 agent count tracks the dirty-atom count (asserted from the verdict logs) — later rounds are strictly cheaper than the first sweep.
- **Block-gate determinism:** pytest feeds `spec_checks.py block-gate` synthetic inputs across the threshold boundary — **pairs** of section sets (evidence footprint + edit-estimate) whose **union** spans one, two, and three distinct anchor units, including overlapping pairs whose union is smaller than their raw sum (so the union, not the total, drives the count), each crossed with both reversal booleans — and asserts the exact `takeable | blocked` partition (blocked iff either boolean is set or the unioned unit count ≥ 3). The decision-taker branches only on this verdict, so the auto-take-vs-block boundary cannot drift across rounds.
- **Tally determinism:** pytest feeds `spec_checks.py tally` synthetic vote sets covering every precedence branch (needs-user overriding refutation, needs-user overriding exclusion, exclusion vs auto-fix, below-bar) and asserts the exact partition; a companion set covers the **head-to-head mode** (the competitive-rewrite 2-of-3 majority — phase H), asserting winner selection across the three-vote outcomes. The JS branches only on tally output in both modes, so control-flow correctness reduces to these fixtures plus the convergence dry-run.
- **`atoms radius` and `decisions summary` determinism:** pytest — `spec_checks.py atoms radius` returns the exact anchor-unit set and count for a fixture atom set (the evidence footprint that `block-gate`, briefing ranking, and override re-drains all consume); and `spec_checks.py decisions summary` derives the exact `status` (`proposal`/`taken`/`blocked`/`pending`) across records covering every kind/`taken`/`untakeable`/`dropped` combination (the derivation rule in Command flow). Both are load-bearing deterministic functions the command and decision-taker branch on, so — like `tally` and `block-gate` — each gets unit-level determinism fixtures, not only end-to-end coverage in the convergence dry-run.
- **Install:** `install.sh --target <tmp>` places the command with all placeholders substituted (including `{MG_INSTALL_WORKFLOWS_DIR}`) and the workflow script under `.claude/spec/workflows/`, and adds the `spec-improve-auto` entry to the installed `spec-help` listing (verifying the Scope registration row); `--project` substitutes project-root-relative paths, which the command absolutizes against its own cwd before passing into the drain (outer loop step 2), so they resolve inside the drain regardless of the spawned agent's cwd (the convergence dry-run, run from the project root, exercises this end-to-end).
- **spec-improve-auto Setup resume branch:** given a leftover `concept-auto-improve.md`, the command runs `paths`, surfaces the leftover state, and offers resume-or-`--fresh` (AskUserQuestion) — resume re-invokes the drain on the existing working copy, `--fresh` discards and restarts; distinct from the `improve_files.py` init-guard unit test (which covers the script) and the `spec-improve` resume test (which covers the manual command) — checked in review.
- **Round-cap command presentation:** on a `round-cap` return the command presents the honest non-convergence report (what churned, the never-verified atoms from `atoms coverage`, the still-`pending` decisions from `decisions summary`) accompanied by the briefing, and offers the re-run / partial-approve / partial-reject choice — the convergence dry-run exercises the `converged` and `blocked` command paths, so this is the third — checked in review.
- **spec-improve resume branch:** `spec-improve.md`'s Setup step handles a guard failure by running `paths` and asking resume-or-`--fresh`; no other flow change (review loop, cap, approval untouched) — checked in review.
- **Acceptance:** a full run on the next real concept spec converges without a manual abort — across as many `blocked` stops as the spec's genuinely-independent architecture decisions require, each a bounded discussion rather than a restart (D5; each resume is a fresh invocation with its own round cap, D4); the briefing's decisions are genuine decisions, none feel like noise, and no major decision is discovered missing from it (user judgment).
