# spec-improve-auto: Workflow-Driven Autonomous Spec Refinement

## Situation

The spec family pipeline runs `mg:spec-draft` → `mg:spec-improve` → `mg:spec-create-milestone`. The middle step, `spec-improve` (`spec/commands/spec-improve.md`), refines a concept spec through rounds of fresh-eyes subagent review:

- One reviewer subagent per round, carrying 10 review dimensions in a single prompt (contradictions, missing pieces, assumptions, engineering calibration, examples↔text, decision quality, simpler alternatives, over-specification, verification coverage, citation discipline).
- Triage caps fixes at **5 per round**; remaining issues "surface in subsequent rounds."
- Every round ends in a hard stop: report → wait for user approval → user re-invokes for the next round.
- All modifications happen on a working copy (`concept-auto-improve.md`, managed by `spec/scripts/improve_files.py`); the original is untouched until explicit `approve`. A `concept-NON-GOALS.md` sidecar accumulates approved scope exclusions that suppress future reviewer flags.

In practice a spec takes **~7 rounds** to refine, each requiring manual re-invocation, and the session ends when the user judges the remaining findings too minor to continue — not when the tool decides it is done.

Relevant existing infrastructure:

- The Claude Code **Workflow tool**: deterministic JavaScript orchestration of subagents (`agent()`, `pipeline()`, `parallel()`, loops). No tool in this repo uses it yet.
- `spec/scripts/milestone_checks.py citations <spec-path>`: the only deterministic check that runs standalone against a working copy (D-block citation discipline; never a vacuous pass).
- In-repo precedents for the mechanics this concept needs: codebase-health's adversarial verify step ("the scanner is fallible; don't rubber-stamp"; "prefer false negatives" for fixes), auto-doc auditv2's convergence assessment (trend-based stop recommendation, "default to CONTINUE if unsure") and dismissed-entity memory (persistent lists preventing re-flagging).
- `improve_files.py init` **unconditionally overwrites** an existing working copy from the source (create-once backup, always-reset working copy).

## Problem

1. **Artificial serialization.** The 5-fix cap forces a spec with 15 mechanical findings into 3+ rounds even when nothing depends on anything. Each round costs a full human gate (report, approval, re-invocation) even when every fix is cosmetic-safe.

2. **No self-termination.** The reviewer is a relative grader: "be harsh, flag everything" plus a critical/major/minor scale with no external anchor means severity normalizes to whatever remains in the current spec. On a near-final spec, the worst remaining nit is that round's "major." The loop structurally never returns empty, so a human must judge "relatively major vs. actually done" and abort manually — the observed ~7-round pattern.

3. **Decisions surface as a drip, under-prepared.** Genuine decisions (intent/scope/architecture) arrive mixed into each round's batch and get discussed one round at a time, without dedicated research. Empirically these decision points are highly relevant and need real back-and-forth — but the current shape spreads that discussion across re-invocations instead of concentrating it.

4. **A pause-and-resume hazard.** Any flow that pauses for discussion and later re-runs `init` silently destroys unapproved fixes in the working copy (`improve_files.py` always resets it from the source). Today this is latent; an autonomous tool that brackets discussions with multiple runs makes it acute.

## Solution

### Overview

A new command `mg:spec-improve-auto` drives the refinement loop through the Workflow tool. One invocation executes a **drain run** in three phases. **Horizontal first:** whole-document agents find gaps, disconnects, contradictions, and simpler-whole-design alternatives, and those are fixed before anything else — macro fixes invalidate micro work, so the skeleton stabilizes first (D12). **Then the verification pyramid:** the spec is decomposed into typed atoms (claims, citations, contracts, scope items, examples); a swarm of micro-agents verifies each atom — small, narrow tasks with near-lookup accuracy — per-section aggregators compose the verified verdicts into evidence-chained findings, and the judge gate plus deterministic tally dispose of them; fixes mark atoms dirty, and only dirty atoms re-verify, so the swarm shrinks as the spec stabilizes (D13). **Finally an exit exam:** coverage-complete ledger, a dry gate, and a fresh whole-document read. Decision-shaped findings do not stop the run: they are researched and **auto-taken** (the recommendation — conservatively on near-ties), written into the spec as D-blocks, and logged as decision records; only a decision that contradicts explicit user intent or exceeds a blast-radius threshold blocks (D5, D9). The deliverable is a fully refined spec plus a **decision briefing** — a deterministic, dependency-ordered rendering of the decision records with computed blast radii. The user reviews decisions, not rounds: an override re-drains only that decision's blast radius; acceptance approves the spec. <!-- v2 (user-directed): architecture revised — horizontal-first + verification pyramid replace the lens fan-out; decisions auto-taken and reviewed post-hoc via briefing instead of blocking mid-run -->

The division of labor: micro-agents do small verifiable things (one atom, one narrow question), holistic agents do what only whole-document reading can (macro coherence), aggregation composes conclusions from verified premises instead of raw impressions, the workflow script does what determinism is good for (looping, branching on tallied outcomes, terminating), and the user does the one thing agents cannot: judge intent. Internal soundness — consistency, true premises, coverage — is machine-assured; intent soundness — is this the thing the user actually wants built? — is only user-assurable, and the briefing is that check, not a courtesy summary. The existing safety net survives intact: all edits land on the working copy, the original changes only on explicit approve, and fixes and non-goals are approved independently.

### Command flow (outer loop)

The command .md orchestrates; the workflow script executes one drain run per invocation.

1. **Setup.** Parse target path; run `improve_files.py init <target>`. If a working copy already exists, `init` fails loudly (D7); the command then runs the read-only `improve_files.py paths <target>` to obtain the resolved-paths JSON, surfaces the leftover state, and asks the user: **resume** (continue with the existing working copy) or **discard and restart** (`init --fresh`). <!-- round-1 fix (M1): guard failure alone left no way to continue — defined the resume path -->

2. **Drain run.** Invoke `Workflow({scriptPath: <installed workflow>, args})`. Args carry the resolved file paths, the run number (`next_run` from `init`/`paths` — the script threads run and round numbers into the fixer/recorder's prompts), and, on later runs, the directives from the previous briefing review or blocked discussion.
3. **On return** the workflow reports one of three statuses:
   - `converged` — present the **decision briefing** (rendered deterministically from the decision records: dependency-ordered, blast-radius-ranked, `review_first` items on top) plus the changelog summary and scorecard. Accepting it approves fixes and proposed non-goals independently via `improve_files.py`, as in `spec-improve` today; overriding any decision turns the override into free-form directives for a scoped re-run — the overridden decision's blast radius is re-drained, not the whole spec.
   - `blocked` — the run hit one or more decisions it may not take (D5's graded gate: reversing an explicit user directive or a NON-GOALS entry, or blast radius over the threshold). Present the blocked cards, discuss them in prose in the conversation (dependency-ordered), collect resolutions as free-form directives, and invoke the workflow again. Expected to be rare — most decisions auto-take. <!-- v2 (user-directed): blocked is now the graded exception, not the normal decision path --> <!-- round-4 fix (M7): plural — all untakeable decisions from the exiting round travel together -->
   - `round-cap` — the drain did not converge within the cap. Present an honest non-convergence report (what kept churning); this is itself a signal the spec has a structural problem. The user then chooses: discuss pending decisions and re-run with directives, or approve/reject the partial work via `improve_files.py` (the working copy, changelog, ledger, and history are intact and auditable either way). <!-- round-3 fix (M3): round-cap was a terminal status with no defined next action --> **Invariant:** the briefing — rendered from the decision records accumulated so far — accompanies *every* approval opportunity, whatever the exit status. Auto-taken decisions are never approved unseen. <!-- round-4 fix (C2): approving at round-cap would have written machine-taken decisions into the original with zero review — briefing was pinned to converged only -->
4. Repeat until a run exits `converged` and the user accepts the briefing.

Workflow return contract (interface):

```json
{
  "status": "converged | blocked | round-cap",
  "rounds": 4,
  "fixed": 23,
  "below_bar": 6,
  "atoms": {"total": 74, "verified": 74, "dirty_at_exit": 0},
  "decisions": [
    {
      "id": "R1",
      "title": "…",
      "finding": "what surfaced the decision",
      "research": "codebase context gathered for it",
      "options": [{"option": "…", "tradeoff": "…"}],
      "taken": "which option was taken, and why",
      "confidence": "high | low",
      "review_first": false,
      "blast_radius": {"sections": ["## Solution/### …", "### D3"], "atoms": 14},
      "depends_on": []
    }
  ],
  "blocked_cards": ["non-empty only when status = blocked: ALL untakeable decisions from the exiting round — same shape, no `taken`"],
  "proposed_non_goals": ["…"]
}
```

Args contract for run N+1: the same paths object plus `"directives": ["free-form decision override or editorial instruction", …]`.

### Drain run (inner loop)

A run executes three phases; rounds live inside phase P. The workflow script itself has no shell or filesystem access; agents execute all script commands. **Relay contract, pinned:** any agent that runs a script returns the script's raw JSON stdout verbatim in a dedicated `script_output` field of its structured return; the workflow script branches only on parsed `script_output`, never on an agent's paraphrase — otherwise every "deterministic" branch point is silently mediated by LLM transcription. <!-- round-4 fix (M2): the JS's inputs all pass through agent hands; relay fidelity was assumed, never contracted --> <!-- v2 (user-directed): drain internals replaced — horizontal phase, verification pyramid with atom ledger, auto-taken decisions, exit exam; the lens fan-out, round-level short-circuit, and group-churn tracking of the prior design are subsumed -->

**Phase H — Horizontal (macro first, D12).** Two to three whole-document agents — context-free, reading the working copy, the concept template, the NON-GOALS and IMPLEMENTER-NOTES sidecars, and any code the spec references — hunt only macro classes: gaps (undefined flows, missing connective tissue), disconnects (sections that do not compose), contradictions, and the simpler-whole-design alternative. Their findings go through the same gate and tally as everything else; decision-shaped ones route to phase P's decision machinery. Structural rewrites may be competitive: N independent rewrites of the broken section, judged, the winner applied. Fixing and recording reuse phase P's mechanics (steps 5–6): the same fixer/recorder, changelog, snapshots, and decision machinery — the ledger is simply still empty. Phase H loops until a pass produces no substantive macro finding; its passes count against the run's round cap.

**Phase P — Pyramid (micro, D13).** Each round:

1. **Decompose (layer 0).** Mechanical atoms (headings, D-blocks, citations, code-fenced contracts) are extracted deterministically via `spec_checks.py atoms extract`; prose atoms (claims, assumptions, scope items, examples) by two redundant extraction agents whose outputs are union-merged deterministically by `spec_checks.py atoms merge`: candidates of the same type under the same section path with overlapping text spans collapse into one atom (the wider span wins, so no flagged text is dropped); only disjoint candidates survive as distinct. Near-duplicates with different span boundaries never double-verify or duplicate findings. <!-- round-5 fix (M4): the "union" was undefined and collided with hash identity — two agents' near-duplicate spans hash differently --> The **atom ledger** (session sidecar, script-managed) records each atom's id, type, anchor, text hash, input set (the spec sections and external files its check reads), and verdict state. **Anchoring, pinned:** atoms are anchored by `###`-level section path plus content hash — never line numbers, which go stale on the first edit. After each fixer pass, `spec_checks.py atoms reanchor` re-walks the document: an atom whose hash still appears under its section path keeps its verdict; an atom whose hash is gone is dirty by definition (its text changed or vanished); text matching no known hash is an edited region routed to incremental extraction. "Only edited regions produce new atoms" is thereby computed, not judged. **Lineage, pinned:** a fixed atom's hash changes, so incremental extraction records succession — a new atom of the same type extracted from the edited region that replaced a vanished atom's text inherits that atom's lineage id and churn counters. Identity survives fixes; without this, "verdict flip" and "fixed twice" would be undefined the moment the first fix landed. <!-- round-5 fix (M1): a fixed atom was a new atom by definition — lineage now carries identity and churn counters across edits --> <!-- round-4 fix (C1): the location/identity model — the ledger's load-bearing mechanism — was entirely unspecified; an implementer would have invented it in the first hour -->
2. **Verify (layer 1).** One micro-agent per unverified or dirty atom, each answering one narrow question with minimal context and returning a structured verdict, evidence, and the exact inputs it consulted — the spec sections and external files actually read. The ledger records these as the atom's input set (produced by the act of verification, not guessed at extraction), external files stored as path plus content hash, so a later run re-dirties atoms whose cited code changed in the meantime. <!-- round-5 fix (M3): input sets had no assigned producer, and external-file inputs were untracked across runs --> The checks: claims are checked against the code they cite; citations against whether the D-block actually motivates the item; examples against the adjacent contract text; scope items against the Verification section; D-blocks against whether the Why discriminates between choice and alternatives; contracts against 3–5 enumerated edge and lifecycle questions answerable from the spec alone. Scope items additionally get an **implementability probe**: two independent agents each answer "what would you build for this one bullet, and which decisions would you have to make yourself" — a comparator diffs the answers, and divergence is an underdetermination finding. The deterministic floor (`milestone_checks.py citations`, `spec_checks.py structure`) is the mechanical slice of this layer, run by a floor agent concurrently with the swarm; floor failures are definitionally substantive and join classification like any finding.
3. **Aggregate (layer 2).** Per-section aggregators receive only their slice's structured verdicts — never the raw dump — and compose evidence-chained candidate findings (patterns across atoms: a false claim plus the D-block resting on it; unanswered contract questions clustering in one section). Every finding carries the atom ids it stands on. A dedup pass folds instances of already-recorded decisions into their records instead of re-emitting them.
4. **Gate (layer 3).** Unchanged from the prior design: a panel of three perspective-diverse judges (*builds-wrong-thing*, *implementer-blocked*, *scope-intent-drift*) votes on the deduped findings — substantive yes/no, needs-user yes/no, optionally intentional-exclusion — and `spec_checks.py tally` computes outcomes under the pinned precedence: **needs-user** (any single vote — 1-of-3, permissive, D5 — overriding the substantive tally and any exclusion votes; a decision can never be refuted into IMPLEMENTER-NOTES or excluded into a non-goal), then **proposed non-goal** (≥2 exclusion votes), then **auto-fixable** (≥2 substantive votes), else **below-bar** → IMPLEMENTER-NOTES. Judges now rule on findings that arrive with verified evidence chains, so their task shrinks to "given these premises, is this substantive or decision-shaped?"
5. **Fix and record.** The single fixer/recorder agent runs `tally` on the raw votes (vote math is never LLM-computed), appends below-bar findings via `improve_files.py append-note` (D6), applies auto-fixable findings, appends one changelog entry per fix via `append-changelog`, and snapshots the round — working copy plus verdict log (atom verdicts, findings, votes, tally outcome) — via `snapshot` (D11). The fixer reports each fix as the set of `###`-level section paths it touched; `spec_checks.py atoms mark-dirty` combines those with the reanchor pass (step 1) and input-set propagation, so an atom whose *check inputs* changed re-verifies even if its own text did not. <!-- round-4 fix (C1): pinned how a fix's location is expressed and consumed -->
6. **Decide.** Needs-user outcomes route to one researcher per decision (codebase context, options, tradeoffs, recommendation, blast radius). **Blast radius is measured in `###`-level units** — Solution subsections, individual D-blocks, Scope subsections (the granularity of the return-contract example): in phase P it is derived from the ledger (atom anchors map to section paths; the atom count rides along for precision), in phase H (empty ledger) the researcher names the units. A decision-taker then applies D5's graded gate: a decision that would reverse an explicit user directive or a NON-GOALS entry, or whose blast radius spans **three or more units**, is untakeable — the round finishes its bookkeeping (records, snapshot), then the run exits `blocked` carrying every untakeable decision from that round; building further on undecided ground of that size is the cascade risk. Every other decision is **taken**: the recommendation by default; on low confidence or a near-tie, the smaller-blast-radius option with `review_first` set. Taking a decision writes or amends the corresponding D-block in the spec (an ordinary fix: changelog entry, atoms dirtied) and appends the decision record via `improve_files.py append-decision`. `depends_on` is assigned by the decision-taker — the one party that sees the round's full batch plus the accumulated DECISIONS.json (per-decision researchers are blind to sibling decisions): mechanically, B depends on A when B's blast radius contains a unit that taking A wrote or amended; semantic edges may be added on top. `spec_checks.py briefing` rejects cyclic records loudly rather than rendering an arbitrary order. <!-- round-5 fix (M5): depends_on — the briefing's ordering substrate — had no defined producer --> <!-- round-4 fixes (M1, M7): blast-radius unit pinned at ### granularity (top-level sections made the threshold meaningless — every real decision spans 1–3 of ~7 ## sections); blocked now batches the round's untakeable decisions and exits after bookkeeping -->
7. **Loop.** Rounds continue while dirty or unverified atoms remain or the gate yields substantive findings. **Churn escalation:** an atom whose verdict flips across re-verifications (tracked along lineage, step 1), or a finding fixed twice and re-found, escalates to the decision machinery (step 6) instead of a third fix attempt — fixes that don't stick are evidence the disagreement is decision-shaped, not mechanical. Finding identity is deterministic: at aggregation each finding receives an id computed from its type plus the lineage ids of the atoms it stands on, recorded in the verdict log — "re-found" is id equality, never the workflow's recollection. <!-- round-5 fix (M1): churn counters had nothing well-defined to count once a fix changed the atoms and findings were recomposed fresh each round -->

**Phase E — Exit exam.** Entry requires: ledger coverage-complete (every atom verified against current text — a deterministic check), one dry gate round, floor green. Then a fresh whole-document read by agents that saw nothing earlier — atoms compose locally, and every brick can verify while the building leans. Exam findings re-enter phase P; a clean exam ends the run.

Termination, pinned: clean exam = `converged`; any untakeable decision = `blocked` at the end of the round that produced it (step 6 — so a pending blocked decision can never coexist with the exam); round cap (8, phases H and P combined — headroom above the healthy profile of 1–2 horizontal passes plus 2–4 pyramid rounds) reached first = `round-cap`. <!-- round-4 fix (M7): "immediate" contradicted step 6's end-of-round exit, and the converged condition carried a dead "no pending blocked decision" clause -->

On a directive-carrying run, an **apply agent** executes the directives against the working copy first (changelog entries logged; touched atoms dirtied — an overridden decision re-drains exactly its blast radius), then the phases proceed as above — resolutions create new review surface and must be re-reviewed like anything else.

Cost shape: discovered at runtime, not scheduled. The first sweep is wide — one micro-agent per atom, roughly 40–80 for a ~250-line spec — but each task is tiny; later rounds shrink with the dirty-atom count, and a near-clean round is a handful of agents. Dozens of small agents, never hundreds of heavyweight ones, and never a whole-milestone implementation simulation (a spec can span 30–50 implementation plans; the per-scope-item probe yields the same divergence signal at tractable size).

### The two gates

The gates answer different questions and deliberately carry opposite default polarities (D5):

- **Termination gate (skeptical, default-refute).** Bar: *name the concrete failure at implementation time if this is not fixed* — the implementer builds the wrong thing, gets stuck, or must come back and ask. No nameable failure → below bar. This replaces the relative critical/major/minor scale with an absolute, falsifiable test that does not drift as the spec improves — which is what makes the loop self-terminating. The bar's third clause ("must come back and ask") is the hand-off guarantee, and it holds by construction, not by judge discipline: the tally escalates on any single needs-user vote before the substantive tally is consulted, so a decision-shaped finding can never be refuted into IMPLEMENTER-NOTES (precedence order pinned in the pyramid gate step). <!-- round-1 fix (M3): made the sequential-gate hand-off explicit --> <!-- round-3 fix (C1): the guarantee was an assumption about judge behavior — two refuting votes could bury a one-vote decision below the ≥2 substantive bar before classification ever ran; the tally's precedence order now makes it mechanical -->
- **Escalation gate (permissive, default-surface).** Bar: *does resolving this change intent, scope, or architecture?* If plausibly yes, it becomes a decision — researched, then auto-taken and recorded for the briefing, or blocked if it trips D5's graded thresholds. Failure costs are asymmetric: a wrongly suppressed decision becomes an implementer's guess (the 5–10x cost this pipeline exists to prevent); a wrongly surfaced one costs briefing-review minutes. Auto-taking relocates the user's judgment from mid-run to the briefing without weakening it: every taken decision is recorded with its alternatives and blast radius, and overriding one is a bounded re-drain, not a restart. <!-- v2 (user-directed): escalation now defaults to auto-take + briefing; blocking is the graded exception -->

### Artifacts and state

All cross-round and cross-run state lives in files (D10); every agent is spawned context-free.

```
docs/work-queue/todo/{name}/
├── concept.md                        ← original; only touched by approve
├── concept.original.md               ← create-once backup (existing)
├── concept-auto-improve.md           ← working copy (existing)
├── concept-NON-GOALS.md              ← approved scope exclusions (existing)
├── concept-IMPLEMENTER-NOTES.md      ← below-bar findings, gate memory (new)
├── concept-CHANGELOG.md              ← per-fix audit trail (new)
├── concept-ATOMS.json                ← atom ledger: inventory, hashes, input sets, verdicts (new)
├── concept-DECISIONS.json            ← decision records; the briefing renders from this (new)
└── history/                          ← per-run archive: round snapshots, verdict logs, changelogs, ledgers (new)
    └── run-N/                        ← round-M.md snapshots, round-M-verdicts.json, CHANGELOG.md, ATOMS.json, DECISIONS.json
```

- **IMPLEMENTER-NOTES** mirrors the NON-GOALS format (header + flat bullets). It is fed to the gate each round as prior-judgment memory (below-bar findings are not re-judged) and remains after approval as advisory input for the implementer. It is *not* consumed by `spec-create-milestone`.
- **CHANGELOG** is a single live file per session — entries tagged with (run, round) by the fixer — created during the run, its path emitted by `init`, **archived into the latest `history/run-N/` by `approve`/`reject`** rather than deleted (D11). It is what makes the autonomous drain auditable — the user reviews *what changed and why* at the end instead of gating every round.
- **ATOMS.json** is the pyramid's working state (D13): managed exclusively via `spec_checks.py atoms` subcommands, never hand-edited, never fed to holistic agents. Verdict caching is hash-guarded — an atom re-verifies whenever its text or any part of its input set changes. Cached facts about unchanged inputs, never cached judgment over changed ones: that is how the ledger coexists with D10's fresh-eyes rule. <!-- v2 (user-directed): atom ledger added -->
- **DECISIONS.json** accumulates decision records (D9); `spec_checks.py briefing` renders it into the user-facing briefing deterministically — dependency-ordered, blast-radius-ranked, `review_first` first — so a major decision cannot be buried by a summarizer. Both JSON sidecars are archived into the latest `history/run-N/` by `approve`/`reject`, like the changelog. <!-- v2 (user-directed): decision records added -->
- **history/** accumulates per run: per-round working-copy snapshots, per-round verdict logs, and the archived changelog, ledger, and decision records. Written exclusively via `improve_files.py`; **never read by the drain** — it is analysis material, not agent memory, so D10's fresh-eyes rule is untouched (D11).
- `improve_files.py init` output JSON gains `implementer_notes`, `changelog`, `atoms`, `decisions`, and corresponding `*_exists` keys.

## Design Decisions

### D1: Separate command; `spec-improve` stays untouched

**Choice:** Build `mg:spec-improve-auto` as a new command. `mg:spec-improve` keeps its current behavior as the manual path.

**Why:** The 5-cap and per-round human gate exist on purpose for the manual path — cheap, controllable, appropriate for small specs. The autonomous variant has a different cost/control profile; forcing both into one command means mode flags and conditional behavior in an LLM-interpreted .md.

**Alternatives rejected:** Replacing `spec-improve` (removes the cheap manual option); one command that escalates to the workflow when finding volume warrants (adds a volume-estimation step and conditional orchestration for little gain — the user knows which mode they want).

### D2: Workflow tool for orchestration; JS carries control flow and prompts only

**Choice:** The drain loop is a Workflow-tool script (plain JavaScript — the only language the tool executes). The JS carries *only* control flow and prompts: agent prompt templates, fan-out structure, branching on script-computed statuses, and trivial loop variables (round index, dry flag, churn counters). Every deterministic judgment computation — vote tallying, classification precedence, the checks floor — lives in Python under `spec/scripts/` (pytest-covered), invoked by the workflow's agents via Bash. <!-- round-3 fixes (M2, m1): the old wording listed "vote counting" as JS content while claiming zero business logic — self-refuting; vote math now lives in spec_checks.py tally, JS keeps only branching and counters -->

**Why:** The self-driving property depends on the loop being code, not LLM-followed instructions — round discipline, vote thresholds, and termination must not drift over many autonomous rounds. Only the Workflow tool provides deterministic multi-agent control flow; Python scripts cannot spawn agents. And that control flow is the point, not a scheduler: the drain is adaptive, never a naive fixed-N re-iteration. Rounds continue only while dirty atoms or substantive findings remain (loop-until-dry), fan-out is sized by each round's actual content (one micro-agent per dirty atom, one researcher per decision), stages run conditionally (the apply agent only on directive-carrying runs; aggregation and gate only when there are verdicts to compose), and stuck work changes route (flipping atoms and twice-fixed findings escalate to the decision machinery instead of a third attempt). <!-- v2 (user-directed): adaptive-behavior list restated in pyramid terms --> The implementation must lean on these dynamic primitives — outcome-driven loops, conditional stages, content-sized fan-out — wherever the drain's shape depends on what a round found. <!-- round-3 fix (M4, user-confirmed): pinned the discriminating argument — the Workflow tool is chosen for adaptive orchestration, not as an automatic re-iterator -->

**Alternatives rejected:** Agent-tool orchestration from the command .md (the codebase-health pattern) — zero JS and full repo precedent, but the loop itself becomes LLM-interpreted instructions, reintroducing exactly the drift this concept eliminates. The stronger variant — .md orchestration plus a `drain_state.py` state machine that ingests each round's verdicts and prints the binding next action (LOOP / CONVERGED / BLOCKED / ROUND-CAP), the `milestone_checks.py` "the script decides" pattern — removes decision drift but not execution drift: spawning dozens of agents per round, in order, with correct context threading, for up to 8 rounds remains LLM-followed procedure; every round's outputs pile into the main conversation exactly where discipline must survive longest; and the adaptive behaviors above flatten into a static re-run schedule. With the vote math already in Python (D4, D5), dynamic multi-agent control flow is precisely the residual value the Workflow tool buys. Keeping the JS thin preserves this repo's markdown/Python separation rule with one added clause: JS = control flow + prompts. <!-- round-3 fix (M4, user-confirmed): D2 previously never engaged the Python-state-machine variant — this repo's own established pattern — and its rejection of .md orchestration didn't justify the added artifact class -->

### D3: Finding production = horizontal pass + verification pyramid

**Choice:** Macro issues (gaps, disconnects, contradictions, simpler whole design) are found by a small set of whole-document agents in a horizontal phase that runs and settles first (D12). Everything decomposable is found by the pyramid (D13): typed atoms verified by micro-agents, composed upward by per-section aggregators into evidence-chained findings. There is no lens-reviewer fan-out.

**Why:** LLM accuracy scales inversely with task scope — "is this one claim true against this one file?" is near-lookup; "is this 250-line spec sound?" is an impression. Building findings from verified premises means a false premise must survive a nearly mechanical check before it can mislead a judge; false positives carry a traceable evidence chain (the failing atom is named); and coverage stops being "no reviewer found more" and becomes ledger accounting. The irreducibly holistic checks stay with whole-document agents — contradictions across distant sections and the simpler-alternative question (historically the single highest-value finding) do not decompose.

**Alternatives rejected:** Four lens reviewers over the whole document (this concept's own prior design — big open-ended tasks whose impressions the judges then re-litigate impression-against-impression; coverage unmeasurable; findings without evidence chains); one agent per review dimension (same problems with more agents); whole-milestone implementation simulation as the implementability check (a spec can span 30–50 implementation plans — the per-scope-item probe yields the same divergence signal at tractable size); the no-ledger hybrid — Workflow orchestration plus evidence-required whole-document reviewers feeding the same judge panel, tally, auto-take, and briefing machinery. This is the nearest simpler design: it solves all four stated Problems and drops the lineage, input-set, and merge machinery entirely. Rejected with eyes open: what it cannot provide is precisely what the autonomous loop stands on — coverage reverts from ledger accounting to "no reviewer found more" (dissolving D4's deterministic termination clause back into judgment), every round re-reads the whole document (rounds never get cheaper, losing the cost profile a multi-round drain needs), and verification reverts from near-lookup one-atom checks to whole-document impressions with an evidence requirement bolted on. The ledger machinery is the price of computed termination, shrinking rounds, and computable blast radii (D4, D9, D13) — and the hybrid remains the named fallback if the pyramid's bookkeeping proves heavier than its value in the first real run. <!-- round-5 fix (M6, user-confirmed): the nearest simpler design was never engaged; rationale confirmed by user — micro-task accuracy floor + deterministic coverage + shrinking cost justify the ledger --> <!-- v2 (user-directed): D3 rewritten — pyramid replaces lens fan-out -->

### D4: Termination = coverage-complete ledger + dry gate + exit exam

**Choice:** Finding and judging stay separated; the three-judge panel and `spec_checks.py tally` are unchanged. Convergence is three-part: the atom ledger is coverage-complete (every atom verified against current text — deterministic), the gate yields one dry round, and a fresh whole-document exit exam finds nothing substantive. The exam replaces the prior rule's second consecutive dry round with a stronger, different-modality guard. Round cap: 8 across phases H and P (headroom above the healthy profile of 1–2 horizontal passes plus 2–4 pyramid rounds), then an honest non-convergence report. <!-- v2 (user-directed): convergence redefined around the atom ledger; exit exam replaces the second dry round -->

**Why:** Reviewers are relative graders — "reviewer finds nothing" never fires, which is why termination must be computed. The ledger makes the largest share of it *checkable* rather than judged: dirtiness is mechanical over the recorded edges (hash + input set — the edges themselves are declared by the verifiers as the inputs they actually read, the one LLM-sourced input the accounting trusts), so "nothing left to verify" is an accounting fact given honest input reporting. <!-- round-5 fix (M3): "fully mechanical" overstated — the dependency edges are LLM-declared; the arithmetic over them is what's deterministic --> What remains judged — the dry gate round and the exam — is guarded against premature convergence by modality diversity (auto-doc's "default to CONTINUE if unsure" precedent): a second identical dry round re-asks the same question of the same kind of agents, while a fresh whole-document read asks a different one. The final human briefing means a wrongly-dropped finding costs a later round, not a bad merge.

**Alternatives rejected:** Loop-until-reviewer-silence (structurally never terminates); two identical consecutive dry rounds (this concept's own prior rule — redundancy without diversity); per-finding refuter trios (the panel already diversifies perspective, and evidence chains shrink what is left to refute); trend-based stop like auto-doc's assess-convergence alone (advisory trends still need a human to call it; the falsifiable bar decides per-finding).

### D5: Two gates with opposite default polarities; escalation is graded

**Choice:** The termination gate is skeptical (default-refute; bar: name the concrete implementation-time failure). The escalation gate is permissive (default-surface; bar: plausibly changes intent, scope, or architecture) — and surfacing has two grades: **auto-take** (the default — research, take the recommendation, record for the briefing) and **block** (the exception — the decision would reverse an explicit user directive or a NON-GOALS entry, or its blast radius spans three or more `###`-level units: Solution subsections, individual D-blocks, Scope subsections). The threshold's logic: one unit is a local change, two is a mechanism plus its D-block, three means the decision has crossed into neighboring design territory — architecture-scale, where a wrong autonomous guess cascades. <!-- v2 (user-directed): escalation graded into auto-take vs block --> <!-- round-4 fix (M1): unit pinned at ### granularity with rationale — "top-level sections" made the threshold either always or never trip, depending on counting -->

**Why:** They answer different questions with asymmetric failure costs. Suppressing a real decision silently converts it into an implementer's guess — the 5–10x downstream cost. Surfacing a borderline one now costs briefing-review minutes, cheaper still than a mid-run stop — the permissive polarity is preserved while the human gate moves to where it is cheapest. The block grade exists because auto-taking an intent-reversing or spec-wide decision would relocate the 5–10x guess rather than eliminate it: everything downstream of a wrongly-taken root decision is cascade rework. The tally rules encode the polarities: an auto-fix requires ≥2-of-3 substantive votes (skeptical), while a single judge's needs-user vote escalates — taking precedence over both the substantive tally and any exclusion votes, so a decision can never be out-voted into silence (permissive; full precedence order pinned in the pyramid gate step). <!-- round-2/3 fixes retained: needs-user mechanically precedes refutation and exclusion -->

**Alternatives rejected:** One gate for both (forces a single bar that is either too strict for escalation or too loose for termination); blocking on every decision (this concept's own prior design — a dozen mid-run stops for decisions the briefing handles post-hoc at lower cost); auto-taking everything (an intent-reversing decision must never be guessed).

### D6: Below-bar findings persist in an IMPLEMENTER-NOTES sidecar

**Choice:** Gate-refuted findings are appended once to `concept-IMPLEMENTER-NOTES.md` (NON-GOALS-style format) and fed back to the gate as prior-judgment memory. The file survives approval as advisory input for the implementer.

**Why:** Without memory, the same minor finding resurfaces every round and burns gate budget (the auto-doc dismissed-entities problem, solved the same way: persistent judged-once lists). A sidecar keeps the frozen spec clean and mirrors the established NON-GOALS convention.

**Alternatives rejected:** Open Items section (leaks into v2-requirements projection — `spec-create-milestone` routes deferred Open Items there); NON-GOALS (wrong semantics — those suppress reviewer flags for *intentional exclusions*, not below-bar observations); an in-spec `## Implementer Notes` section (breaks template symmetry, visible to future reviewers as an unexpected section); report-only (lost after the session).

### D7: `improve_files.py` hardening — init guard (breaking) and sidecar lifecycle

**Choice:** `init` refuses to overwrite an existing working copy (exit 1, loud message); a new `--fresh` flag forces the old reset behavior. A read-only `paths` subcommand emits the same resolved-paths JSON as `init` without touching any file — the resume entry point after a guard failure or session crash. New subcommands: `append-note` (IMPLEMENTER-NOTES, mirroring `append-non-goal`), `append-changelog` (per-fix entries — the fixer never writes sidecars by hand), and `snapshot` (`snapshot <target> --run N --round M --verdicts <file>`: copies the working copy to `history/run-N/round-M.md` and stores the verdict log, D11). `init` and `paths` emit the notes and changelog paths plus `next_run` (derived by scanning `history/`). **Sidecar lifecycle, pinned:** `approve`/`reject` delete the working copy and **move** — not copy — the changelog, atom ledger, and decision records into the latest `history/run-N/` (D11); IMPLEMENTER-NOTES stays, per D6, as advisory input for the implementer. `init --fresh` archives harder: it moves those three *plus* IMPLEMENTER-NOTES into `history/` before resetting the working copy from source — the session is being discarded, and a stale DECISIONS.json would render ghost decisions into the next briefing while a stale ATOMS.json would seed reanchor with hashes from a discarded document. NON-GOALS alone always survives: user-approved scoping, not session state. <!-- round-5 fix (M2): --fresh reset only the working copy; live JSON sidecars from an abandoned session would poison the next one — exactly the Problem-4 hazard class --> <!-- round-2 fixes (M2, M6): append-changelog added; run-number allocation and snapshot contract pinned -->

**Why:** The always-reset behavior silently destroys unapproved fixes in every pause-and-resume flow — acute for a tool that brackets discussions with multiple runs. Failing loudly surfaces leftover state; plain `spec-improve` gets safer for free. All file operations stay in the script per repo convention. Breaking change, per this repo's stated preference over compatibility shims.

**Alternatives rejected:** Orchestrator discipline alone ("only call init once") — protects nothing across session crashes and resumes.

### D8: Deterministic floor = existing `citations` check + a new structure check; verification coverage stays LLM-judged

**Choice:** Per-round deterministic checks are `milestone_checks.py citations` (exists, standalone-capable) and a new `spec_checks.py structure <spec-path>` (asserts required template headings present, file non-empty). Scope↔verification coverage (#9) remains an LLM-judged check — a layer-1 atom check in the pyramid (D13).

**Why:** Deterministic checks cannot be sweet-talked and cost nothing — use them wherever no judgment is needed. But making #9 deterministic requires a citation-like link syntax between Scope bullets and Verification items — a template change rippling through spec-draft, spec-improve, and create-milestone. Wrong blast radius for this concept.

**Alternatives rejected:** Verification link syntax in the template (cross-command contract change; deliberately excluded); no floor at all (wastes gate budget on mechanically checkable failures).

### D9: Decisions are auto-taken and reviewed post-hoc via a deterministic briefing

**Choice:** Each needs-user finding becomes a researched decision: finding, codebase research, options with tradeoffs, recommendation, blast radius computed from the ledger; dependency edges are assigned afterward by the decision-taker, which — unlike the per-decision researchers — sees every accumulated record (pinned in the pyramid's Decide step). <!-- round-5 fix (M5) --> Below D5's graded thresholds the run **takes** the recommendation — conservatively: on low confidence or a near-tie it takes the smaller-blast-radius option and flags `review_first` — writes the resulting D-block into the spec, and appends a decision record. At `converged` the user receives the briefing: `spec_checks.py briefing` renders the records deterministically, dependency-ordered and blast-radius-ranked, `review_first` items first. Overrides return as free-form prose directives; an apply agent executes them and the run re-drains exactly the overridden decision's blast radius. <!-- v2 (user-directed): D9 rewritten from mid-run cards to auto-take + briefing -->

**Why:** Internal soundness is machine-assurable; intent soundness is not — only the user can say whether the spec builds the right thing, so human review of the decisions is irreducible. The design's job is to make that review cheap, complete, and reversible. Cheap: reading a handful of decision records once beats 10–20 mid-run stops. Complete: the briefing is a deterministic rendering of structured records — a summarizing LLM could bury decision #7; the renderer cannot. Reversible: the ledger prices every reversal (sections + atom count), and an override re-drains only that slice. Dependency ordering mitigates cascades — root decisions are reviewed first, so reversing one invalidates its dependents visibly, not silently. Prose directives are retained because real resolutions are often editorial ("section 4's approach is wrong, redo it"), which a structured decision→answer map cannot carry.

**Alternatives rejected:** Blocking mid-run on every decision (this concept's own prior design — recreates the serialization the tool exists to remove, and the user decides with *less* context mid-drain than post-drain, when research reflects the finished spec); AskUserQuestion pickers (flattens a discussion into a selection); a free-prose briefing (ordering and completeness must be mechanical); skipping user review entirely (intent soundness is not machine-assurable — see Why).

### D10: All cross-round state lives in files; agents stay context-free

**Choice:** Holistic agents, micro-verifiers, aggregators, judges, fixer, and researchers are spawned fresh every round with no memory. Cross-round knowledge exists only as files (NON-GOALS, IMPLEMENTER-NOTES, CHANGELOG, the atom ledger, the decision records, the working copy itself) plus the workflow script's loop variables (round index, dry flag, per-atom flip and per-finding fix counts for churn escalation). <!-- v2 (user-directed): state inventory updated for the pyramid -->

**Why:** Fresh eyes are the founding principle of `spec-improve` — a reviewer that remembers prior rounds starts filtering by memory instead of re-reading. Files-as-state also makes runs resumable and auditable, and matches how the rest of the repo persists pipeline state (JSON contracts, sidecars).

### D11: Run history — every round is recorded, nothing analytical is deleted

**Choice:** A `history/` directory next to the spec accumulates, per run: a working-copy snapshot after every round, a per-round verdict log (atom verdicts, deduped findings, judge votes, tally outcome), and — archived by `approve`/`reject` instead of deleted — the changelog, atom ledger, and decision records. All writes go through `improve_files.py` (`snapshot` subcommand + archival behavior), invoked by the fixer/recorder at round end. The drain never reads `history/`.

**Why:** The design's core bet — the gate actually goes dry, without premature convergence — is unvalidated until trialed; without persisted rounds and verdicts the trial produces no data to judge it with (did findings stop, or did judges drift lenient?). Git cannot cover this: intra-run rounds live on a working copy overwritten in place, and git records *what* changed but none of the judgment metadata (findings, votes, refutation reasons). Direct precedent: auto-doc archives `history/audit-N` per run. Storage is trivial (~30 KB per snapshot). Plain `spec-improve` inherits changelog archival for free through the shared script.

**Alternatives rejected:** Git-only versioning (misses intra-run rounds and all judgment metadata; still recommended for approved states — commit after approve); persisting only the changelog (shows why edits happened but not what was *refused* — verdict data is the gate-tuning substrate); building analysis tooling (history is raw material; hindsight analysis stays ad-hoc).

### D12: Horizontal before vertical — macro settles before decomposition

**Choice:** A run opens with the horizontal phase (whole-document gap/disconnect/contradiction/simpler-design agents, findings gated like all others) and decomposition waits until a horizontal pass comes back clean. Structural edits later in the run trigger a scoped horizontal re-check of the touched slice; the exit exam ends with a fresh whole-document read.

**Why:** Fix economics. Macro fixes rewrite paragraphs and move sections — each one invalidates atom verdicts wholesale. Verifying atoms first means paying for verdicts the first structural fix throws away; stabilizing the skeleton first means the pyramid verifies text that will live. Extraction quality also depends on coherent structure. The closing read exists because atoms compose locally: every brick can verify while the building leans.

**Alternatives rejected:** One combined pass (macro and micro findings compete in the same gate while macro fixes churn the atom ledger); horizontal only at the end (the pyramid verifies doomed text all run long). <!-- v2 (user-directed): new D-block — horizontal-first ordering -->

### D13: Verification pyramid over an atom ledger; dirty-atom incremental re-verification

**Choice:** The spec is decomposed into typed atoms — mechanically where possible, redundant extraction agents for prose. Each atom is verified by a micro-agent answering one narrow question; per-section aggregators compose verified verdicts into evidence-chained findings. The ledger (`concept-ATOMS.json`, managed by `spec_checks.py atoms` subcommands) records id, type, anchor, text hash, input set, and verdict. Atoms are anchored by `###`-level section path plus content hash — never line numbers; a post-fix `reanchor` pass makes "edited region" and "overlapping atom" well-defined (hash gone under its path = dirty; unknown text = new region for incremental extraction), and records lineage — a successor atom inherits the replaced atom's lineage id and churn counters, so identity survives edits (round-5 fix M1). Fixes dirty overlapping atoms; dirtiness propagates along input sets; only dirty or new atoms re-verify. <!-- round-4 fix (C1): anchoring model pinned in the D-block -->

**Why:** Small tasks are the accuracy floor — a micro-check with one subject and minimal context is close to a lookup, and every layer above it reasons over verified premises instead of raw impressions. The ledger makes re-verification incremental (the swarm shrinks as the spec stabilizes — the cost profile an autonomous multi-round design needs), makes coverage a deterministic fact (D4), and makes blast radii computable (D9). Hash-guarded caching coexists with D10's fresh-eyes rule because only facts about *unchanged inputs* are cached — judgment over anything that changed, and every holistic read, is always fresh.

**Alternatives rejected:** Re-verifying everything every round (rounds never get cheaper; the swarm becomes a fixed cost instead of a shrinking one); caching by atom text alone (a scope↔verification atom goes stale when the *other* side of the link changes — input sets exist precisely for this); an in-conversation atom table instead of a ledger file (dies with the session; violates D10). <!-- v2 (user-directed): new D-block — the pyramid and its ledger -->
