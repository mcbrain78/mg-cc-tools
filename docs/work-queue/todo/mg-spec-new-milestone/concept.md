# mg:spec-create-milestone — Project a Frozen Spec into a GSD Milestone

## Situation

GSD offers structured work at two granularities; three entry points already exist:

- **Milestone-level — `gsd:new-milestone`** (`.claude/get-shit-done/workflows/new-milestone.md`): top-down. Loads project context → optional 4-agent domain research (`gsd-project-researcher` × Stack/Features/Architecture/Pitfalls + synthesizer → `research/SUMMARY.md`) → per-category requirements elicitation → `gsd-roadmapper` derives phases. It is greenfield-shaped: it *discovers* what to build.
- **Phase-level — `mg:spec-create-context <phase> <doc>`** (`.claude/commands/mg/spec-create-context.md`): projects a source doc into a phase's `CONTEXT.md` as locked decisions, producing a file GSD already understands (no GSD patches). The phase must already exist in `ROADMAP.md`.
- **Phase-level, batch — `mg:spec-gsd-phases <doc>`** (`.claude/commands/mg/spec-gsd-phases.md`): analyzes a concept doc and appends goal-only phases (`Requirements: TBD`) to the **current open milestone** via `gsd:add-phase`. It opens no milestone, writes no `REQUIREMENTS.md`, keeps no traceability, and runs no research — requirements are derived later, per phase, by `mg:plan-phase`. It is the family's mid-milestone phase-insertion path, not a milestone creator.

Separately, work here is often pre-specced: `mg:spec-draft` → `mg:spec-improve` produce a frozen, code-grounded concept at `docs/work-queue/todo/<slug>/concept.md` (with `D1..Dn` decisions + a sibling `concept-NON-GOALS.md`). Both v4.0 and v5.0 were seeded this way.

Reusable machinery is confirmed present:
- **`gsd-roadmapper`** (`.claude/agents/gsd-roadmapper.md`) reads `REQUIREMENTS.md` + `PROJECT.md` (+ `config.json` for granularity), treats `research/SUMMARY.md` as **optional**, enforces **100% requirement→phase coverage** (one phase per REQ), writes `ROADMAP.md` + `STATE.md`, and rewrites the REQUIREMENTS.md `## Traceability` table. It is spawned standalone today by both `new-project` and `new-milestone` — reusable unchanged (but the spawner must inject the starting phase number; see Stage 4).
- **`gsd:plan-phase --prd` (step 3.5 of the underlying GSD workflow — `mg:plan-phase` forwards `--prd` to it verbatim)** is a working precedent: an external frozen doc → locked decisions (everything in the doc) → the rest of the pipeline runs normally, with uncovered areas flagged as "Claude's Discretion."

## Problem

When a milestone's job is to *implement an already-frozen, code-grounded spec* — a "fix observed issues" milestone, not a greenfield exploration — `gsd:new-milestone`'s top-down front-end is mismatched. Observed empirically on the **v5.0 run (2026-06-30)**: with the L2 concept in hand, `new-milestone` still ran full domain research and derived its own 22 requirements. The output came out faithful (it cited D-numbers, covered D1–D10, respected the NON-GOALS) — but only a hand audit established that, and three distinct failure modes showed up:

1. **Redundant discovery.** It re-ran domain research to *discover what to build* when the spec (post multiple `spec-improve` rounds + code citations) had already settled it — wasted effort/tokens, and it reframes settled decisions as open questions.
2. **Re-elicitation invites silent drift.** The per-category "scope each category" gate re-opens frozen decisions, so the requirements are the tool's *re-derivation*, not a faithful *projection*. Drift is silent: scope was **added** (a FINRA "SHORT" track absent from the concept leaked into the requirements), and a component count slipped ("48" vs ~50 mapped columns) — both caught only by manual audit.
3. **No faithfulness check.** Nothing verifies the requirements are a *complete + non-drifting* projection of the spec (every `Dx` → ≥1 REQ; every REQ → a `Dx` or an explicitly-flagged addition). On v5.0 this required a manual audit before the requirements could be trusted.

The correction is **not** "remove research." Context-aware research *earned its keep once*: it surfaced a real gap the concept omitted — the consumption view needs a `GRANT`, because `CREATE VIEW` doesn't inherit the renamed table's grants. The mismatch is specifically **blind discovery + elicitation**, not **verification**.

## Solution

### Overview

A new command **`mg:spec-create-milestone <version> <spec-path>`** — the milestone-level, spec-first sibling of `mg:spec-create-context` (`spec→phase :: spec→milestone`). It **projects** a frozen concept spec into GSD-native milestone artifacts (`PROJECT.md` milestone section, `REQUIREMENTS.md`, then `ROADMAP.md` via the unchanged roadmapper) instead of eliciting them. It **keeps** a research pass but **re-aims it from discovery to verification** (spec-seeded: "do these decisions still hold against the code, and what did the spec miss?"), and it adds a **faithfulness gate** — the manual v5.0 audit, made a built-in step. **Strict projection is the default**; anything beyond the spec must arrive as a research-surfaced, explicitly operator-approved addition. Output is GSD-native — no GSD patches.

Family routing: use `mg:spec-gsd-phases` to add spec-derived phases to an *already-open* milestone; use this command when the spec *is* the milestone — it opens the milestone (Stage 0), projects gated requirements with traceability, and derives a coverage-enforced roadmap (see D4 for why the existing path can't be composed into this). The two paths converge downstream: after either, `mg:spec-prepare-context` → `mg:spec-create-context` seed each phase's `CONTEXT.md` from the same spec, which is why this command ends with an explicit handoff (Stage 6) instead of duplicating that step (NG7).

### Interface

`mg:spec-create-milestone <version> <spec-path>` — e.g. `mg:spec-create-milestone v6.0 docs/work-queue/todo/point-in-time-l2/concept.md`.

**Both arguments are required (arity check, ahead of every other check).** With either missing — or with extra positional arguments — the command fails fast with `ERROR: <version> and <spec-path> are both required.`, prints a `Usage:` / `Example:` block (mirroring `spec-improve`'s missing-arg `ERROR` and `spec-create-context` step 2), and exits with `.planning/` untouched. Arity necessarily precedes `preflight` (which consumes `<version>`) and the spec-content checks (which consume `<spec-path>`): neither can run before its argument is known to be present.

- `<version>` — the milestone version, dot-format `vX.Y` (`v6.0`, `v6.1` — the same format `new-milestone` step 3 suggests; minor milestones are legal).
- `<spec-path>` — the frozen concept spec. Two distinct discovery mechanisms:
  - **Sibling NON-GOALS file** — the command globs `*-NON-GOALS.md` in the spec's directory. An exact convention match (`<spec-basename>-NON-GOALS.md`) is read automatically; every other hit is presented to the operator individually to confirm or skip — with multiple hits, each gets its own confirm, and all confirmed files feed Out of Scope (a renamed spec or working copy silently breaks the basename convention otherwise); zero hits → proceed, but the Stage-3 gate states "no NON-GOALS file found" explicitly, so a missing Out-of-Scope source is a visible fact the operator approves — never a silent drop. **This is net-new** — `spec-create-context` step 7 follows explicit markdown links only and does *not* auto-discover convention-named siblings, so the command adds a dedicated glob step rather than relying on the spec linking to it.
  - **Local markdown links inside the spec** are followed and read up to a **≤5** budget (this is the `spec-create-context` step-7 behavior). The NON-GOALS sibling is read separately and does not count against the 5. Linked docs are **context, never scope**: they inform milestone naming, REQ phrasing, and gate presentation, but requirements, waivers, and Source entries derive solely from the spec's `D1..Dn`, its cited `### What gets built` bullets, and gate-approved `SV-n` findings — nothing read via a link can introduce any of them (the one-source-namespace property would otherwise leak here).
- **Preconditions — each fail-fast validated at startup** (mirroring `spec-create-context` steps 2–4's explicit `ERROR: ...` + exit per violation). The GSD-side state classification — from `.planning/PROJECT.md` presence through the version/live-marker state machine of the last two bullets — is **script-classified, not eyeballed**: `milestone_checks.py preflight <version>` computes one named verdict per state (see Scope), and the command only maps verdicts to the ERROR/confirm texts specified below — a multi-way file-state machine re-derived in-context on every run is exactly the unreliability the repo's scripts convention exists to remove. Spec-content checks stay outside `preflight`: existence/non-emptiness and D-block presence are trivial reads, and the citation contract has its own subcommand (`citations`). The states:
  - The spec file exists and is non-empty (maturity — post `spec-improve` — is asserted by the operator, not detectable).
  - The spec is decision-structured: it contains `D1..Dn` blocks (the spec-family output this command exists to process — D7). Absent → ERROR pointing at `mg:spec-draft` → `mg:spec-improve`; genuinely unstructured docs already have the `plan-phase --prd` path at phase level.
  - The spec honors the citation contract (D8): every top-level bullet under `### What gets built` cites ≥1 existing `Dx` — validated by `milestone_checks.py citations` against the pinned bullet/citation grammar (see D8 — one definition shared by the template, `mg:spec-draft`, and the parser). A bullet with no citation, or citing a nonexistent `Dx`, → ERROR naming the bullet and pointing at a `mg:spec-improve` round to add citations (the migration path for specs frozen before the contract existed). A missing `### What gets built` section, or one with zero top-level bullets, is itself an ERROR — `citations` must never pass vacuously (the hazard D7 names for the rejected `Sn` fallback applies equally to this check).
  - The project is GSD-initialized: `.planning/PROJECT.md` exists (else ERROR pointing at `gsd:new-project` — `PROJECT.md` is the marker `gsd:new-project` creates and every milestone-lifecycle step here assumes, starting with Stage 0's rewrite of its Current Milestone section). **`MILESTONES.md` is deliberately NOT required:** GSD creates it only at `gsd:complete-milestone` time, so a project that has never *completed* a milestone legitimately lacks it — including the entirely plausible "first milestone is spec-driven" flow. Absence simply means zero completed milestones, and every consumer of the file already has that branch: the version-collision check passes vacuously, Stage-1 REQ-IDs start at 01 (the no-archives branch), and `phase-start` finds no archived roadmaps so Stage 4 injects `Start phase numbering from 1`.
  - GSD is installed (`.claude/get-shit-done/` present) — the command shells out to `gsd-tools.cjs` (Stage 0), a dependency its sibling `spec-create-context` deliberately avoids but a full milestone lifecycle requires.
  - `<version>` is well-formed `vX.Y` and **not already recorded in `MILESTONES.md`** (vacuously satisfied when the file doesn't exist) — re-running a completed milestone would corrupt bookkeeping. `<version>` matching `PROJECT.md`'s *current* milestone is allowed **only as a pre-roadmap resume** (e.g. after a Stage-3 Reject, or a crash before Stage 4), and Stage 0 idempotently rewrites the same section. **Live-phase detection is a conjunction — BOTH conditions required: a `### Phase N:` *heading* (not a bullet), AND that N ≥ the `phase-start` number (see Stage 4). If `.planning/ROADMAP.md` holds any such heading, the current milestone is already roadmapped.** An implementer must test both; heading-presence alone is wrong (the rationale below explains why each half is load-bearing). Bare `ROADMAP.md` existence is *not* the signal: `gsd:complete-milestone` leaves a reorganized, constant-size `ROADMAP.md` behind (prior-milestone one-line summaries — this repo's post-v1.1 state; its archiving code only *copies* the file, and though its workflow prose also carries a contradictory `rm .planning/ROADMAP.md` step, both outcomes — residue file or no file — must read as clean), and completed-phase residue appears as `- [x] Phase N:` bullets, never `### Phase N:` headings (verified against this repo's post-v1.1 residue: 0 `### Phase N:` headings vs 24 `- [x] Phase N:` bullets inside `<details>`; both prescribed reorganize formats reserve `### Phase N:` headings for *active* phases). Two independent guards therefore make residue read as clean — the detector keys on `### Phase N:` **headings**, which residue never emits, *and* it requires those headings to be numbered ≥ `phase-start`, whereas any residue phase (heading or bullet, inside `<details>` or not) carries a number below `phase-start` by construction. The heading-vs-bullet distinction is the load-bearing one: were a future GSD reorganize format to emit `### Phase N:` headings for completed phases, the `≥ phase-start` comparison is what would still hold the line — which is why the detector tests the number, not mere heading presence. A live-phase roadmap means mid-execution, or opened by `gsd:new-milestone` rather than an earlier run of this command — and re-running would let Stage 4 overwrite live phase state with colliding phase numbers (the injected start number derives from the *archived* roadmaps, not the live one) → ERROR. One reachable state needs its own remedy in that ERROR: this command's own Stage 4 writes `ROADMAP.md` *before* the roadmap is approved (the roadmapper writes files, then returns), so a crash between roadmapper return and the Stage-5 commit leaves a live, not-yet-committed roadmap with `<version>` == the current milestone. The ERROR therefore names three paths: `mg:spec-gsd-phases` (add phases to a genuinely open milestone), `gsd:complete-milestone` (close it first), or — when the operator knows the roadmap is the unapproved leftover of a crashed run — delete `.planning/ROADMAP.md` by hand and re-run as a pre-roadmap resume (nothing durable is lost: the roadmapper's write already replaced the post-completion residue, and milestone history persists in `MILESTONES.md` + `.planning/milestones/`). The command never deletes it itself: it cannot reliably distinguish an unapproved leftover from a mid-execution roadmap (commit state is no signal when `commit_docs` is off), so that judgment stays with the operator.
  - **No other milestone is open:** if `.planning/REQUIREMENTS.md` exists, or `.planning/ROADMAP.md` holds live phase sections (previous bullet's definition), while `<version>` is not `PROJECT.md`'s current milestone, a previous milestone is still in progress → ERROR pointing at `gsd:complete-milestone`. The open-milestone marker is `REQUIREMENTS.md`, **not** `ROADMAP.md` existence: completion reliably deletes the former (workflow instruction + this repo's post-v1.1 state confirm it) but leaves the latter as reorganized residue — keying on bare `ROADMAP.md` existence would ERROR on the command's *primary entry state*, a freshly completed project. This check must run **before Stage 0 mutates anything**: the dirty-state decision cannot sit after the bookkeeping commit, or an abort partway through would leave the project half-switched (`PROJECT.md`/`STATE.md` on the new milestone, `ROADMAP.md` still holding the old one's open phases). One state slips past file-based detection: a `gsd:new-milestone` run that stopped right after its bookkeeping steps leaves `PROJECT.md`'s Current Milestone naming a different version with *neither* live marker present. The complication: after `gsd:complete-milestone`'s PROJECT.md evolution review, the `## Current Milestone` section may be **absent entirely or renamed** (this repo's reads `## Current State (post-v1.1)`) — a clean state that must not trip the confirm on every run. So, with no live markers: a Current-Milestone section that is absent, or names a version already recorded in `MILESTONES.md` (completed-milestone residue), → clean, proceed silently (Stage 0 creates or rewrites the section); one naming a version that is neither `<version>` nor `MILESTONES.md`-recorded → abandoned bookkeeping, stop and ask (`AskUserQuestion`: Continue — overwrite the abandoned bookkeeping / Abort) instead of letting Stage 0 overwrite it silently — the same visible-fact standard the NON-GOALS discovery applies. On **Continue**, Stage 0 rewrites the Current-Milestone section to name `<version>`, projected fresh from the spec — the abandoned version's name, goal, and target features are discarded, not merged; **Abort** exits pre-mutation.

**`preflight` verdicts — ordered decision table** (first matching row wins; the prose above defines the edge wording, this table pins the precedence the script encodes). "current" = the version named by `PROJECT.md`'s current-milestone section; "live-phase `ROADMAP.md`" = `### Phase N:` headings numbered ≥ `phase-start`; "no live markers" = neither `REQUIREMENTS.md` present nor a live-phase `ROADMAP.md`.

| # | Condition (first match wins) | Verdict | Outcome |
|---|------------------------------|---------|---------|
| 1 | `.planning/PROJECT.md` missing | `missing-project` | ERROR → `gsd:new-project` |
| 2 | `.claude/get-shit-done/` missing | `missing-gsd` | ERROR (install GSD) |
| 3 | `<version>` not well-formed `vX.Y` | `bad-version` | ERROR |
| 4 | `<version>` recorded in `MILESTONES.md` | `version-completed` | ERROR (completed milestone) |
| 5 | live-phase `ROADMAP.md` **and** `<version>` = current | `live-phase-current` | ERROR (names 3 recovery paths) |
| 6 | (`REQUIREMENTS.md` present **or** live-phase `ROADMAP.md`) **and** `<version>` ≠ current | `open-other-milestone` | ERROR → `gsd:complete-milestone` |
| 7 | `<version>` = current **and** no live-phase `ROADMAP.md` | `resume-pre-roadmap` | proceed (Stage 0 idempotent; Stage-1 guard may offer Resume when `REQUIREMENTS.md` is snapshot-identical) |
| 8 | no live markers **and** current-milestone names a version ∉ {`<version>`, `MILESTONES.md`-recorded} | `abandoned-bookkeeping` | CONFIRM (overwrite / abort) |
| 9 | no live markers **and** current-milestone absent/renamed, or names a `MILESTONES.md`-recorded version | `clean` | proceed silently |

**Malformed GSD-side state never falls through to `clean` (silent-overwrite guard).** Row 9's `clean` — the only verdict that proceeds with no prompt — is reserved for a Current-Milestone section that is genuinely *absent*, or whose version parses cleanly *and* is `MILESTONES.md`-recorded. A section that is *present* but whose version token is not well-formed `vX.Y` (or is otherwise unrecognizable) routes to row 8 `abandoned-bookkeeping` — a visible confirm — never row 9; and a `PROJECT.md` or `MILESTONES.md` that exists but cannot be parsed for the versions rows 4/8/9 test is a loud `ERROR` (the same fail-loud contract `citations`, the findings-file parser, and `coverage` carry), never a silent misclassification into `clean`. `preflight` prints the token it could not parse. Without this, a version-garbled `PROJECT.md` would fall through to `clean` and Stage 0 would silently overwrite it — the exact silent overwrite rows 8–9 exist to prevent.

**Startup ordering (fixed; all pre-mutation).** Nothing in `.planning/` is written until Stage 0, and the startup checks run in an order that clears every fail-fast `ERROR` before any interactive prompt — so the operator is never asked to confirm an overwrite and then hit an `ERROR` two checks later: (1) `preflight <version>` classifies the GSD-side state — an `ERROR` verdict (table rows 1–7) exits here; (2) the spec-content `ERROR` checks — existence/non-emptiness, `D1..Dn` presence, `citations` (these are spec `ERROR`s, independent of `preflight`); (3) the template-drift check (see **Template-drift guard**) — the first interactive prompt, Continue-anyway/Abort, matching that section's "after the fail-fast preconditions … before Stage 0"; (4) the one `preflight` **confirm** verdict, `abandoned-bookkeeping` (row 8), presented now that all fatal `ERROR`s are cleared. An `ERROR` or Abort at any of steps 1–4 leaves `.planning/` byte-untouched. Stage 0 then begins; its own `MILESTONE-CONTEXT.md` disposition (Delete/Keep — non-aborting) sits *inside* Stage 0, after the `PROJECT.md`/`STATE.md` writes and before their commit, so it is not part of this pre-mutation sequence.

### Stage 0 — Milestone bookkeeping (`PROJECT.md` + `STATE.md`), before anything reads them

Mirror `new-milestone` steps 4–6 **before** the pipeline runs. The ordering is load-bearing: Stage 4 passes `PROJECT.md` to the roadmapper, so it must describe *this* milestone, not the previous one — in `new-milestone` too, these steps precede the roadmapper.

- **Resolve config + models first:** run `node .claude/get-shit-done/bin/gsd-tools.cjs init new-milestone` and extract `researcher_model`, `roadmapper_model`, `commit_docs` (the same extraction `new-milestone` step 7 does; `synthesizer_model` and `research_enabled` are unused — there is no synthesizer, and the Stage-2 verification pass always runs, deliberately overriding the persisted `workflow.research` toggle; argued in D2). The two models are injected into the Stage-2 and Stage-4 spawns (`model="{researcher_model}"` / `model="{roadmapper_model}"`), so the operator's `/gsd:set-profile` choice is honored exactly as in `new-milestone`.
- Update `PROJECT.md`'s `## Current Milestone: v[X.Y] [Name]` section — creating it when the post-completion evolution review removed or renamed it (see Preconditions) — goal + target features projected from the spec's Problem/Solution (milestone name from the spec's H1 title, confirmed with the operator) — and refresh the `Active requirements` section and the `Last updated` footer, completing the step-4 mirror: the roadmapper reads the whole file, so an Active-requirements block still describing the previous milestone is exactly the stale residue the load-bearing ordering exists to prevent.
- Reset `STATE.md` to "defining requirements", keeping the Accumulated Context section (`new-milestone` step 5's exact behavior).
- **`MILESTONE-CONTEXT.md` disposition (step-6 mirror, made visible):** `new-milestone` step 6 deletes a consumed `.planning/MILESTONE-CONTEXT.md`; here the spec plays that role and the file is never consumed — but a leftover from an abandoned `/gsd:discuss-milestone` would silently feed a *future* `gsd:new-milestone` run. If present, surface it (`AskUserQuestion`: Delete — abandoned, remove it / Keep — intended for a later `gsd:new-milestone`) rather than auto-deleting a file this command never read — the preconditions' visible-fact standard again.
- Commit both via `gsd-tools.cjs commit "docs: start milestone v[X.Y] [Name]" --files .planning/PROJECT.md .planning/STATE.md`. `gsd-tools.cjs commit` checks `commit_docs` itself and skips when false — so "honoring `commit_docs`" at every commit point in this document means exactly one thing: commit through `gsd-tools.cjs commit`, never raw git.

### Stage 1 — Project the spec → `REQUIREMENTS.md`

**Before writing:** if `.planning/REQUIREMENTS.md` still exists here, it belongs to the *current* milestone — the startup preconditions already errored on any other milestone's live markers and on a live-phase `ROADMAP.md` — though not necessarily to an earlier run of this command (a `gsd:new-milestone` run mid-flight, requirements defined but no roadmap yet, reaches this same guard). Either way, stop and ask via `AskUserQuestion` (mirrors `spec-create-context` step 5's existing-file guard, minus Merge: a projection is whole-file; merging two milestones' requirement sets is not meaningful). Two options always: **Overwrite / Abort**. A third — **Resume at Stage 4** — is offered only when the live file *is* the gate-approved projection left by a crash between Stage-3 Approve and roadmap approval, detected by identity, not inference: `.planning/.requirements.snapshot` exists **and** the live `REQUIREMENTS.md` is **byte-identical** to it (`milestone_checks.py snapshot --matches`, exit code only). Byte-identity is sound with no supporting lifecycle: a foreign file (e.g. one `gsd:new-milestone` wrote), a fresh never-approved projection sitting beside an older run's snapshot, and a hand-edited copy of the approved file all differ from the approved bytes, so the option never appears for them — they route to Overwrite/Abort by design. A hand-edited file *should* re-gate: a `check`-based detection would accept any structurally-legal edit and re-anchor it into the gated set with no gate pass — a laundering channel byte-identity closes. Resume needs no `check` re-run (identical bytes already passed the gate) and no re-snapshot (the snapshot already holds exactly the file being resumed). Choosing Resume skips Stages 1–3 (the approval already happened; `spec-verification.md` was committed at Approve, and Stage 2's stale-file guard never runs) and proceeds directly to Stage 4; the alternative, Overwrite, discards an already-approved gate pass and re-runs the whole pipeline including a second approval — including a fresh, nondeterministic Stage-2 pass whose findings may differ from the set already litigated. Byte-identity holds across the entire Stage-4 approval loop by construction: the unconditional restore returns the live file to snapshot bytes after every roadmapper return, and the one legitimate post-approval divergence — the `## Traceability` fill — is deferred to Stage 5, after roadmap approval, precisely so a crash anywhere in the window Resume serves leaves a Resume-detectable file (see Stages 4–5). **REQ-ID continuation:** `[CAT]-NN` numbering continues from the highest existing number per category across previous milestones — scanning both the v1 and v2 sections of each archive (v2 items carry IDs too) — read from the archives `gsd:complete-milestone` writes to `.planning/milestones/v*-REQUIREMENTS.md` (each prepended with a `complete-milestone` archive header — `# Requirements Archive … **Status:** SHIPPED …` — which carries no `[CAT]-NN` ids, so the per-category number scan is unaffected; `MILESTONES.md` itself records no REQ-IDs, so it is not a usable source), mirroring `new-milestone` step 9's "Continue numbering from existing"; categories with no prior REQs start at 01, as does everything when no archives exist. Colliding REQ-IDs across milestones would corrupt cross-milestone traceability — the archived requirements keep their IDs forever.

Emit a GSD-native `REQUIREMENTS.md`:
- **Requirements** grouped by category, `[CAT]-NN` checkboxes — projected from the spec's `D1..Dn` decisions and its `### What gets built` deliverables. Each deliverable bullet's `(Dx)` citations (startup-validated — see Preconditions / D8) tell the projection which decision it realizes, so scope outside D-blocks reaches the requirements *through its cited decision* — one source namespace, no second id scheme.
- **Out of Scope** table ← `concept-NON-GOALS.md` + the spec's "What does NOT get built."
- **v2 Requirements** (checkbox-less but ID-carrying, per the template — `- **[CAT]-NN**:` without a checkbox) ← the spec's deferred items / resolved-as-later Open Items. v2 IDs draw from the **same per-category continuation sequence** as v1 — they persist in the archives, so a parallel sequence would collide with future milestones' REQ-IDs. **Every v2 item is anchored by a deferred-form waiver row naming it** (see the `## Spec Traceability` schema below) — the row is its `Dx`'s sole coverage when the decision has no v1 checkboxes, or the v2-remainder's row beside the decision's v1 REQ rows when it has some; v2 items are never checkboxes, so they get no REQ rows of their own. The anchoring is `check`-enforced in both directions (Stage 3): a deferred row naming a nonexistent v2 ID fails, and a v2 item named by no deferred row fails — without the converse, v2 would be the one place scope could enter the gated, archived file with no `Dx` trace (the v5.0 SHORT leak, parked as deferred instead of scoped, would pass a v1-only rule). Expected empty for template-compliant specs — the upstream template tells mature specs to promote or drop deferred work — so these rules are the backstop for the specs that defer anyway.
- **Scope context (not requirements)** ← the spec's satisfied preconditions, as a non-checkbox note (so already-done work isn't re-scoped).
- **`## Spec Traceability`** — a net-new REQ↔`Dx` table (source→requirement), kept **separate** from the script-filled `## Traceability` (REQ→Phase). It survives Stage 4 by construction: the roadmapper is forbidden to write `REQUIREMENTS.md` at all, and Stage 4 unconditionally restores the whole file from the gate-approval snapshot after every roadmapper return; the script fills `## Traceability` only in Stage 5, after roadmap approval (see D5). **Schema — one row per REQ, `| REQ | Source | Note |`.** The row forms, the checkbox definition, and the gate checks are pinned as separate labeled items below so none stays buried in prose:
  - **Source forms** (the no-drift check enforces exactly this set — nothing else is a legal Source):
    - *decision-derived:* one or more `Dx` refs, comma-separated (mirroring the `(Dx)` / `(Dx, Dy)` citation forms — a bullet citing several decisions projects to a REQ realizing them all).
    - *amended:* a decision-derived Source optionally followed by `; SV-n[, SV-m] (gate-approved)` — one or more accepted Stage-2 findings amending the REQ, comma-separated (several findings may legally amend the same REQ; see Stage 3).
    - *new-REQ from a finding:* a Source with no `Dx`, of the form `SV-n (gate-approved)` — a finding accepted as a *new* REQ.
    - *waiver / deferred* (no REQ — `—` in the REQ column): `| — | Dx | waived: <reason> |` marks a decision that legitimately projects to zero requirements; the deferred variant `| — | Dx | deferred to v2 (CAT-NN): <reason> |` anchors a v2 requirement to its motivating decision — one row per v2 item, whether the decision's sole coverage or the v2 remainder beside its v1 REQ rows — deferred rather than dropped, the named v2 ID keeping the row auditable and `check`-verified in both directions (Stage 3). **Stage 1 proposes waiver/deferred rows itself** for decisions it classifies as zero-REQ constraints or v2-only deferrals (the gate cannot open otherwise: `check` fails while any `Dx` is uncovered, and Approve is only offered once it passes); the operator adjusts or vetoes each at the Stage-3 gate.
  - **Checkbox** (the unit the REQ↔row rule is defined over): a `- [ ]` / `- [x]` / `- [X]` line carrying a `**[CAT]-NN**:` id. **Checked state is ignored** — the Stage-6 `check` re-run happens mid-milestone when completed REQs are already ticked, so a `- [ ]`-only parser would silently drop them from the rule.
  - **Gate checks over this table:**
    - *completeness* = every `Dx` appears in ≥1 row's Source list (each decision in a multi-decision Source counts as covered), waivers counting — and because the citation contract (D8) wires every deliverable to a `Dx`, decision-completeness spans deliverables too. One residual, stated rather than hidden: when several bullets share one `Dx`, per-bullet mapping *inside* that decision is operator-reviewed at the gate (the citations make that grouping trivial to present).
    - *no-drift* = every row's Source is one of the forms above — nothing else is legal.
    - *REQ↔row* is **bidirectional**, defined over v1 checkboxes only (v2 items are checkbox-less — policed by the separate v2-anchoring rule over deferred rows, not this one): every `[CAT]-NN` checkbox in the file has exactly one row (a REQ without a row fails) *and* every non-waiver row's REQ matches a live checkbox (a row whose checkbox is gone fails too). Without the converse direction, an Edit-loop checkbox removal that forgets the row's twin would pass `check`, embed a phantom REQ in the Stage-3 snapshot, and resurface only as a Stage-4 `coverage` failure the roadmapper is re-spawned to fix but cannot.
- **`## Traceability` (empty placeholder)** — Stage 1 seeds the REQ→Phase table as an empty placeholder (matching GSD's requirements template) for Stage 5's post-approval deterministic fill: `milestone_checks.py traceability` rewrites it from the approved `ROADMAP.md`; the roadmapper itself never touches this file (see Stages 4–5 / D5).

**Projection rules** — what "faithful" means operationally, so two implementers produce materially the same file (the gate verifies mapping *presence*; these rules pin the projection itself):
- **Granularity:** default one REQ per `### What gets built` top-level bullet — the citation contract makes bullets the deliverable unit, and the bullet's `(Dx)` citations become the row's Source. Merge bullets only when they state the same observable capability at different granularities; a `Dx` cited by no bullet projects to its own REQ if it demands observable work, else to a Stage-1-proposed waiver row.
- **Phrasing:** GSD's own requirement criteria (`new-milestone` step 9 — specific and testable, atomic, independent), with "user-centric" read as operator/system-observable for infrastructure specs; the test is `mg:plan-phase` 5c's three quality gates (externally observable, implementation-independent, independently meaningful). The spec's literal values (counts, totals, names) are carried into REQ text verbatim — the "verbatim value fidelity" property Verification asserts.
- **Categories:** derived from the spec's own component/deliverable grouping (`### What gets built` families, the Solution's structure) — *not* from research `FEATURES.md`, `new-milestone`'s category source, which doesn't exist here. Prefixes follow the `plan-phase` 5c convention: reuse an archived category's prefix when the domain matches, else a new 3–5-char uppercase prefix; the grouping is operator-reviewed at the Stage-3 gate like every other projection choice.
- **Headings:** emitted section names follow the live GSD template verbatim (`## v1 Requirements`, `### <Category>`, `- [ ] **[CAT]-NN**:`, `## v2 Requirements`, `## Out of Scope` as the `| Feature | Reason |` table, `## Traceability`) — the Stage-1 labels above are descriptions, not headings; the only net-new sections are `## Spec Traceability` and the scope-context note.

### Stage 2 — Context-aware verification (spec-seeded research)

Spawn **`gsd-project-researcher`** (reuse the agent + its tools — NG4; `model="{researcher_model}"` from Stage 0's init) with a **spec-seeded prompt**, *not* the discovery dimensions:

- **Inputs** (`<files_to_read>`): the concept spec (`D1..Dn` + NON-GOALS), the just-projected `REQUIREMENTS.md`, and the codebase (source dirs + `.planning/codebase/` map if present).
- **Task:** for each decision, verify it still holds against current code; surface gaps, stale assumptions, and missing constraints (the class of finding that caught the `GRANT`).
- **Output contract — one file, not the discovery set.** The agent's body *unconditionally* writes `SUMMARY.md`/`STACK.md`/`FEATURES.md`/`PITFALLS.md` (its Step-5 "Always" list is **not** mode-gated), so a "verify only" prompt fights the agent body. Control it the way `new-milestone` narrows each of its researchers — pass an explicit `<output>Write to: .planning/research/spec-verification.md</output>` block and instruct the agent to emit **only** that file. **`<output>` is best-effort prose, not an agent-parsed directive** — the agent formally honors only `<files_to_read>` (its documented mandatory-read contract) and treats `<output>` as ordinary prompt text (exactly as `new-milestone`'s spawns do), so it may ignore it. The two things riding on the redirect have different safety nets: the **file-path** part is backstopped deterministically by the `research-post` janitor below (stray files are deleted whatever the agent wrote), while the **verification-task** part (audit each `Dx` against local code, *not* the agent's native feasibility / external-library posture) has **no mechanical backstop** — no janitor turns discovery findings into verification findings — so that half rests on the prompt alone and is the genuinely load-bearing steering (D2). The **findings-file format** is a separate, hard contract, pinned because `check` must parse it deterministically (the `<output>` block states this format verbatim): a markdown table, one finding per row, `| id | decision-ref | kind | what | suggested-addition | severity |`, where `id` is sequential `SV-1..SV-n`, `decision-ref` is a `Dx` or REQ id (`—` for spec-wide findings), `kind` ∈ `gap | stale | missing-constraint`, and `severity` ∈ `critical | major | minor`; zero findings = the header row with no data rows. `check` **fails loudly on an unparseable findings file** rather than treating it as empty — an empty read would silently invalidate every legitimate `SV-n` citation. Loud failure has a defined recovery, mirroring Stage 4's bounded re-spawn: re-spawn the researcher with the parse error and the pinned table contract as revision context; after 2 failed re-spawns for the same parse failure, stop and hand the file to the operator, who may hand-edit `spec-verification.md` into contract shape and have `check` re-run (the operator is already the gate's approval authority, so hand-edited findings open no channel the gate doesn't grant them) — rejecting the whole run is never the only exit from a malformed findings file. The `SV-n` id is what `## Spec Traceability` cites as Source when the operator accepts a finding at the gate. Findings are **candidate additions/corrections only — never silently merged**; they feed the Stage-3 gate. This file is also the reference `check` validates `SV-n` citations against (Stage 3), so it carries a **stale-file guard**: the command deletes any pre-existing `spec-verification.md` before the spawn — a leftover from an earlier run (e.g. after a Reject) would otherwise present stale findings as fresh, and stale `SV-n` ids as legal citations.
- **Backstops** (should the agent still emit its defaults despite the prompt) — one write-side mechanism, two read-side instructions. Write side: `milestone_checks.py research-pre` runs **exactly once, before the *first* spawn** (records `.planning/research/`'s current filenames to `.planning/.research-manifest`; a missing directory yields an empty manifest — and is **not** re-captured on any re-spawn, since re-capturing would fold a stray `SUMMARY.md` written by the first attempt into the manifest and make the janitor preserve the very file it exists to delete) and `research-post` after every researcher return, re-spawns included — it is idempotent against the same manifest — deleting any file in `.planning/research/` that is in neither the manifest nor named `spec-verification.md`, printing each deletion. Stray discovery output (`SUMMARY/STACK/FEATURES/PITFALLS`) is thus removed by set-difference the moment it appears, while pre-existing files (e.g. a previous milestone's committed `SUMMARY.md`) are never touched — the command deletes only what its own spawn created. Read side: the gate reads **only** `spec-verification.md`, and the Stage-4 spawn omits `research/SUMMARY.md` and bans reading `.planning/research/` — an **instruction-scoped** ban (unlike the `REQUIREMENTS.md` write guard, no restore-style mechanism can back a read-side ban), whose runtime detector is the Stage-4 `coverage` re-check. The full rationale for the ban and why `coverage` is its net lives at **Stage 4**. What that script *cannot* see: discovery content leaking into phase **goals** or **success criteria** carries no REQ-ID, so that residue is caught only at the Stage-4 roadmap approval — one reason that approval is a real review, not a rubber stamp. Note a stray `SUMMARY.md` needs no Stage-2 misfire to exist: a previous milestone's `new-milestone` run typically leaves one in `.planning/research/` — pre-existing, so `research-post` deliberately preserves it — and the same read-side exclusion covers it.

### Stage 3 — Faithfulness gate (single scope approval)

Present, for a single scope approval (the roadmap gets its own approval in Stage 4 — the same two approvals a `new-milestone` run has: requirements confirm + roadmap approve):
- **Completeness:** every spec `Dx` → ≥1 requirement **or** an operator-approved waiver row (below) — no silently dropped decisions. Deliverable coverage rides on the same check: the citation contract (D8, startup-validated) wires every `### What gets built` bullet to a `Dx`, so a dropped deliverable surfaces as an uncovered or visibly under-projected decision; where several bullets share one `Dx`, the gate presents them grouped by decision for the operator to confirm each landed.
- **No drift:** every requirement → a `Dx`, **or** an explicitly **flagged Stage-2 finding** the operator accepts/rejects item-by-item.
- **Additions vs corrections — both defined.** An accepted finding that introduces a **new** REQ records Source `SV-n (gate-approved)`. An accepted finding that **amends** an existing decision-derived REQ (a `stale` decision, or a missing constraint folded into an existing requirement — the `GRANT` shape) keeps that REQ's row and appends `; SV-n (gate-approved)` to its Source (a further accepted amendment to the same REQ joins the list — `; SV-n, SV-m (gate-approved)`) — `check` still sees every listed `Dx` covered, and the audit trail names each amendment. Either way, the row's Note column carries a one-line summary of the accepted finding, so the archived `REQUIREMENTS.md` stays self-explanatory even when `commit_docs` is off and no committed `spec-verification.md` exists. NG3 stands either way: the spec file is never edited; the divergence lives in the requirement and its traceability row.
- **Zero-REQ decisions use waivers, not filler REQs.** A `Dx` that legitimately projects to no requirement (a pure constraint like "keep X unchanged", or a process/tooling decision) gets a waiver row `| — | Dx | waived: <reason> |`; v2-deferred scope gets the deferred variant `| — | Dx | deferred to v2 (CAT-NN): <reason> |`, one row per v2 item whether or not the decision also has v1 rows — same row form, same gate review; `check` counts both as completeness coverage and enforces v2 anchoring bidirectionally: every deferred row's `CAT-NN` must name a live v2 item, and every v2 item must be named by exactly one deferred row. Waiver rows arrive pre-proposed by Stage-1 projection (see Stage 1) — the gate is where the operator confirms, edits, or vetoes each one; a vetoed waiver means the decision needs a real REQ, resolved in the Edit loop. Waivers live in the same gated file, so a bogus waiver faces the same operator approval as everything else.
- Stage-2 findings are the **only** source of beyond-spec scope (D3).

The checks are **script-run, not eyeballed** — `milestone_checks.py check` (see Scope) parses `## Spec Traceability` plus the spec's `D1..Dn` ids and names each violation (dropped `Dx`, illegal Source, REQ missing its row, a `deferred to v2` row naming no live v2 item, a v2 item no deferred row names, a cited `SV-n` with no matching finding in `spec-verification.md`, REQ-ID colliding with a prior milestone's archive under `.planning/milestones/`). The SV-existence check matters: a legal-looking Source *form* is not drift-proof — `SV-3 (gate-approved)` citing a finding that doesn't exist is exactly the fabricated-scope channel the gate exists to close, so `check` reads `spec-verification.md` and fails any citation without a backing finding. An LLM re-reading its own projection is the unreliability this gate exists to remove; per the repo convention, deterministic logic lives in `scripts/*.py`. **Approve is only offered once `check` passes** — while it fails, the gate presents the named violations with Edit / Reject only; there is no approve-with-known-violations path.

Each operator path is defined:
- **Approve** → commit `REQUIREMENTS.md` **and `.planning/research/spec-verification.md`** (`docs: define milestone v[X.Y] requirements`, honoring `commit_docs`) — the verification file must be as durable as the traceability rows that cite its `SV-n` ids: the live copy is overwritten by the next run or milestone, so the committed copy is the lasting audit trail (mirrors `new-milestone` step 9's per-step commit). Then snapshot the **entire approved `REQUIREMENTS.md`** via `milestone_checks.py snapshot` (writes `.planning/.requirements.snapshot` — the sole `restore` source, the `coverage` gated-set reference, and the byte-exact baseline Stage 4 restores after every roadmapper return, see Scope/D5), and proceed to Stage 4.
- **Edit** → apply the operator's edits to `REQUIREMENTS.md` (including `## Spec Traceability`) — or, for findings-file violations (an unparseable `spec-verification.md`, a cited `SV-n` with no backing finding), to `.planning/research/spec-verification.md` itself — then re-run `milestone_checks.py check`, re-present. Loop until approve/reject.
- **Reject** → abort. Run `milestone_checks.py snapshot --clear` — hygiene, not soundness: Resume detection is byte-identity against the snapshot (Stage 1), so a stale snapshot can only ever enable Resume for a live file that genuinely is the projection it approved; clearing on Reject just removes a dead witness. `REQUIREMENTS.md` is left uncommitted for inspection; the Stage-0 bookkeeping commit stands. The operator revises the spec upstream and re-runs (NG3 — the command never edits the spec).

This is the gate v5.0 lacked.

### Stage 4 — Roadmap (reuse `gsd-roadmapper`, unchanged)

Spawn `gsd-roadmapper` (agent unchanged; `model="{roadmapper_model}"` from Stage 0's init) with the **explicit input set** `new-milestone` gives it, **minus `research/SUMMARY.md`**:

- **`<files_to_read>`:** `PROJECT.md` (current — Stage 0 already rewrote its milestone section), the gated `REQUIREMENTS.md`, `config.json` (the roadmapper reads *granularity* from it), and `MILESTONES.md` (when present — absent means zero completed milestones, see Preconditions). **Omit `research/SUMMARY.md` and instruct: do not read `.planning/research/`** — omission alone is convention, not a mechanism (the agent lists `research/SUMMARY.md (if exists)` as expected context, holds Read/Glob/Grep, and a stale `SUMMARY.md` from a *previous* milestone will often still sit there); reading it would re-admit the discovery shaping this command exists to remove (NG5). Stage-2 findings reach scope through the gate, never through the roadmapper — which is why Stage 2 writes `spec-verification.md`, never `SUMMARY.md`. The coverage re-check below is the runtime detector if the instruction fails. **Post-completion `ROADMAP.md` residue needs no special handling:** the roadmapper writes `ROADMAP.md` wholesale, exactly as under `new-milestone` — the reorganized prior-milestone summary is replaced (history persists in `MILESTONES.md` + `.planning/milestones/`), so the file `coverage`/`traceability` later parse holds only this milestone's phases; and neither residue shape carries `**Requirements**:` lines anyway (verified: this repo's post-v1.1 residue and both prescribed reorganize formats keep them only under active `### Phase N:` sections).
- **Phase numbering is not automatic — and `MILESTONES.md` cannot supply it.** The roadmapper's own rule (`gsd-roadmapper.md`, Phase Numbering) is *"New milestone: Start at 1; Continuing milestone: Check existing phases, start at last + 1"* — so it *does* consult history, but only by reading the live `ROADMAP.md` it can see, and here that holds nothing but post-completion residue (`- [x] Phase N:` bullets, not live `### Phase N:` sections — see Preconditions), a signal too unreliable to derive a start number from; nor can it reliably tell "new" from "continuing" here, since a genuinely new spec-driven milestone opens beside months of archived phases. `new-milestone` says "read `MILESTONES.md` for the last phase number", but that file records only a phase **count** (`**Phases completed:** N phases` — the exact line `milestone.cjs` writes), which diverges from the last number the moment decimal phases or a non-1 start exist — the same disqualification Stage 1 already applies to it for REQ-IDs. Derive N deterministically instead: `milestone_checks.py phase-start` scans the archived `.planning/milestones/v*-ROADMAP.md` files (code-written verbatim copies of each completed roadmap) for the highest `### Phase N:` heading and prints `floor(max)+1`; no archives → `1`. Inject `Start phase numbering from [N]` into the prompt. (`MILESTONES.md` is still passed so the agent can cross-check; the same `phase-start` value already served the startup live-phase detection — it is computed once, pre-mutation.)
- **Coverage:** 100% / one-phase-per-REQ, enforced by the roadmapper as in `new-milestone`.
- **`REQUIREMENTS.md` is off-limits to the roadmapper — by instruction, made harmless by mechanism.** Its role doc expects to update the `## Traceability` (REQ→Phase) table in place; this spawn instead instructs it to write **only** `ROADMAP.md` + `STATE.md` and never touch `REQUIREMENTS.md` — the table is filled deterministically after it returns (next bullet). The instruction can still fail (the agent holds `Write`), but the whole-file restore (D5) erases any violation by construction, so no tampering survives to need policing. Tell it also that **gap resolution must never add, remove, demote to v2, or otherwise descope requirements** — its role doc's Step 4 explicitly offers "Add requirement to REQUIREMENTS.md" as a gap remedy, and its philosophy equally allows deferring a criterion to v2 or marking it out of scope; adding routes beyond-spec scope around the gate (D3), demoting silently drops spec-mandated scope, and either can surface *inside `ROADMAP.md`* as a phase citing an invented REQ-ID or omitting a gated one — which is why `coverage` stays the runtime net. Any gap → return `## ROADMAP BLOCKED` and let the operator decide.
- **After every return: restore, then cross-check — script-run, not eyeballed.** First, `milestone_checks.py restore` runs unconditionally, rewriting `REQUIREMENTS.md` byte-exact from the gate-approval snapshot (written by `milestone_checks.py snapshot` at Stage-3 Approve) — this erases any roadmapper edit to that file, of any kind, by construction (**why restore-always rather than compare-then-repair: D5**). Then `milestone_checks.py coverage` parses each phase's `**Requirements**:` line in `ROADMAP.md` and confirms the mapping is **bidirectional** — every gated REQ landed in exactly one phase, *and* every REQ-ID cited in `ROADMAP.md` is in the gated set (a roadmapper-*invented* REQ-ID fails, not just a dropped one — without the converse direction, a roadmapper that read stray research could smuggle scope in as phases citing nonexistent REQs). **The gated set is the snapshot's `## Spec Traceability` non-waiver rows** — authoritative because the section's one-row-per-REQ rule was `check`-verified at the gate, and the snapshot is the one REQ list the roadmapper cannot write. The `## Traceability` fill is deliberately **not** part of this sequence — it runs once in Stage 5, after roadmap approval; until then the live `REQUIREMENTS.md` stays byte-identical to the snapshot, preserving Stage 1's Resume detection across the whole approval loop.
- **Return handling + roadmap approval (mirrors `new-milestone` step 10).** `## ROADMAP BLOCKED` → present the blocker, work with the operator, re-spawn. `## ROADMAP CREATED` → run the previous bullet's sequence (unconditional `restore`, then `coverage`). A **`coverage` violation** (REQ unmapped, double-mapped, or invented) → re-spawn the roadmapper with revision context naming it — its `## ROADMAP REVISED` flow exists for exactly this. A roadmapper edit to `REQUIREMENTS.md` never triggers a re-spawn — the unconditional `restore` has already erased it before `coverage` ran (re-spawning would just re-roll a failure mode the mechanism already absorbs). **Bounded:** after 2 failed re-spawns for the same violation, stop and present it to the operator instead of looping — with defined paths, mirroring the Stage-2 parse-failure recovery: the operator may hand-edit `ROADMAP.md` and continue (the hand-edited file re-enters the same restore→coverage sequence before any approval prompt — the operator is already the roadmap's approval authority, so hand-edits open no channel approval doesn't grant), re-spawn once more with their own revision notes, or abort — an abort leaves the Stage-0/Stage-3 commits standing and the unapproved `ROADMAP.md` on disk, exactly the crashed-run state whose remedy the startup preconditions already name (delete `ROADMAP.md`, re-run as a pre-roadmap resume). The restore→coverage sequence re-runs after **every** roadmapper return — creation, revision, or adjustment — before any approval prompt. Once it passes, present the roadmap for approval (**Approve / Adjust phases / Review full file**); "Adjust" → re-spawn with revision notes, looping (sequence included) until approved. Nothing is committed until approval.

### Stage 5 — Commit roadmap artifacts

`PROJECT.md`/`STATE.md` were already updated and committed in **Stage 0** (mirroring `new-milestone` steps 4–6), and the roadmapper itself writes `STATE.md` fresh in Stage 4 (its "Write STATE.md" step) — Stage 5 must **not** rewrite it. What remains, mirroring `new-milestone` step 10's post-approval commit: after the Stage-4 approval loop and cross-check pass, **first fill the table** — `milestone_checks.py traceability` fills the `## Traceability` placeholder in the restored `REQUIREMENTS.md` from the approved `ROADMAP.md`'s `### Phase N:` / `**Requirements**:` lines (one `| REQ | Phase N | Pending |` row per mapping, plus the template's `**Coverage:**` summary: v1 total / mapped / unmapped — unmapped 0 by construction once `coverage` passed) — the roadmapper never writes the table, so `REQUIREMENTS.md` and `ROADMAP.md` cannot disagree. The fill sits here, not in Stage 4, so the live file stays byte-identical to the snapshot throughout the approval loop (Stage 1's Resume detection); the residual unguarded window — a crash between this fill and the commit below — is two script actions wide, versus the operator-paced loop the ordering protects. Then commit `ROADMAP.md` + `STATE.md` + `REQUIREMENTS.md` (`docs: create milestone v[X.Y] roadmap`, honoring `commit_docs`). Commit granularity thus matches `new-milestone`'s per-step atomic commits: bookkeeping (Stage 0) → gated requirements (Stage 3) → roadmap set (here).

### Stage 6 — Handoff (tell the operator what runs next)

The command ends by printing the downstream pipeline invocations, concretely parameterized (mirroring `spec-gsd-phases` step 8's Next Steps block). The phase range comes from the approved `ROADMAP.md` — the Stage-4 coverage re-check already parsed the roadmapper-assigned numbers, so the printed range is the actual continued numbering, never 1-based:

```
/mg:spec-prepare-context {first}-{last} {spec-path}    ← split the spec into per-phase files
/mg:spec-create-context {N} {per-phase file}           ← per phase: project the split into CONTEXT.md
/mg:plan-phase {first}                                 ← then plan as usual
```

The handover is verified compatible: `spec-prepare-context` validates `### Phase {N}:` entries in `ROADMAP.md` (exactly what the roadmapper writes) and uses each phase's REQ IDs + their `REQUIREMENTS.md` texts as content-mapping signals — signals this command's output uniquely provides (the `spec-gsd-phases` path leaves `Requirements: TBD`, degrading that mapping). And `mg:plan-phase` step 5b routes phases that already carry REQ IDs to its coverage-check path (5d), so requirement generation (5c) never runs — projected requirements are not re-derived from scratch. But 5d is not a pass-through: when it judges a `CONTEXT.md` decision uncovered by the existing REQ texts, it appends new requirement IDs to `REQUIREMENTS.md`/`ROADMAP.md` and commits, explicitly without operator approval (its role doc states no approval is needed). Such additions carry no `## Spec Traceability` row and pass no gate — **the faithfulness guarantee ends at Stage 5.** The handoff block therefore closes with a one-line caveat: on a spec-projected milestone, treat any `plan-phase` "+N added" requirement output as beyond-spec scope to review against the spec — and the caveat prints the exact re-run invocation, parameterized like the rest of the block (`uv run {installed scripts dir}/milestone_checks.py check {spec-path}` — the pinned invocation form, script path resolved at install), whose REQ↔row rule flags the row-less checkboxes.

### Template-drift guard

Ship **one snapshot** — `requirements-template.snapshot`, source `spec/references/`, installed to `.claude/spec/references/` — and a **startup compatibility check** diffing it against the live `.claude/get-shit-done/templates/requirements.md` (mirrors `spec-create-context`'s context-template check — its internal "Step 1": identical → proceed; drift → `AskUserQuestion` Continue-anyway / Abort, snapshot never auto-updated). **Compared blocks pinned:** `<template>` and `<guidelines>` only; `<example>` and `<evolution>` are ignored — cosmetic example edits must not fire drift (the same section-scoping the `spec-create-context` check applies to `context.md`, which ignores its `<good_examples>`). It runs at startup, after the fail-fast preconditions and before Stage 0 mutates anything — an Abort here leaves `.planning/` untouched. **No roadmap snapshot:** the command never authors `ROADMAP.md` (the roadmapper does), and the only roadmap surface it depends on — the `### Phase N:` / `**Requirements**:` contract the faithfulness re-check and the `traceability` filler parse — is already guarded at runtime by that re-check, which fails loudly if the shape drifts. A full roadmap-template diff would be disproportionate to a two-line parse contract.

## Design Decisions

### D1: Project, don't elicit (bottom-up, spec-first)
**Choice:** Derive `REQUIREMENTS.md` as a faithful projection of the frozen spec, not through per-category elicitation.
**Why:** For a "fix observed issues" milestone the scope is already settled in the spec; elicitation re-opens frozen decisions and produces a re-derivation that can silently drift (v5.0 SHORT leak). Projection with a traceability mapping makes drift checkable.
**Alternatives rejected:** `new-milestone`'s elicitation flow (re-litigates the spec); a bare doc→REQUIREMENTS dump with no traceability (no faithfulness signal).

### D2: Keep research — re-aimed from discovery to spec-verification
**Choice:** Retain a research pass, seeded with the spec + projected requirements + code and tasked to *verify each decision against the code and flag gaps*. Reuse `gsd-project-researcher` **unchanged as an agent**, steered entirely by the spawn prompt + `<output>` redirect (Stage 2) — no edits to the agent file (NG4).
**Why:** Blind domain discovery is redundant against a code-grounded spec, but context-aware verification demonstrably catches real gaps the spec missed (the view `GRANT`), and reusing the deployed agent avoids a new maintenance surface. **Caveat — this is steering an over-general agent, not a natural fit:** the agent's native Feasibility mode answers "*can* we build X?" (→ `FEASIBILITY.md`, YES/NO/MAYBE) and its "Verify before asserting" posture targets *external* library claims (Context7/docs) — neither is "audit each frozen `Dx` against local code" out of the box, and its Step-5 body unconditionally writes the `SUMMARY/STACK/FEATURES/PITFALLS` discovery set. The Stage-2 prompt + `<output>` redirect must override all three — but only the third (stray discovery *files*) has a mechanical backstop, the `research-post` janitor (Stage 2); overriding the first two (feasibility framing, external-library verification posture) is *behavioral* and rests on the prompt alone, so that steering is the genuinely load-bearing part. Its failure mode is **contained, not silent**: a mis-steered researcher yields discovery-flavored or off-target findings, and every finding then faces the **Stage-3 operator gate** (accept/reject item-by-item), so bad steering produces junk the operator rejects — never scope that enters unseen. The steering therefore has no *mechanical* verification (LLM behavior is not deterministically CI-testable, and the "No blind research" check covers only the file-hygiene half), but it has a real *human* backstop — the same trust boundary D3 designates. `<output>` itself is best-effort prose the agent may ignore — it formally honors only `<files_to_read>`, never `<output>` as a parsed directive (Stage 2). If steering proves unreliable, the answer is a tighter prompt — **not** a new agent (NG4 forbids it).
**Always-on — deliberately ignoring the persisted `workflow.research` toggle** (`research_enabled` in Stage 0's init extract): that toggle governs *discovery* research — `new-milestone` step 8 asks per milestone and persists the answer via `config-set` for other tools to honor. Stage 2 is not discovery; it is part of the faithfulness machinery itself: `check` validates every `SV-n` Source against `spec-verification.md`, and D3 makes gate-approved findings the *only* legal beyond-spec channel — skip the pass and the gate loses its findings reference while genuine gaps (the `GRANT`) lose their only door. So a `workflow.research: false` project still gets exactly one spec-seeded verification spawn per run — including full re-runs after a Reject, where the stale-file guard deletes the prior findings (a revised spec invalidates them anyway). The toggle keeps governing discovery research everywhere else in GSD.
**Alternatives rejected:** Drop research entirely (loses the gap-catching that earned its keep); author a purpose-built verification agent (NG4 — the spawn prompt carries the load instead); honor `workflow.research` / add a skip flag (a skipped pass severs the gate from its findings reference and closes the D3 channel — the one research mode this command cannot make optional).

### D3: Strict projection; beyond-spec scope only via research-surfaced, gate-approved additions
**Choice:** The command projects only what's in the spec. Scope not in the spec appears **only** if Stage-2 research flagged it *and* the operator accepted it at the faithfulness gate.
**Why:** This is the direct fix for the v5.0 SHORT leak — no path exists for un-vetted scope to enter silently, while genuine gaps (the `GRANT`) still land, with an audit trail.
**Alternatives rejected:** A `--also <note>` freeform input (re-opens the elicitation drift door); silent merge of research findings (removes the operator gate).

### D4: Reuse `gsd-roadmapper` unchanged; run the faithfulness gate around it
**Choice:** Spawn the existing roadmapper for phase derivation; run the completeness/no-drift check before it and re-verify after it.
**Why:** Phase quality then equals `new-milestone`'s, and the roadmapper's 100%-coverage/one-phase-per-REQ enforcement is synergistic with the gate. Unlike in `new-milestone`, it is barred from `REQUIREMENTS.md` entirely — the `## Traceability` table it would normally rewrite is script-filled from its `ROADMAP.md` output instead, and the gate re-verifies its output via `coverage` (D5).
**Alternatives rejected:** A bespoke phase deriver (duplicates a maintained agent, diverges in quality). Composing the existing family path (`mg:spec-gsd-phases` + `gsd:add-phase`) — it appends goal-only phases (`Requirements: TBD`) to an already-open milestone: no milestone bookkeeping, no `REQUIREMENTS.md`, no Dx traceability, no coverage enforcement, no faithfulness gate — every v5.0 failure mode would pass through unchecked.

### D5: Dx↔REQ mapping in a separate `## Spec Traceability` section; `REQUIREMENTS.md` roadmapper-proof by whole-file restore
**Choice:** Store the source→requirement mapping in its own REQUIREMENTS.md section, distinct from the script-filled `## Traceability` (REQ→Phase) — and bar the roadmapper from `REQUIREMENTS.md` entirely: Stage-3 Approve snapshots the whole approved file, Stage 4 restores it byte-exact after every roadmapper return, and `milestone_checks.py traceability` fills `## Traceability` — rows plus the template's `**Coverage:**` summary — deterministically from `ROADMAP.md`'s `**Requirements**:` lines (the same parse `coverage` runs), in Stage 5 once the roadmap is approved: a pre-approval fill would break Stage 1's byte-identity Resume detection.
**Why:** REQUIREMENTS.md has no native source column, so the mapping needs its own section. And once a gated file must survive an agent that holds `Write`, instruction-scoping alone ("only touch `## Traceability`") leaves a tampering class — added/removed checkboxes, a strayed mapping section — that needs a post-roadmapper `check` re-run and re-spawn budget to police. The whole-file restore removes that class by construction: the roadmapper's only legitimate REQUIREMENTS.md contribution — REQ→Phase rows with constant `Pending` status — is fully derivable from its `ROADMAP.md` output, so nothing is lost by forbidding the write and emitting the table with a script, and the two artifacts cannot disagree. (Restore reads the snapshot *file*, never conversation context — robust to a long run's compaction, and no LLM judgment — and behaves identically whether or not `commit_docs` is on; this is why there is no compare-then-repair `intact` subcommand.) The decisive argument for the in-file home is **archive self-containment**: `gsd:complete-milestone` archives `REQUIREMENTS.md` to `.planning/milestones/v*-REQUIREMENTS.md`, so traceability inside the file persists for the milestone's lifetime — anything outside it dies at archive time. The `.planning/.requirements.snapshot` sidecar does not contradict this: it is a transient, run-scoped *guard reference* (also the `coverage` check's gated-set source), overwritten by the next run and never archived — the section in `REQUIREMENTS.md` remains the record.
**Alternatives rejected:** Overload the `## Traceability` table (loses the source→REQ record — that table is REQ→Phase, rewritten wholesale on every fill); a sidecar file as the *primary* home (never archived by `complete-milestone`, so the mapping dies with the run; splits the artifact); letting the roadmapper update `## Traceability` in place with a section-scoped snapshot/restore around `## Spec Traceability` (the earlier design of this spec: keeps an agent writing a gated file, so roadmapper-added checkboxes survive the section restore and need a `check` re-run plus re-spawn budget — a failure class the whole-file restore erases by construction, for the cost of one deterministic table emitter); writing the section into `REQUIREMENTS.md` only after Stage-4 approval to spare the restore guard (leaves the Stage-3 requirements commit without its traceability — a weaker mid-run audit trail — and the snapshot is still needed anyway as `coverage`'s gated-set reference, so nothing is actually saved).

### D6: GSD-native output, no GSD patches; installed via mg-cc-tools
**Choice:** Produce only files GSD already understands (`REQUIREMENTS.md`, then roadmapper-written `ROADMAP.md`/`STATE.md`, `PROJECT.md`), shipped as an mg-cc-tools command with a `requirements-template.snapshot` + a startup drift check.
**Why:** Matches `spec-create-context`'s proven "no GSD patches" property; the drift guard keeps the projection honest as GSD's templates evolve.
**Alternatives rejected:** Forking `new-milestone` in GSD itself (patch-maintenance burden; couples to GSD's release cadence).

### D7: Require D-blocks — no unstructured-spec fallback
**Choice:** The spec must carry `D1..Dn` decision blocks; a spec without them fails the startup precondition, pointing at `mg:spec-draft` → `mg:spec-improve`.
**Why:** The command's sole intended input is the spec-family output, which always carries D-blocks. A fallback would need a second source-id namespace (positional `Sn` ids over Scope bullets) whose ids renumber silently when the spec is revised upstream — while persisting forever in archived traceability tables — and whose completeness check turns vacuous when "What gets built" holds prose or a file tree instead of bullets (the concept-spec-template mandates no bullets there): a gate that can pass while verifying nothing. Genuinely unstructured docs already have a home at phase level (`plan-phase --prd`). Note the boundary with D8: requiring D-blocks does not mean all scope lives *inside* them — deliverables outside D-blocks are wired to decisions by the citation contract (D8). What D7 rejects is serving specs with *no* D-blocks at all.
**Alternatives rejected:** Fall back to extracting requirements from Solution/Scope/Verification with `Sn`/`§section` pseudo-ids (unstable ids + the vacuous-pass hazard + a second completeness semantics in `milestone_checks.py`, all for an input class the command is not meant to serve).

### D8: Scope→decision citation discipline — an upstream contract, one id namespace
**Choice:** Every top-level bullet under a spec's `### What gets built` must cite the decision(s) it realizes — `(Dx)` / `(Dx, Dy)`. The contract is enforced upstream: the concept-spec-template mandates the structure, `mg:spec-draft` emits it, and `mg:spec-improve`'s reviewer flags violations. This command validates it at startup (`milestone_checks.py citations`) and projects from a single source namespace: `Dx`.
**Pinned grammar** (one definition, three consumers — the template, `mg:spec-draft`, and the `citations` parser; divergence here is exactly the two-implementer drift this spec elsewhere forbids): the section is the level-3 heading `### What gets built`, matched verbatim, and extends to the next heading of level 1–3 (`#`/`##`/`###`) or end-of-file — `####`-and-deeper headings stay inside it as illustration; a **top-level bullet** is a line starting at column 0 with `- ` inside that section — indented sub-bullets, prose paragraphs, code blocks, and file-tree diagrams remain legal as illustration but are ignored by the parser, so scope must ride on the top-level bullets; a **citation** is any parenthesized group of the exact form `(Dx)` / `(Dx, Dy, …)` — pattern `\(D\d+(, ?D\d+)*\)` — appearing anywhere in the bullet's own text — which is its **single physical line**: the parser scans only the `- ` line itself, never indented continuation lines or nested bullets, so a citation must sit on the bullet's own line (the spec family emits single-line bullets; pinning one physical line is what keeps two implementations byte-agreed); position within the line is free because bullets legitimately end in other parentheticals (this spec's own `…re-check). (D6)` shape defeats a trailing-only match). **Decision ids** are the `n` of `### Dn:` headings under `## Design Decisions`; contiguity is not required — `citations` validates against the extracted id set, nothing else.
**Why:** Deliverables routinely live outside D-blocks (the template is explicit that not every choice needs one), and both in-command repairs fail the trackability test: projection-time positional ids renumber silently on upstream edits (D7), and quote-anchored excerpts are unreferenceable, fragile identifiers that give no-drift but no completeness check. Authored ids are the only stable ids — and the only authored ids worth having are the decisions themselves. The discipline also improves the specs: a deliverable no decision motivates is a spec smell, surfaced upstream where the author+reviewer loop can fix it. The contract is unconditional in the template — not gated on "will this become a milestone" — so any spec can be promoted later without a refresh round.
**Alternatives rejected:** Quote-anchored `S: "<excerpt>"` traceability rows (fabrication-proof but untrackable, and deliverable-completeness stayed a manual eyeball); a second authored namespace `S1..Sm` (permanent dual-namespace cost in every table, archive, and check, plus id-lifecycle rules); precondition-only enforcement without the template change (new and old specs silently diverge).

### D9: Mirror `new-milestone`'s lifecycle mechanics verbatim
**Choice:** Stage 0 reproduces `new-milestone` steps 4–6 (PROJECT.md milestone section + Active-requirements/`Last updated` refresh, STATE.md reset, MILESTONE-CONTEXT.md disposition, per-step commits through `gsd-tools.cjs`, config/model extraction), and Stage 1 reproduces step 9's REQ-ID continuation from the milestone archives. Two deliberate divergences: MILESTONE-CONTEXT.md is operator-confirmed rather than auto-deleted — `new-milestone` deletes it as *consumed*, and this command never consumes it (Stage 0) — and the starting phase number derives from the archived `.planning/milestones/v*-ROADMAP.md` files via `phase-start`, not from `new-milestone`'s "read `MILESTONES.md` for the last phase number" instruction, which names a datum the file doesn't contain (it records a phase *count*; Stage 4).
**Why:** These mechanics are GSD's state contract, not incidental style: `PROJECT.md` must describe the new milestone before the roadmapper reads it (the ordering is load-bearing), `gsd-tools.cjs commit` self-checks `commit_docs`, and continued REQ numbering keeps archived traceability collision-free. Inventing parallel mechanics would desynchronize this command from every other GSD lifecycle tool.
**Alternatives rejected:** Custom bookkeeping (drifts from GSD's state expectations); restarting REQ numbering per milestone (collides with archives — corrupts cross-milestone traceability).

### D10: End at the roadmap; hand off with parameterized next steps
**Choice:** Stage 6 prints the exact downstream invocations (`spec-prepare-context {first}-{last} {spec-path}` → `spec-create-context` → `plan-phase`) using the roadmapper-assigned phase range, then stops.
**Why:** Phase-`CONTEXT.md` seeding is owned by shipped downstream commands (NG7) — duplicating it here would fork that logic — and printing the actual continued phase numbering removes the one operator error the handoff invites (guessing a 1-based range).
**Alternatives rejected:** Auto-running `spec-prepare-context` (couples the commands and removes the operator's roadmap-review moment); ending without the block (the operator reconstructs parameters by hand — exactly the guesswork Stage 4 already solved).

## Verification

- **Faithful projection.** Given a citation-compliant spec with `D1..Dn`, the generated `REQUIREMENTS.md` has, for every `Dx`, ≥1 row in `## Spec Traceability` (a REQ mapping, or an operator-approved waiver/deferred row — filler REQs for pure-constraint decisions are exactly what waivers exist to prevent), and every REQ maps to a `Dx` or a gate-approved flagged addition. *Acceptance case (in-repo fixture):* a synthetic citation-compliant spec fixture shipped with the tests — including deliverables whose only decision link is their bullet citation — projects with every `Dx` covered, the cited deliverables landing under their decisions, and nothing beyond the fixture's content. *Optional manual validation (runs in the target project, not CI):* replay the v5.0 L2 `concept.md` → expect the SCHM/QTR/ANN/VIEW/ORCH/CONS families with **no SHORT track** unless research flags it and the operator accepts it.
- **Projection rules applied.** The Stage-1 projection rules are exercised, not just the traceability *structure*: against the fixture spec, the projection yields one REQ per `### What gets built` top-level bullet except where two bullets state the same observable capability (a documented merge — the fixture carries one such pair, asserted merged), assigns each REQ to a category derived from the spec's own deliverable grouping (never a research `FEATURES.md`, which does not exist here), and reuses an archived category's prefix when the domain matches while minting a fresh 3–5-char uppercase prefix otherwise (the fixture shares a domain with a seeded archive category, asserted reused). Without this, the granularity/category/prefix rules — the ones that make two implementers produce materially the same file — have no test.
- **Beyond-spec is never silent.** A scope item absent from the spec lands **only** if Stage 2 flagged it and the operator accepted it. *Drive it deterministically with an injected findings file* — live re-discovery of a specific gap is an LLM outcome, not an acceptance criterion: a fixture `spec-verification.md` containing a `GRANT`-shaped finding (operator accepts → lands as an amendment to the fixture's view requirement, its row recording Source `Dx; SV-n (gate-approved)`) and a spurious item absent from the findings file (→ never appears).
- **Roadmapper coverage.** After the Stage-5 fill, `## Traceability` maps 100% of REQs to exactly one phase (0 unmapped, its `**Coverage:**` summary reading mapped = total, unmapped 0) — script-filled by `traceability` from the approved `ROADMAP.md`, so it agrees with the phase mapping by construction; throughout the Stage-4 approval loop, before the fill, the live `REQUIREMENTS.md` stays byte-identical to the snapshot — and `coverage` finds every gated REQ in some phase's `**Requirements**:` line and, conversely, no phase citing a REQ-ID outside the gated set (a `ROADMAP.md` citing an unknown REQ-ID fails `coverage`). The gated set comes from the Stage-3 snapshot; any roadmapper edit to `REQUIREMENTS.md` — an added requirement included — is erased by the unconditional whole-file `restore` before `coverage` runs, and if a phase maps the invented REQ anyway, `coverage` fails it.
- **Drop-in artifacts.** `gsd:plan-phase <N>` runs against the produced `ROADMAP.md` with no format errors (GSD-native, no patches).
- **Preconditions fail fast, pre-mutation.** Each startup violation produces its specified `ERROR` and exits with `.planning/` untouched (no `PROJECT.md`/`STATE.md` edit, no commit): either `<version>` or `<spec-path>` argument missing (usage `ERROR`, arity checked before all else); missing/empty spec; spec without `D1..Dn` decision blocks; a `### What gets built` bullet with no `Dx` citation or citing a nonexistent `Dx`; a missing or bullet-less `### What gets built` section (no vacuous `citations` pass); missing `.planning/PROJECT.md`; missing `.claude/get-shit-done/`; malformed `<version>`; `<version>` already recorded in `MILESTONES.md`; a live `REQUIREMENTS.md` or a live-phase `ROADMAP.md` (`### Phase N:` headings ≥ the `phase-start` number) while `<version>` ≠ the current milestone; a live-phase `ROADMAP.md` while `<version>` == the current milestone — this ERROR names the manual recovery for a crashed run's unapproved roadmap (operator deletes `ROADMAP.md`, re-runs as pre-roadmap resume; the command never auto-deletes). **Post-completion clean state:** a residue-only `ROADMAP.md` (reorganized prior-milestone summaries, no live `### Phase N:` sections) with no `REQUIREMENTS.md` — the command's primary entry state — proceeds with no ERROR and no confirm; bare `ROADMAP.md` existence is never the open-milestone signal. The one legal dirty state — `<version>` == `PROJECT.md`'s current milestone with **no** live-phase `ROADMAP.md` — proceeds as a pre-roadmap resume; when its leftover `REQUIREMENTS.md` is the gate-approved projection (snapshot present + byte-identical — `snapshot --matches`), the Stage-1 guard offers **Resume at Stage 4** alongside Overwrite/Abort, and Resume lands in Stage 4 without re-running Stages 1–3; a live file differing from the snapshot by any edit gets Overwrite/Abort only. **First-milestone case:** `PROJECT.md` present but no `MILESTONES.md` is *not* a violation — the run proceeds with phase numbering injected as 1 (`phase-start` over zero archives), all REQ categories starting at 01, and the version-collision check vacuously passing. **Abandoned-bookkeeping case:** a `PROJECT.md` Current-Milestone section naming a version that is neither `<version>` nor `MILESTONES.md`-recorded, with no live markers, is a confirm, not an ERROR — the run proceeds only after the operator approves overwriting it; an **absent or renamed** Current-Milestone section, or one naming an already-completed (`MILESTONES.md`-recorded) version, proceeds silently as the post-completion clean state. **Script-classified:** every GSD-side state above is a named `milestone_checks.py preflight` verdict — the command maps verdicts to the specified ERROR/confirm texts and never re-derives the classification in-context (verdict fixtures under **Deterministic checks** below).
- **Drift guard.** Against an unmodified GSD `requirements.md` template, the startup drift check reports "compatible"; against a mutated `requirements.md` template section, it surfaces "Template drift" with Continue/Abort, and an Abort leaves `.planning/` untouched. (The roadmap-template contract is covered instead by the post-roadmapper re-check under **Roadmapper coverage** above.)
- **No blind research.** The Stage-2 pass reads the spec + code and returns verify/gap findings, not ecosystem tables. After `research-post` runs, `.planning/research/` holds no file that wasn't there before the spawn except `spec-verification.md` — a property the set-difference janitor gives by construction, not by prompt compliance — and files predating the spawn (e.g. a previous milestone's `SUMMARY.md`) are untouched. The *content* half — that findings are verification-shaped (`gap`/`stale`/`missing-constraint` keyed to a `Dx`), not discovery — is **not** CI-gated (it is LLM behavior); its backstop is the Stage-3 operator gate, where discovery-flavored or off-target findings are rejected item-by-item, so a steering failure degrades finding *quality* but cannot inject un-vetted scope (D2/D3).
- **Full projection coverage.** Given a spec with a populated NON-GOALS file, deferred/Open items, and satisfied preconditions: `concept-NON-GOALS.md` + "What does NOT get built" land in **`## Out of Scope`**; deferred / resolved-as-later items land in **`## v2 Requirements`**; satisfied preconditions land in the **scope-context note** (never as checkboxes). Each is asserted present. Given a spec with *no* NON-GOALS sibling, the Stage-3 gate explicitly reports "no NON-GOALS file found" (absence is visible, not silent); a `*-NON-GOALS.md` sibling not matching the basename convention is surfaced for operator confirmation, not skipped.
- **Verbatim value fidelity.** Projected requirements preserve the spec's specific values (counts, column totals, names) exactly — the fixture spec carries distinctive literal values that must appear unchanged in the projected REQs (the "48 vs ~50" class of slip). Projection-not-elicitation should make this hold by construction; the check proves it. The optional v5.0 replay double-checks the same property on real data.
- **Milestone bookkeeping (Stages 0 + 5).** After a run, `PROJECT.md` gains/updates its current-milestone section plus a refreshed `Active requirements` section and `Last updated` footer — all written in Stage 0, **before** the roadmapper reads it — and `STATE.md` reflects the new milestone (roadmapper-written in Stage 4, not rewritten afterward); with `commit_docs` enabled the three commit points land (bookkeeping; requirements + `spec-verification.md`; roadmap set), and with it disabled none do. A pre-existing `MILESTONE-CONTEXT.md` is surfaced for operator disposition (Delete / Keep), never silently deleted or silently left to leak into a future `gsd:new-milestone`.
- **Handoff.** After Stage 5, the Next Steps block prints with the actual roadmapper-assigned phase range (continued numbering, not 1-based) and the original `<spec-path>`; running the printed `/mg:spec-prepare-context {first}-{last} {spec-path}` succeeds against the produced `ROADMAP.md`/`REQUIREMENTS.md` (phase entries found, REQ texts resolved), and downstream `plan-phase` on any produced phase takes its existing-REQ-IDs path (step 5b → 5d), never requirement generation (5c); the printed block ends with the 5d beyond-spec caveat line (Stage 6) including the concrete `milestone_checks.py check {spec-path}` re-run invocation, asserted present — 5d's own uncovered-decision additions are outside this command's guarantee.
- **Deterministic checks.** `milestone_checks.py` verdicts are exercised on fixtures: a citation-compliant spec passes `citations`, and a faithful projection passes `check` (including one whose coverage relies on a legal waiver row, one on a `deferred to v2 (CAT-NN)` row, one with a multi-decision `Dx, Dy` Source row, one with a `Dx; SV-n` amended row, one with a multi-amendment `Dx; SV-n, SV-m` row, and one mid-milestone copy whose completed checkboxes are ticked `- [x]`/`- [X]` — checked state never drops a REQ from the REQ↔row rule); an uncited `### What gets built` bullet, a citation to a nonexistent `Dx`, a bullet-less or missing `### What gets built` section (no vacuous pass), a dropped `Dx`, an illegal Source, a Source citing an `SV-n` absent from `spec-verification.md`, an unparseable `spec-verification.md` (fails loudly, not treated as empty), a REQ without a traceability row, a non-waiver row whose REQ has no matching checkbox (the forgotten-twin Edit case), a `deferred to v2` row naming a v2 item that doesn't exist, a v2 item named by no deferred row (the deferred-scope drift case), an unmapped/double-mapped REQ, and a `ROADMAP.md` citing a REQ-ID outside the snapshot-derived gated set each fail the corresponding subcommand (`citations` / `check` / `coverage`) naming the specific violation; `restore` run against a `REQUIREMENTS.md` the roadmapper edited (an added requirement checkbox, a mutated `## Spec Traceability` — the tampering cases) leaves the file byte-identical to the snapshot; `traceability` run against an approved `ROADMAP.md` fixture fills `## Traceability` with exactly the phase mapping `coverage` validated plus a `**Coverage:**` summary matching it (mapped = total, unmapped 0); `snapshot --matches` exits 0 against a byte-identical live `REQUIREMENTS.md` and non-zero against a one-byte edit or a missing snapshot (Resume is never offered for a hand-edited or foreign file); `snapshot --clear` deletes the snapshot (the rejected-projection hygiene case); `phase-start` over archive fixtures prints last-phase+1 (an archive whose highest heading is a decimal `### Phase 24.1:` yields `25`) and `1` with no archives — never the `MILESTONES.md` phase *count*; `preflight` fixtures produce each named verdict — `clean` over post-completion residue (reorganized `ROADMAP.md`, no `REQUIREMENTS.md`), `resume-pre-roadmap`, `live-phase-current`, `open-other-milestone`, `version-completed`, `abandoned-bookkeeping`, `bad-version`, `missing-project`, `missing-gsd` — with the ERROR states exiting non-zero; `research-post` run against a manifest plus a directory holding newly-appeared discovery files deletes exactly the strays — manifest-listed files and `spec-verification.md` survive.
- **Upstream citation contract.** The updated `concept-spec-template.md` mandates the `### What gets built` bullet+citation structure; a `mg:spec-draft`-produced spec carries the citations; a `mg:spec-improve` round on a spec containing an uncited deliverable flags it as a violation. This concept spec itself passes `milestone_checks.py citations` — the contract's first compliance case.
- **Install + registration.** `spec/install.sh --project <proj>` copies the command + the `requirements-template.snapshot` + `milestone_checks.py`, resolves every `{MG_INSTALL_*}` placeholder (no stray placeholders remain in the installed command), and registers the command and script in `mg-cc-tools.manifest.json`; and the extended source-existence validation fails fast with a clear error when any newly-required source file (`spec-create-milestone.md`, `requirements-template.snapshot`, `milestone_checks.py`) is absent before copy.
