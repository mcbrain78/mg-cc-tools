The command follows the codebase-health-verify.md pattern adapted for documentation verification. Structure:

**Role section:** You are the Verifier -- step 3 of the scan-generate-verify pipeline. Read-only, never modifies docs.

**Before You Start section:**
1. Read references/schema.md for the scan data contract
2. Read the verifier agent file: `agents/verifier.md` -- store its full contents for the Task prompt

**Prerequisites section:**
- Check .mg/docs/docs-scan.json exists (scan must have run)
- Check docs directory contains .md files (generation must have run)
- If either missing, abort with message directing to the correct prior step

**Process section -- 5 steps:**

**Step 1: Load Context**
1. Read .mg/docs/.docs.config.json (fall back to {GLOBAL_CONFIG}). Extract docs_dir, audiences.
2. Read .mg/docs/docs-scan.json. Extract root_path as project_root.
3. Build runtime paths: docs_dir_abs = {project_root}/{docs_dir}

**Step 2: Reference Extraction (deterministic)**
Run check-references.py ONCE for the entire docs directory:
```bash
python3 {SCRIPTS_DIR}/check-references.py \
  --docs-dir <docs_dir_abs> \
  --project-root <project_root> \
  --output <project_root>/.mg/docs/scan-logs/verify-refs.json
```
IMPORTANT: Use --docs-dir (directory-level), NOT --doc-file. The script iterates internally.

Save the output path -- the verifier agent will read this file.

**Step 3: Spawn Verifier Agent**
Spawn a SINGLE verifier agent via Task tool. Unlike codebase-health which parallelizes by category, docs verification runs 6 sequential checks in one agent instance.

The Task prompt MUST:
- Paste the full contents of agents/verifier.md
- Pass these parameters: project_root, docs_dir (absolute path), scan_data_path (.mg/docs/docs-scan.json), glossary_path ({docs_dir_abs}/GLOSSARY.md), style_guide_path (references/style-guide.md), output_report_path ({project_root}/.mg/docs/docs-verify-report.md)
- Pass the reference extraction output path: {project_root}/.mg/docs/scan-logs/verify-refs.json
- OVERRIDE the agent's reference integrity step with this instruction: "For Check 1 (Reference Integrity): Read the pre-extracted references from {verify-refs.json path}. For entries with type 'file_path', use the script's status directly (broken = critical issue, valid = no issue). For entries with type 'symbol', IGNORE the script's status -- instead use the LSP tool (go-to-definition) to verify each symbol. If LSP resolves it, it is valid. If LSP cannot resolve it, report as severity high."
- Include the glossary inconsistency flag instruction: "During Check 2 (Cross-Doc Consistency), also surface glossary inconsistency flags from the generate pipeline's reconciliation pass if {project_root}/.mg/docs/scan-logs/glossary-reconciliation.log exists."

**Step 4: Present Results**
1. Read the generated docs-verify-report.md
2. Parse the severity summary table
3. Present a concise summary:
   ```
   Verification complete -- {total} issues found.
     {N} critical, {N} high, {N} medium, {N} low, {N} info

   Full report: .mg/docs/docs-verify-report.md
   ```
4. If critical or high issues exist, suggest: "To fix documentation issues, re-run /mg:create-docs-generate after a fresh scan."
5. If no critical/high issues, congratulate: "Documentation quality looks good."
6. Informational note at end: "Found {N} documentation gaps. Consider adding to .planning/BACKLOG.md as documentation debt."

**Step 5: Suggest Next Steps**
- If this is the last pipeline step: "Pipeline complete. Review the report and re-generate as needed."
- Direct to /mg:create-docs for pipeline overview

**Important Principles section:**
- Read-only on docs. Write only to .mg/docs/ workspace (verify-refs.json, docs-verify-report.md).
- Use --docs-dir not --doc-file for check-references.py.
- Agent instructions ARE pasted into the Task prompt (agent reads data files itself via paths).
- The agent uses LSP for symbol verification -- DO NOT use check-references.py's symbol status.
- 5-tier severity model: critical, high, medium, low, info (matching verifier agent definition).
- Prefer false negatives over false positives -- same principle as the verifier agent.
- Do not modify the verifier agent file (agents/verifier.md). Override behavior in the Task prompt only.

CRITICAL CONSTRAINTS:
- DO NOT modify agents/verifier.md. The override happens in the Task prompt.
- DO NOT modify check-references.py. It is used as-is for extraction.
- DO NOT modify install.sh. All commands and sed placeholders are already handled.
- Use {SCRIPTS_DIR} placeholder for script paths (resolved by install.sh at install time).
- Use {GLOBAL_CONFIG} placeholder for default config path.


The command is a lightweight standalone -- no subagents, no pipeline state, no prerequisites beyond .mg/docs/ existing.

**Role section:** You capture documentation notes to the inbox for later processing by the generate pipeline. Standalone command -- does not trigger any pipeline step.

**Arguments section:**
$ARGUMENTS contains the note text. Example: `/mg:add-docs "Document the new auth flow for JWT tokens"`

**Process section -- 5 steps:**

**Step 1: Parse and Validate**
1. Extract note text from $ARGUMENTS. If empty, tell user: `Usage: /mg:add-docs "your note text here"`
2. Check .mg/docs/ directory exists. If not, tell user: `Error: Documentation workspace not found. Run /mg:create-docs first to initialize.`
3. Check .mg/docs/notes-inbox.json exists. If not, create it with initial structure: `{"notes": []}`

**Step 2: Detect Context**
1. Check if user has an active file open (use the context available to the LLM -- if unclear, skip).
2. Check if .planning/STATE.md exists. If so, read it and extract current phase name from "Current focus:" or "Phase:" line. This becomes the --phase argument.
3. Build context parameters:
   - `phase_arg`: current phase name or empty string
   - `file_arg`: active file path or empty string

**Step 3: Add Note to Inbox**
Run add-note.py:
```bash
python3 {SCRIPTS_DIR}/add-note.py \
  --inbox <project_root>/.mg/docs/notes-inbox.json \
  --text "<user_note_text>" \
  --phase "<phase_arg>" \
  --file "<file_arg>"
```
Capture stdout -- it returns JSON with the new note_id.

**Step 4: Classify the Note**
Run classify-note.py:
```bash
python3 {SCRIPTS_DIR}/classify-note.py \
  --text "<user_note_text>" \
  --note-id <note_id_from_step_3> \
  --inbox <project_root>/.mg/docs/notes-inbox.json
```
The script outputs classification JSON to stdout AND updates the note in the inbox file.

Parse the classification: audience, document, section, confidence.

**Step 5: Present and Offer Correction**
Display the result:
```
Note added: {note_id}
Classification:
  Audience:   {audience}
  Document:   {document}
  Section:    {section}
  Confidence: {confidence:.0%}
```

Use AskUserQuestion:
- header: "Classification"
- question: "Accept this classification? If not, provide corrections."
- options:
  - "Accept" -- "Classification looks correct"
  - "Correct" -- "I'll specify the correct audience, document, or section"

If "Accept": Done. Print "Note saved. It will be processed on next /mg:create-docs-generate run."

If "Correct": Ask the user for corrections via a follow-up AskUserQuestion. Read the current notes-inbox.json, update the note's classification fields with the user's corrections, write the updated inbox back. Print "Classification updated."

**Important Principles section:**
- Standalone command -- never triggers scan, generate, or verify.
- One note at a time (no batch ingestion for v1).
- GSD phase context detection is best-effort -- if .planning/ doesn't exist, skip.
- The note stays in inbox until /mg:create-docs-generate processes it.
- Use {SCRIPTS_DIR} placeholder for script paths.
- Active file context is best-effort -- pass empty string if unavailable.

CRITICAL CONSTRAINTS:
- DO NOT modify add-note.py or classify-note.py. Use them as-is.
- DO NOT modify install.sh. The add-docs command is already in the COMMANDS array.
