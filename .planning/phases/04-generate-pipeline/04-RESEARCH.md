# Phase 4: Generate Pipeline - Research

**Researched:** 2026-03-16
**Domain:** LLM command orchestration for documentation generation (markdown-based pipeline commands and subagent coordination)
**Confidence:** HIGH

## Summary

Phase 4 builds the `/mg:create-docs-generate` command -- the only pipeline step that writes documentation files. It reads the `docs-scan.json` contract produced by Phase 3, orchestrates writer agents (Phase 2) with templates and source material, and produces 12 audience-segmented documents (DOC-04 deferred) plus shared OVERVIEW.md and GLOSSARY.md. The phase has two modes: initial (creates all docs from scratch) and update (staleness-driven selective regeneration with interactive approval).

The implementation follows the established codebase-health pattern: a command markdown file orchestrates subagents via the Task tool. The key differences are (a) writers are creative generators rather than diagnostic scanners, (b) execution has a fixed 4-stage order (glossary, parallel writers, reconciliation, overview), and (c) update mode requires an interactive approval flow before any regeneration occurs. All 5 writer agents and the glossary agent were built in Phase 2 and are ready to consume -- this phase wires them into the orchestration command.

No new Python scripts are needed. No changes to install.sh are needed (the command file is already in the COMMANDS array; agents are copied via wildcard). The entire deliverable is a single markdown command file (`create-docs-generate.md`) that replaces the current stub, plus potentially a small Python helper for notes status tracking.

**Primary recommendation:** Implement as a single command file (~400-500 lines) with clear stage separation (initial mode flow, update mode flow, shared generation stages), following the codebase-health-scan.md orchestration pattern exactly.

### Pattern 1: 4-Stage Execution Pipeline
**What:** Fixed execution order ensuring data dependencies are met: (1) glossary initial pass, (2) 4 audience writers in parallel, (3) glossary reconciliation, (4) OVERVIEW.md generation.
**When to use:** Always -- this is the locked execution order from CONTEXT.md.
**How it maps to the command:**
```markdown
### Stage 1: Build Glossary (initial pass)
[Spawn glossary-writer agent with pass="initial"]

### Stage 2: Write Audience Documents (parallel)
[Spawn 4 writer agents in parallel via Task tool]

### Stage 3: Reconcile Glossary
[Spawn glossary-writer agent with pass="reconciliation"]

### Stage 4: Generate OVERVIEW.md
[Generate OVERVIEW.md using OVERVIEW.template.md + knowledge of all docs]
```

### Pattern 2: Writer Agent Delegation (from codebase-health)
**What:** Orchestrator reads agent file, composes prompt with runtime parameters, spawns via Task tool.
**When to use:** For all writer subagent calls.
**Source:** `codebase-health/commands/codebase-health-scan.md` Step 2 subagent pattern.
**Key difference from scan pattern:** Writer agents receive FILE PATHS, not content pasted into prompts. This is a locked decision from CONTEXT.md -- it differs from codebase-health where agent file contents are pasted.

Example Task tool call:
```
Task(
  description="Generate developer documentation",
  prompt="You are a developer writer agent.

[paste full contents of agents/developer-writer.md here]

Project root: {project_root}
Docs dir: {docs_dir}
Scan data path: {project_root}/.mg/docs/docs-scan.json
Templates dir: {TEMPLATES_DIR}/developers/
Style guide: references/style-guide.md
Glossary: {docs_dir}/GLOSSARY.md
Documents: ARCHITECTURE, DEVELOPER_GUIDE, QUICK_REFERENCE
Mode: initial
Update sections: []"
)
```

**IMPORTANT NUANCE:** The agents themselves receive file paths and read files themselves (locked decision). But the orchestrator DOES paste the agent file contents into the Task prompt (per codebase-health pattern) because the subagent cannot read the agent definition file directly via relative path.

### Pattern 3: Update Mode Interactive Approval (AskUserQuestion tool)
**What:** Multi-tier approval flow before regenerating stale sections.
**When to use:** When mode is "update" and staleness_report has entries.
**Flow:**
1. Present document-level overview: "ARCHITECTURE.md: 3 stale sections (2 critical, 1 warning)"
2. User chooses: approve all, approve by document, or approve by severity level
3. If by-document: drill into section name + reason + changed files
4. If inbox notes exist: shown as separate group after staleness sections
5. Collect approved sections list
6. Pass only approved sections to writers as `update_sections` parameter

### Pattern 4: File Ownership Header
**What:** Every generated file starts with auto-generation notice.
**When to use:** All generated files.
**Format:**
```markdown
<!-- This file is auto-generated by /mg:create-docs. To add content, use /mg:add-docs. Manual edits may be overwritten. -->
```
This goes BEFORE the DIATAXIS/AUDIENCE comments and any content.

### Pattern 5: docs-meta Section Tracking
**What:** HTML comment after each section heading tracking generation metadata.
**When to use:** Every generated section.
**Format:**
```markdown
## System Overview
<!-- docs-meta: last-updated: 2026-03-16, sources: [src/app.ts, src/routes/index.ts] -->
```
This is the contract between generate and scan steps -- the staleness-check.py script parses these comments.

### Anti-Patterns to Avoid
- **Pasting source material into agent prompts:** Agents MUST receive file paths and read files themselves. This is a locked decision. Violating it will exceed context limits on large projects.
- **Generating OVERVIEW.md before audience docs:** OVERVIEW.md requires knowledge of what each audience directory contains. It MUST be generated last.
- **Mixing initial and update logic into a single flow:** The command should have clearly separated paths for initial mode vs update mode, converging at the shared generation stages.
- **Skipping the glossary initial pass:** Even if a GLOSSARY.md exists from a prior run, the glossary agent should still run its initial pass to catch any new terms from updated scan data.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|

**Key insight:** Phase 4 is primarily an ORCHESTRATION phase. All the specialized logic (writing conventions, template parsing, term management, staleness detection) was built in Phases 1-3. This phase wires it together.

## Common Pitfalls

### Pitfall 1: Subagent Context Limits on Large Projects
**What goes wrong:** If the command pastes too much content into a subagent prompt (scan data, templates, source files), the subagent hits context limits and truncates output.
**Why it happens:** Scan data for large projects can be 10K+ lines. Templates add ~100 lines each. Source files add more.
**How to avoid:** Pass FILE PATHS, not content. The locked decision says "Agents receive file paths only, read files themselves." The orchestrator prompt should contain: agent instructions (pasted), path references (as strings), mode/config (short strings). Nothing else.
**Warning signs:** Subagent produces truncated or incomplete documents.

### Pitfall 2: Audience Directory Creation
**What goes wrong:** Writer agents try to write to `docs/auto-doc/developers/ARCHITECTURE.md` but the `developers/` directory does not exist yet.
**Why it happens:** On initial mode, the entire `docs/auto-doc/` tree is new. Writer agents assume directories exist.
**How to avoid:** The command MUST create the full directory tree before spawning writer agents:
```bash
mkdir -p {docs_dir}/end-users {docs_dir}/developers {docs_dir}/agents {docs_dir}/devops
```
**Warning signs:** FileNotFoundError or "No such file or directory" in subagent output.

### Pitfall 3: GLOSSARY.md Timing in Initial Mode
**What goes wrong:** Writer agents reference GLOSSARY.md for terminology consistency, but on initial mode it does not exist until the glossary agent completes Stage 1.
**Why it happens:** The glossary_path input points to a file that has not been written yet when the command first loads.
**How to avoid:** The execution order handles this (glossary runs first). Ensure the glossary_path passed to Stage 2 writers points to the file that Stage 1 just created. If Stage 1 fails, writers should proceed without a glossary and note the gap.
**Warning signs:** Writer agents report "glossary file not found" or use inconsistent terminology.

### Pitfall 4: Notes Status Update Atomicity
**What goes wrong:** After integrating notes, the command needs to mark them as `"status": "integrated"` in notes-inbox.json. If multiple notes are processed and the update fails midway, some notes get double-integrated on the next run.
**Why it happens:** notes-inbox.json is updated by the orchestrator LLM, not by a dedicated script with atomic guarantees.
**How to avoid:** Read the full inbox, update all integrated notes' statuses in memory, then write the full file once using the Write tool. This is effectively atomic from the LLM's perspective.
**Warning signs:** Notes appearing as "pending" after they were already integrated.

### Pitfall 5: Update Mode Section Matching
**What goes wrong:** The staleness report uses `document/section` keys from the scan, but the writer agent expects section names matching template headings. If naming conventions differ, approved sections do not match.
**Why it happens:** Section slugs in source_material_index use lowercased-hyphenated format (`system-overview`), but template headings use Title Case (`System Overview`).
**How to avoid:** The command should normalize section identifiers when building the update_sections list. Use the same slug format that the source_material_index uses. Writer agents already know to match by slug.
**Warning signs:** Sections approved for update are not actually regenerated.

### Pitfall 6: OVERVIEW.md Cannot Be Generated in Parallel
**What goes wrong:** If OVERVIEW.md is generated before all audience docs complete, the Audience Guide routing table will be incomplete or inaccurate.
**Why it happens:** Temptation to generate shared docs alongside audience docs for speed.
**How to avoid:** OVERVIEW.md generation is locked as Stage 4 (after all writers complete). The command can generate it inline (not via subagent) since it is a single document that needs knowledge of what was generated.
**Warning signs:** OVERVIEW.md references documents that do not exist or mischaracterizes their content.

### Pitfall 7: Term Proposals Directory Must Be Clean
**What goes wrong:** Stale `terms-{audience}.json` files from a prior run cause the glossary reconciliation pass to re-add terms that were already reconciled.
**Why it happens:** The scan-logs directory was cleared by the scan command, but if generate is run twice without re-scanning, the old term proposals persist.
**How to avoid:** The generate command should clear `terms-*.json` files from `.mg/docs/scan-logs/` before starting Stage 2. Or better: write term proposals to a generate-specific subdirectory.
**Warning signs:** Glossary grows with duplicate terms across runs.

### Pitfall 8: File Ownership Header Placement
**What goes wrong:** The auto-generation header is placed after the DIATAXIS/AUDIENCE comments or after the H1 heading, breaking the expected document structure.
**Why it happens:** Templates start with DIATAXIS/AUDIENCE comments, so it is unclear where the ownership header goes.
**How to avoid:** The ownership header goes at the very top of the file, BEFORE any template-originated content:
```markdown
<!-- This file is auto-generated by /mg:create-docs. To add content, use /mg:add-docs. Manual edits may be overwritten. -->
<!-- DIATAXIS: explanation + reference -->
<!-- AUDIENCE: developers -->

# Architecture
```
**Warning signs:** Inconsistent header placement across generated files.

| Old Approach | Current Approach | When Changed | Impact |

**Key architecture insight:** This is not a code-generation phase. It is an LLM-orchestration phase. The deliverable is a single markdown file (~400-500 lines) that instructs an LLM how to coordinate 6 subagents in the correct order, handle two distinct modes, manage an interactive approval flow, and produce a structured output directory.

## Open Questions

1. **OVERVIEW.md generation: subagent or inline?**
   - What we know: OVERVIEW.md is a single document generated after all others complete. It needs to know what each audience directory contains.
   - What's unclear: Should the orchestrator generate it inline (since it has context of what was just generated) or delegate to a subagent?
   - Recommendation: Generate inline. The orchestrator already knows what documents were produced. A subagent would need to re-read all generated docs to produce an accurate routing table. Inline generation is simpler and avoids a round-trip.

2. **Notes integration timing: during writer agents or after?**
   - What we know: Classified notes have a target document/section. In update mode, they appear in the approval flow.
   - What's unclear: Should writers handle note expansion as part of their section generation, or should notes be integrated as a separate post-writing step?
   - Recommendation: Writers handle notes as part of section generation. The writer agent already receives scan data (which includes note_classifications). When generating a section that has a classified note, the writer can expand the note into prose within that section's context. This avoids a separate post-processing pass.

3. **Update mode: how to handle sections approved for update that have no writer subagent running?**
   - What we know: Update mode may approve only sections for one audience (e.g., only developer docs need updates).
   - What's unclear: Should we still spawn all 4 writer agents, or only the ones with approved sections?
   - Recommendation: Only spawn writers that have approved sections. Pass an empty `update_sections` parameter to skip an audience entirely. This saves subagent costs.
