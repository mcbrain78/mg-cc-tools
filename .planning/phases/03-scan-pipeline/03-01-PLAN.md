  <files>create-docs/agents/scan-audience.md</files>
  <action>
Create `create-docs/agents/scan-audience.md` -- a generic subagent template for per-audience source material scanning. Follow the established agent definition pattern from Phase 2 (Role, Inputs, Process, Output Format, Principles).

**Role:** Scan subagent that analyzes a project for a specific audience, identifying which source files map to which document sections and which components lack documentation for that audience.

**Inputs the subagent receives (passed by orchestrator):**
- `project_root`: Absolute path to project root
- `orientation_path`: Path to `scan-orientation.md` in scan-logs
- `audience`: The audience this agent is scanning for (e.g., "developers")
- `documents`: List of document names for this audience (e.g., ["ARCHITECTURE", "DEVELOPER_GUIDE", "QUICK_REFERENCE"])
- `templates_dir`: Path to templates directory (so agent can read template headings for section slugs)
- `output_path`: Where to write the partial scan JSON

**Process:**
1. Read orientation summary from `orientation_path` for project context
2. For each document in the documents list:
   a. Read the corresponding template from `{templates_dir}/{audience}/{DOCUMENT}.template.md` (for audience-specific) or `{templates_dir}/{DOCUMENT}.template.md` (for shared)
   b. Extract section headings from the template
   c. For each section, identify source files from the project that are relevant to that section's content
   d. Build source_material_index entries with key format `"{DOCUMENT}/{section-slug}"` where section-slug is the heading lowercased with spaces replaced by hyphens
3. Identify undocumented components: project components (from orientation) that have no source_material_index entry for this audience
4. Identify missing topics: standard topics for this audience type that have no coverage
5. Write partial JSON output

**Output format:** JSON matching what merge-scan.py expects:
```json
{
  "source_material_index": {
    "DOCUMENT/section-slug": {
      "source_files": ["path/to/file.py"],
      "staleness": "unknown"
    }
  },
  "gap_analysis": {
    "undocumented_components": ["path/to/component"],
    "missing_for_audience": {
      "{audience}": ["missing-topic-1"]
    }
  }
}
```

**Principles (include these):**
- Read source files yourself using Read tool (you receive paths, not contents)
- Use `"unknown"` for staleness on initial scan; orchestrator handles staleness separately
- Key format MUST be `{DOCUMENT_NAME}/{section-slug}` -- document name matches config entries exactly (e.g., "ARCHITECTURE" not "architecture")
- Only include source files that genuinely relate to the section content -- do not pad with loosely related files
- For gap analysis, compare project components against the set of sections you built; components with no coverage are undocumented

Target length: 80-100 lines. Use placeholder `{SCRIPTS_DIR}`, `{TEMPLATES_DIR}`, and `references/style-guide.md` for install-time sed resolution.

name: mg:create-docs-scan

**Command structure -- 6 steps following codebase-health pattern:**

### Step 1: Orient
1. Identify project root (ask user if ambiguous)
2. Read top-level structure (2-3 levels deep via `ls` or Glob)
3. Identify languages, frameworks, package managers (look for package.json, pyproject.toml, Cargo.toml, go.mod, etc.)
4. Identify entry points (main files, route definitions, CLI scripts)
5. Scan deployment artifacts (Dockerfile, docker-compose, CI/CD configs, systemd units)
6. Scan existing documentation (docs/, README, CLAUDE.md, inline comments)
7. Scan database schemas, API contracts, configuration files
8. Scan environment files (.env.example, config templates)
9. Load config from `.mg/docs/.docs.config.json` -- if not found, read defaults from `{GLOBAL_CONFIG}`
10. Detect mode: check if `{config.docs_dir}` (default `docs/auto-doc`) contains .md files. If yes: `mode = "update"`. If no: `mode = "initial"`
11. If update mode but no prior `docs-scan.json` exists, fall back to initial mode gracefully (per Pitfall 4 from research)
12. Clear `.mg/docs/scan-logs/*.json` and `*.md` to prevent stale data from prior runs (per Pitfall 6). Do NOT delete notes-inbox.json or .docs.config.json (those are in parent .mg/docs/, not scan-logs/).
13. Write orientation to TWO files:
    - `.mg/docs/scan-logs/scan-orientation.md` -- human-readable log (markdown)
    - `.mg/docs/scan-logs/scan-project.json` -- structured data with `project_model` field for merge-scan.py (per Pitfall 3: merge takes project_model from first file that has it)

**IMPORTANT for scan-project.json:** Include the full `project_model` object matching schema.md format: `{ tech_stack[], entry_points[], components[], infrastructure{} }`. This JSON file participates in the merge. Also include `gsd_context: null` (gets overwritten in Step 2 if GSD exists).

### Step 2: GSD Context (conditional)
**Only if** `.planning/` directory exists AND config has `gsd_integration: true` (per Pitfall 5):
1. Read `.planning/STATE.md` for current position and milestone info
2. Read all `*-SUMMARY.md` files from completed phases (use Glob `.planning/phases/*/*.md` pattern)
3. Read `.planning/REQUIREMENTS.md` traceability table for completed requirement IDs
4. Read any `.planning/phases/*-VERIFICATION.md` files for known gaps
5. Read `.planning/MILESTONES.md` if it exists
6. Build `gsd_context` object: `{ milestone, completed_phases[], deviations[], new_requirements_completed[] }`
7. Update `scan-project.json` to include the `gsd_context` field (overwrite the file, replacing the null)

### Step 3: Staleness Check (update mode only)
**Only if** mode is "update" AND docs directory contains .md files:
1. Run `staleness-check.py`:
   ```bash
   python3 {SCRIPTS_DIR}/staleness-check.py --docs-dir <docs_dir> --project-root <project_root> --output <project_root>/.mg/docs/scan-logs/staleness-results.json
   ```
2. Run `check-references.py`:
   ```bash
   python3 {SCRIPTS_DIR}/check-references.py --docs-dir <docs_dir> --project-root <project_root> --output <project_root>/.mg/docs/scan-logs/refs-check.json
   ```
3. Note: These scripts use `--docs-dir` (directory-level), NOT `--doc-file` (per-file). The staleness-scanner.md agent has outdated examples using `--doc-file` -- ignore those examples and use the correct CLI flags documented here.

### Step 4: Notes Classification
**Only if** `.mg/docs/notes-inbox.json` has pending notes (notes where `classified` is false or missing):
1. Read notes-inbox.json
2. For each pending note, run:
   ```bash
   python3 {SCRIPTS_DIR}/classify-note.py --text "<note_text>" --note-id <note_id> --inbox <project_root>/.mg/docs/notes-inbox.json
   ```
3. Collect classification results (stdout JSON) for inclusion in scan output
4. Write classifications to `scan-logs/note-classifications.json` for merge

### Step 5: Per-Audience Scan (parallel via Task tool)
For each enabled audience in config:
1. Read the `agents/scan-audience.md` file
2. Spawn a Task tool subagent with a composed prompt that includes:
   - The full contents of scan-audience.md (pasted into the prompt -- subagent cannot read relative paths)
   - Project root path (absolute)
   - Path to scan-orientation.md
   - Audience name (e.g., "developers")
   - Document list for this audience (from config)
   - Templates directory path: `{TEMPLATES_DIR}`
   - Output path: `<project_root>/.mg/docs/scan-logs/scan-{audience}.json`
3. Launch all audience subagents in parallel (multiple Task tool calls in one message)
4. Each subagent produces a partial JSON with `source_material_index` and `gap_analysis`

Example Task tool call pattern:
```
Task(
  description="Scan source material for {audience} audience",
  prompt="You are a scan subagent for the {audience} audience.\n\n[paste scan-audience.md contents]\n\nProject root: {project_root}\nRead orientation: {project_root}/.mg/docs/scan-logs/scan-orientation.md\nYour audience: {audience}\nYour documents: {document_list}\nTemplates directory: {TEMPLATES_DIR}\nWrite output: {project_root}/.mg/docs/scan-logs/scan-{audience}.json"
)
```

### Step 6: Merge and Present
1. Run merge-scan.py:
   ```bash
   python3 {SCRIPTS_DIR}/merge-scan.py \
       --scan-dir <project_root>/.mg/docs/scan-logs \
       --output <project_root>/.mg/docs/docs-scan.json \
       --project-name "<project_name>" \
       --root-path "<project_root>" \
       --mode <initial|update>
   ```
2. Read the resulting docs-scan.json
3. Present a summary to the user:
   - Mode (initial/update)
   - Components discovered
   - Source material entries count
   - Staleness issues (if update mode)
   - Notes classified (if any)
   - Gaps identified per audience
   - GSD context loaded (if applicable)
4. Tell user: "Scan complete. Run `/mg:create-docs-generate` to generate documentation."

**Additional sections to include in the command:**

**Important Principles (at the end):**
- Read-only on project source code. Only write to `.mg/docs/` workspace.
- Scan agents receive file paths only; they read files themselves (locked cross-cutting decision).
- The `agents/` prefix in file references gets resolved to absolute paths by install.sh.
- If a subagent fails (no output JSON), log a warning and continue with other audiences. The merge handles partial results.
- If python3 is not available, abort with install instructions.

Target length: 250-350 lines. Use placeholders `{SCRIPTS_DIR}`, `{GLOBAL_CONFIG}`, `{TEMPLATES_DIR}`, `agents/` for install-time sed resolution. These match the 6 existing sed patterns in install.sh.
