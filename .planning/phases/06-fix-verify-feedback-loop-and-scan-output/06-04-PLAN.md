<task type="auto">
  <name>Task 1: Add 3rd approval tier to create-docs-generate.md</name>
  <files>create-docs/commands/create-docs-generate.md</files>
  <action>
    This is the most complex change in Phase 6. The generate command is ~465 lines with a 2-tier approval UX. Carefully integrate the 3rd tier without breaking existing behavior.

    **Step 2a (Parse Staleness Data) — add findings loading and fix exit condition:**

    After parsing staleness report (existing step 2a.1) and notes (existing step 2a.2), add step 2a.2.5:

    ```
    2.5. Load verify findings. Run:
    ```bash
    python3 {SCRIPTS_DIR}/list-verify-findings.py \
      --findings-file {project_root}/.mg/docs/docs-verify-findings.json \
      --summary \
      --output /tmp/findings-summary.json
    ```
    Read the output file. Extract total findings count and per-document/per-severity breakdowns. If the findings file does not exist or is empty, treat as zero findings.
    ```

    **CRITICAL — Fix exit condition (step 2a.3, Pitfall 1 in RESEARCH.md):**
    Change from:
    ```
    3. If both the staleness report is empty AND there are no pending notes, print:
       "No stale sections or pending notes found. Nothing to update."
    ```
    To:
    ```
    3. If the staleness report is empty AND there are no pending notes AND there are no verify findings, print:
       "No stale sections, verify findings, or pending notes found. Nothing to update."
       Then exit gracefully (no generation needed).
    ```
    Findings alone MUST prevent early exit. This is the most common regression risk.

    **Step 2b (Present Level 1 Overview) — add findings to overview:**

    Update the AskUserQuestion presentation to include verify findings as the 2nd tier (between staleness and notes, per CONTEXT.md tier ordering: staleness -> findings -> notes):

    ```
    Documentation Update Report:

    Staleness:
      ARCHITECTURE.md:    3 stale sections (2 high, 1 medium)
      DEVELOPER_GUIDE.md: 1 stale section (1 low)

    Verify findings:
      OPERATIONS.md:      2 issues (1 high, 1 medium)
      ARCHITECTURE.md:    1 issue (1 medium)
      Total: 3 findings from last verification run

    Inbox notes: 2 pending (1 for ARCHITECTURE, 1 for USER_GUIDE)

    How would you like to proceed?
      1. Approve all -- update all stale sections, address all findings, and integrate all notes
      2. Select by document -- choose which documents to update
      3. Select by severity -- approve by minimum severity level
      4. Cancel -- exit without changes
    ```

    The 4 options are UNIFORM across all 3 tiers — same options as before. "Approve all" means all staleness + all findings + all notes.

    **Step 2c (Handle User Selection) — merged drill-in:**

    When user selects "Select by document" (option 2): show staleness sections AND verify findings MERGED per document (per CONTEXT.md "Merged drill-in" decision, Pitfall 7 in RESEARCH.md):

    ```
    OPERATIONS.md — 0 stale sections, 2 verify findings:
      Verify findings:
        1. deployment-pipeline — broken file reference (high)
        2. monitoring-setup — Diataxis mixing (medium)

    Approve: all / none / specific numbers (e.g., "1,2")
    ```

    ```
    ARCHITECTURE.md — 3 stale sections, 1 verify finding:
      Stale sections:
        1. system-overview — src/app.ts changed (2026-03-15) [high]
        2. data-model — schema.prisma changed (2026-03-14) [high]
        3. component-map — lib/utils.py changed (2026-03-10) [medium]
      Verify findings:
        4. data-model — Diataxis mixing (medium)

    Approve: all / none / specific numbers (e.g., "1,2,4")
    ```

    Group by document name first, then list staleness sections and findings together under each document with unified numbering. One approval per document covers both staleness and findings.

    When user selects "Select by severity" (option 3): severity filter applies to BOTH staleness sections and verify findings. Use the same severity ranking.

    **Step 2d (Notes Approval) — keep as-is:**
    Notes approval remains a separate group after staleness + findings approval (unchanged).

    **Step 2e (Build Approved Sections Dict) — include findings:**
    When building `approved_sections`, include sections from approved verify findings alongside approved stale sections. A finding's `section` slug gets added to the appropriate audience's list.

    For approved findings, also build a separate `approved_findings` structure so writer agents receive the specific finding details (not just section names):
    ```json
    {
      "developers": {
        "data-model": [
          {"check": "diataxis", "severity": "medium", "description": "...", "suggestion": "..."}
        ]
      }
    }
    ```

    **Stage 2 (Write Audience Documents) — pass findings to writer agents:**

    In update mode, when spawning writer agents (Stage 2, step 3), add findings context to the Task prompt for audiences that have approved findings:

    Before spawning each writer, run:
    ```bash
    python3 {SCRIPTS_DIR}/list-verify-findings.py \
      --findings-file {project_root}/.mg/docs/docs-verify-findings.json \
      --document {DOCUMENT} \
      --audience {audience} \
      --output /tmp/findings-{audience}-{document}.json
    ```

    Read the output and include in the Task prompt:
    ```
    Verify findings for your sections (fix these issues from the previous version):
    [paste findings from the output file — each has description and suggestion]
    ```

    Per CONTEXT.md: "Writer agents receive approved verify findings as context via list-verify-findings.py --document X --audience Y --output + Read tool with instruction: 'the previous version had this specific error, fix it'"

    Only include findings for sections that were approved. If a finding's section was not approved, omit it.

    **Step 5 (Summary) — add findings stats:**

    In the summary stats section (step 5.3), add:
    - If findings were addressed: `"Verify findings addressed: {count} ({severity breakdown})"`

    **Important Principles section — add findings principle:**
    Add: "Generate reads verify findings via list-verify-findings.py but NEVER clears docs-verify-findings.json. Only the verify command clears findings (at the start of each verify run). Findings the user skips in the approval flow reappear on the next verify run — this is correct behavior, not a bug."

    Add: "Tier ordering is staleness -> verify findings -> notes. This follows logical severity ordering: code changes first, quality issues second, user knowledge third."
  </action>
