**Header comments:**
- `<!-- DIATAXIS: how-to + reference -->` (script READMEs are a mix of how-to and reference)
- `<!-- AUDIENCE: all -->` (standalone scripts serve any reader)
- No `<!-- docs-meta -->` line (this is not a pipeline-generated document -- no staleness tracking)

**Sections, each with `<!-- PURPOSE -->` and `<!-- EXAMPLE -->` annotations:**

1. **Title** (H1) -- `# {Script/Tool Name}`. PURPOSE: one-line description of what it does. EXAMPLE: use a realistic standalone script exemplar like a CSV-to-JSON converter (`convert.py`), NOT Road Runner or DataForge.

2. **Prerequisites** -- PURPOSE: language runtime, packages, env vars, file access needed before running. Mark `<!-- OPTIONAL -- delete if not applicable -->` since simple scripts may need nothing beyond the language runtime. EXAMPLE: show Python 3.8+, a pip package, an env var.

3. **Usage** -- PURPOSE: the primary invocation pattern with all required arguments. EXAMPLE: show `$ python3 convert.py --input data.csv --format json` in a ```console block with `$` prompt prefix.

4. **Options** -- PURPOSE: complete reference of all flags/arguments with types, defaults, and descriptions. Mark `<!-- OPTIONAL -- delete if not applicable -->`. EXAMPLE: show a table with columns: Flag, Type, Default, Description.

5. **Examples** -- PURPOSE: fully runnable examples with realistic args AND expected output. EXAMPLE: show 2-3 ```console blocks covering common use cases (basic usage, with flags, edge case like empty input).

6. **Output** -- PURPOSE: what the script produces (files, stdout format, side effects, exit codes). Mark `<!-- OPTIONAL -- delete if not applicable -->`. EXAMPLE: describe output file format and location.

7. **How It Works** -- PURPOSE: brief explanation of internal logic for non-trivial scripts. Mark `<!-- OPTIONAL -- delete if not applicable -->`. EXAMPLE: 3-4 bullet points describing the processing steps.

8. **Notes** -- PURPOSE: gotchas, limitations, related scripts, version history. Mark `<!-- OPTIONAL -- delete if not applicable -->`. EXAMPLE: show a known limitation and a related script reference.

**For the directory-mode case, add a comment block at the top (after the header comments, before the first section) with guidance:**

```markdown
     - Add a brief "Architecture" paragraph or bullet list showing directory
       structure and what supporting files do
     - Order per-script sections by importance (main entry point first) -->
```

<task type="auto">
  <name>Task 2: Create auto-doc-script command file with argument parsing and generation logic</name>
  <files>auto-doc/commands/auto-doc-script.md</files>
  <action>
Create `auto-doc/commands/auto-doc-script.md` (~150-200 lines). Follow the `auto-doc-add.md` structural pattern: frontmatter, role description, arguments section, numbered process steps, important principles.

**Frontmatter (exact values from CONTEXT.md):**
```yaml
---
name: mg:auto-doc-script
description: Generate a README for a standalone script or small tool directory
allowed-tools: Bash, Read, Write, Glob, Grep
---
```

No `Task` tool (single agent, no subagents). No `AskUserQuestion` (fully autonomous).

**Role paragraph:** You generate a README.AUTO-DOC.md for a standalone script or small tool directory. You read the source code, extract the CLI interface and prerequisites, then write a structured README following the SCRIPT_README template. This is a lightweight, single-pass command -- no scan phase, no audience segmentation, no verify step.

**Arguments section:** Document that `$ARGUMENTS` contains the target path and optional `--output <path>`. Show example usages:
- `/mg:auto-doc-script scripts/convert.py`
- `/mg:auto-doc-script tools/data-pipeline/`
- `/mg:auto-doc-script scripts/convert.py --output docs/convert-readme.md`

**Process steps:**

**Step 1: Parse and Validate Arguments**
- Split `$ARGUMENTS` on whitespace
- If empty, show usage message and stop
- If `--output` is present, the next token is the output path; everything before `--output` is the target path
- If `--output` is the last token with no value after it, show error: "Error: --output requires a path argument" and stop
- Verify target path exists using Bash `test -e`. If not, show error: "Error: path does not exist: {path}" and stop
- If `--output` specified, verify its parent directory exists. If not, show error: "Error: output directory does not exist: {parent}" and stop

**Step 2: Determine Mode**
- If target is a file (`test -f`): single-file mode
- If target is a directory (`test -d`): directory mode
  - Count source files (`.py`, `.js`, `.ts`, `.sh`, `.go`, `.rs`, `.rb`, `.pl`, `.lua`, `.java`, `.kt`, `.swift`, `.c`, `.cpp`, `.h`) excluding: test files (`test_*`, `*_test.*`, `*_spec.*`), `__init__.py`, dotfiles, `node_modules/`, `__pycache__/`, `.git/`
  - If zero source files: show error "Error: no source files found in {path}" and stop
  - If >20 source files: print warning "Warning: {N} source files found. Consider the full /mg:auto-doc pipeline for large projects. Continuing..." and proceed

**Step 3: Determine Output Path**
- If `--output` was specified: use that path
- If single-file mode: `{target_dir}/README.AUTO-DOC.md` (same directory as the script)
- If directory mode: `{target_dir}/README.AUTO-DOC.md` (inside the target directory)

**Step 4: Read and Analyze Target**
- Single-file mode: Read the script file. Extract: CLI interface (argparse, click, typer, getopts, etc.), docstrings/comments describing purpose, imports (what needs installed), env var reads (`os.environ`, `os.getenv`, `$ENV_VAR`), file/network access patterns.
- Directory mode: Use Glob to find source files. Identify entry points: `__main__.py`, `cli.py`, `main.py`, files with `argparse`/`click`/`typer`, files with `if __name__` blocks, shell scripts with getopts. Read entry points fully. Read supporting modules to understand structure, but focus documentation on entry points and their direct imports. If multiple independent entry points: prepare per-script sections.

**Step 5: Read Template**
- Read `{TEMPLATES_DIR}/SCRIPT_README.template.md` for section structure and annotation guidance
- Use the template's `<!-- PURPOSE -->` annotations to understand what each section should contain
- Use the template's `<!-- EXAMPLE -->` annotations as quality reference for content density

**Step 6: Generate README.AUTO-DOC.md**
- Write the file to the output path determined in Step 3
- Follow the template's section structure
- **Omit any section that would only contain "None", "N/A", or trivially empty content** -- if a section has nothing substantive, skip it entirely
- For directory mode with multiple entry points: add summary table after title, create per-script sections, add Architecture note
- For examples: use ```console fenced code blocks with `$` prompt prefix for commands and plain text for output. Examples must be fully runnable with realistic arguments and expected output shown
- After writing, print: "Generated: {output_path}"

**Important Principles section:**
- Full overwrite on each run. The filename README.AUTO-DOC.md signals "auto-generated" -- no merge or preservation logic.
- One generic prompt handles all languages. Do not add language-specific extraction instructions.
- Omit empty sections. If a section would contain only "None" or "N/A", delete it entirely.
- Quality bar: "A year from now, someone should be able to open the README and use the script without reading the source."
- Use `{TEMPLATES_DIR}` placeholder for the template path -- resolved by install.sh at install time.
- Do not modify install.sh, templates, or any other auto-doc file from within this command.
