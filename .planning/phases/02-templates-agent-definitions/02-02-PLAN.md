<!-- Three-layer template format (from 02-RESEARCH.md Pattern 1) — all templates follow this exact structure -->

```markdown
<!-- DIATAXIS: type -->
<!-- AUDIENCE: audience-name -->

# {Document Title}

<!-- docs-meta: last-updated: {date}, sources: [{source_files}] -->

## Section Name
<!-- PURPOSE: 1-2 sentences explaining why this section exists and what
     the reader needs from it. -->
<!-- EXAMPLE:
Concrete example showing what this section looks like when filled in
for a real project. 3-10 lines minimum. Uses realistic names.

| Column 1 | Column 2 |
|----------|----------|
| Real     | Data     |
-->

## Optional Section
<!-- OPTIONAL -- delete if not applicable -->
<!-- PURPOSE: Why this section might exist for some projects. -->
<!-- EXAMPLE:
What this looks like when applicable.
-->
```

Key rules:
- Layer 1 (classification) at very top as HTML comments
- Layer 2 (structure) = heading + PURPOSE comment
- Layer 3 (exemplar) = EXAMPLE comment with concrete content
- OPTIONAL before PURPOSE when applicable
- docs-meta after title for staleness tracking
- No placeholder text between sections — comments ARE the template content
</interfaces>

**ARCHITECTURE.template.md** (Diataxis: explanation + reference):
Sections:
- System Overview: high-level architecture description with ASCII component diagram
- Design Decisions: ADR (Architecture Decision Record) format -- decision, context, options considered, rationale. EXAMPLE shows a realistic ADR (e.g., "Why we chose SQLite over PostgreSQL")

- OPTIONAL: External Integrations (APIs, services, webhooks)
- OPTIONAL: Security Model

**DEVELOPER_GUIDE.template.md** (Diataxis: how-to + tutorial):

- Development Setup: prerequisites, clone, install deps, verify setup -- all copy-paste-ready commands

- Adding a New [Feature Type]: step-by-step extension pattern with code examples (e.g., "Adding a new scanner agent" or "Adding a new API endpoint")
- Testing: how to run tests, add tests, test conventions
- OPTIONAL: Debugging Tips
- OPTIONAL: Contributing Guidelines

- OPTIONAL: Environment Variables
- OPTIONAL: Error Codes

- Component Registry: table of components with file path, purpose, public API, dependencies
- File Structure: directory tree with one-line annotations
- Entry Points: every way to invoke the system (CLI, API, events, scheduled) with exact paths
- Data Flow: numbered step-by-step request/pipeline flow with file references
- API Surface: function signatures with parameter types, return types, side effects
- OPTIONAL: External Dependencies (services, APIs consumed)
- OPTIONAL: Configuration Schema

**CONVENTIONS.template.md** (Diataxis: reference):
Sections:
- Naming Conventions: file naming, function naming, variable naming with examples of correct/incorrect
- Code Patterns: established patterns in the codebase (e.g., "atomic JSON I/O", "error handling pattern") with code blocks
- Do / Don't Rules: table format with concrete good/bad examples
- Import Conventions: how imports are organized, what to import from where
- OPTIONAL: Error Handling Conventions
- OPTIONAL: Logging Conventions

**GOTCHAS.template.md** (Diataxis: reference):
Sections:
- Edge Cases: specific behaviors that are non-obvious, with trigger condition and correct handling
- Ordering Constraints: operations that MUST happen in a specific order, with what breaks if violated
- Invariants: conditions that must always be true, with how to verify
- Common Mistakes: table of mistake -> symptom -> fix
- OPTIONAL: Platform-Specific Gotchas
- OPTIONAL: Performance Gotchas

**TESTING.template.md** (Diataxis: reference + how-to):
Sections:
- Test Structure: where tests live, naming conventions, how test discovery works
- Running Tests: exact commands for full suite, single file, single test, with expected output
- Test Patterns: established patterns (fixtures, mocks, factories) with code examples
- Writing a New Test: step-by-step with code template
- OPTIONAL: Integration Test Setup
- OPTIONAL: Test Data Management

Agent template exemplars should use YAML frontmatter in examples, MUST/SHOULD/MUST NOT constraint language, tables for structured data, and absolute paths. Use a consistent example project.
