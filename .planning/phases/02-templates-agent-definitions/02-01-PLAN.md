  <name>Task 1: Create TEMPLATE.md shared writer agent pattern and glossary-writer.md</name>
  <files>create-docs/agents/TEMPLATE.md, create-docs/agents/glossary-writer.md</files>
  <action>
Create `create-docs/agents/TEMPLATE.md` following the codebase-health TEMPLATE.md pattern but adapted for documentation writing rather than code scanning. This file documents the common execution pattern shared by all 4 writer agents. Include:

**TEMPLATE.md structure (target ~120 lines):**
- File listing: list all 4 writer agent files (end-user-writer.md, developer-writer.md, agent-writer.md, devops-writer.md)
- **Role** section: "You are a specialized writer agent for the [AUDIENCE_NAME] audience. You generate documentation by reading templates and source material, then writing document files to the project's docs directory."
- **Inputs** section: project_root, docs_dir, scan_data_path, templates_dir, style_guide_path (use placeholder `references/style-guide.md`), glossary_path, documents (list from config), mode ("initial" or "update"), update_sections (update mode only)
- **Process** section with numbered steps: (1) Read context -- load scan data, style guide, glossary. (2) For each assigned document: read template, extract sections by `## ` headings, for each section read PURPOSE/EXAMPLE comments, look up source material in scan_data.source_material_index, generate following style guide, add docs-meta comment, skip OPTIONAL sections with no source material. (3) Propose new terms -- output JSON array of `{"term": "...", "context": "..."}` to `.mg/docs/scan-logs/terms-{audience}.json`.
- **Output Conventions** section: write to `{docs_dir}/{audience}/` for audience-specific, `{docs_dir}/` root for shared. Include docs-meta HTML comments. Strip template comments (PURPOSE, EXAMPLE, OPTIONAL) from output.
- **Execution Order** section: Document the locked execution order per CONTEXT.md cross-cutting decisions: (1) glossary agent runs first (initial definitions pass), (2) 4 writer agents run in parallel (one per audience), (3) glossary reconciliation pass (merge proposed terms), (4) OVERVIEW.md generated last (after all audience docs complete for accurate routing).
- **Principles** section: Source material over inference. Follow the style guide. Use glossary terms consistently. Skip optional sections rather than generating boilerplate. One Diataxis type per document.

Use placeholder paths for references (`references/style-guide.md`, `references/schema.md`, `{SCRIPTS_DIR}`, `{TEMPLATES_DIR}`) -- install.sh sed-resolves these at install time.

**glossary-writer.md structure (target ~100 lines):**
Create `create-docs/agents/glossary-writer.md` as a specialized agent. Unlike the 4 writer agents, the glossary agent has a dual role:

- **Role**: "You are the glossary writer agent. You manage GLOSSARY.md as the terminology source of truth. You run twice during generation: once before writers (initial pass) and once after (reconciliation pass)."
- **Inputs**: project_root, docs_dir, scan_data_path, glossary_template_path (use `{TEMPLATES_DIR}/GLOSSARY.template.md`), style_guide_path (use `references/style-guide.md`), mode ("initial" or "update"), pass ("initial" or "reconciliation"), term_proposals_dir (path to `.mg/docs/scan-logs/` where `terms-{audience}.json` files land)
- **Process -- Initial Pass**: Read scan data, read glossary template, identify domain terms from project model and source material, generate GLOSSARY.md with categorized definitions (system concepts, domain terms, technical terms).
- **Process -- Reconciliation Pass**: Read all `terms-{audience}.json` files from term_proposals_dir. For each proposed term: check if already in glossary (skip), check for synonym conflicts (reconcile), add new terms with proper definitions. Update GLOSSARY.md.
- **Conventions**: Terms defined in sentence form starting with the term in bold. Organized by category. Each term includes audience-relevance note. Consistent with style guide terminology rules.
- **Principles**: Writers propose terms only (term + one-line context note), glossary agent writes all definitions. No synonyms allowed -- pick one canonical term. Every term must have a clear, jargon-free definition.

<task type="auto">
  <name>Task 2: Create shared and end-user templates with three-layer architecture</name>
  <files>create-docs/references/templates/OVERVIEW.template.md, create-docs/references/templates/GLOSSARY.template.md, create-docs/references/templates/end-users/USER_GUIDE.template.md, create-docs/references/templates/end-users/DOMAIN_SPECIFIC.template.md</files>
  <action>
Create the directory structure first:
```
mkdir -p create-docs/references/templates/end-users
```

All 4 templates MUST follow the three-layer architecture exactly:
- Layer 1 (top of file): `<!-- DIATAXIS: type -->` and `<!-- AUDIENCE: audience -->`
- Layer 2 (per section): `## Heading` followed by `<!-- PURPOSE: 1-2 sentences -->`
- Layer 3 (per section): `<!-- EXAMPLE: 3-10 lines of concrete content -->`
- Optional sections: `<!-- OPTIONAL -- delete if not applicable -->` before PURPOSE
- After title: `<!-- docs-meta: last-updated: {date}, sources: [{source_files}] -->`
- No placeholder text between sections -- the comments ARE the template content

**OVERVIEW.template.md** (Diataxis: reference + explanation, Audience: all):
Sections: System Purpose (what this project does and why), Key Concepts (core domain terminology with brief definitions), Architecture at a Glance (high-level system diagram in ASCII, major components), Audience Guide (table routing readers to their audience-specific docs with description of what each contains). PURPOSE explains this is the landing page preventing context duplication. EXAMPLE uses a realistic project (e.g., a portfolio analytics platform) for exemplars.

**GLOSSARY.template.md** (Diataxis: reference, Audience: all):
Sections: System Concepts (project-specific abstractions), Domain Terms (business/industry terminology), Technical Terms (implementation-level terms). Optional: API Terms, Infrastructure Terms. PURPOSE explains each category's scope. EXAMPLE shows 2-3 realistic terms per category with bold term + sentence definition + audience relevance.

**USER_GUIDE.template.md** (Diataxis: how-to, Audience: end-users):
Sections: Getting Started (prerequisites + first-time setup), Common Tasks (the 3-5 most frequent operations), [Task-Specific Sections] (one section per major workflow -- these are generated dynamically from scan data), Configuration (user-facing config options), Troubleshooting (common issues). OPTIONAL on Troubleshooting. Follow end-user conventions from CONTEXT.md: numbered steps max 7, one action per step, expected results after each step, plain language.

**DOMAIN_SPECIFIC.template.md** (Diataxis: reference + how-to, Audience: end-users):
This is a meta-template for project-defined custom documents. Keep it simpler than other templates.
Sections: Overview (what this domain area covers), Key Concepts (domain-specific terminology for this area), How It Works (high-level explanation), Common Operations (task-oriented procedures), Reference (detailed settings, options, parameters). OPTIONAL on Reference. PURPOSE comments explain that this template is used for project-specific documents defined in config `custom_documents`. EXAMPLE uses a realistic domain (e.g., "Scoring Methodology" for a financial tool).

CRITICAL: Every non-OPTIONAL section MUST have both a PURPOSE and an EXAMPLE comment. Exemplars must be 3-10 lines of concrete content using realistic names, not generic placeholders like "Component A."
  </action>
