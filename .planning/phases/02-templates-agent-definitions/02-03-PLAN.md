**end-user-writer.md (target ~120 lines):**

Opening: Brief description -- "End-user writer agent for non-technical audiences. Generates task-oriented documentation in plain language."

- **Role**: Specialized writer for the end-users audience. Generates USER_GUIDE.md and any custom domain-specific documents.
- **Inputs**: Follow TEMPLATE.md inputs section. templates_dir points to `{TEMPLATES_DIR}/end-users/`.
- **Documents**: USER_GUIDE (always), plus any `custom_documents` entries with `audience: "end-users"` from config.
- **Process**: Follow TEMPLATE.md process section. Add end-user-specific step: after generating each section, verify it passes a "jargon check" -- re-read and replace any technical terms with plain language equivalents or inline definitions.
- **End-User-Specific Conventions** (from CONTEXT.md locked decisions):
  - Plain language. No jargon. If unavoidable, define inline.
  - Task-oriented structure: organize by "How do I..." not by system module.
  - Scannable formatting: numbered steps for procedures, bullet lists for options, tables for comparisons (58% usability improvement per NNGroup).
  - Numbered steps: one action per step, max 7 steps per procedure. If more, split into sub-procedures.
  - Expected results: after each step, state what the user should see.
  - Progressive disclosure: overview first, details in expandable sections or linked pages.
  - No implementation details: users don't need to know which library handles auth.
- **Principles**: Follow TEMPLATE.md principles plus: "If a concept can be explained without a technical term, do so."

**developer-writer.md (target ~130 lines):**

Opening: "Developer writer agent for software engineers who maintain and extend the codebase. Generates code-first documentation in Stripe/Twilio style."

- **Role**: Specialized writer for the developers audience. Generates ARCHITECTURE.md, DEVELOPER_GUIDE.md, QUICK_REFERENCE.md.
- **Inputs**: Follow TEMPLATE.md inputs section. templates_dir points to `{TEMPLATES_DIR}/developers/`.
- **Documents**: ARCHITECTURE, DEVELOPER_GUIDE, QUICK_REFERENCE.
- **Process**: Follow TEMPLATE.md process section. Add developer-specific steps: (1) For each code example, verify it uses correct language tags and is self-contained. (2) For API references, include full type signatures (params, returns, exceptions). (3) For architecture sections, include file path references to actual source files.
- **Developer-Specific Conventions** (from CONTEXT.md locked decisions):
  - Code examples are #1 priority (SmartBear research). Show the example BEFORE the explanation.
  - Interleave prose and code -- never more than 2 paragraphs without a code block.
  - Organize by developer goal, not internal API structure.
  - Separate Diataxis types: never mix tutorial steps into reference docs or explanations into how-to guides.
  - Fenced code blocks with language tags always (`python`, `bash`, `json`).
  - Copy-paste-ready: every code example should be runnable as-is.
  - "I want to..." lookup tables: table mapping developer goals to files and code patterns.
  - Type signatures: include parameter types, return types, and exception types.
  - Show edge cases: document what happens with empty input, missing files, invalid data.
- **Principles**: Follow TEMPLATE.md principles plus: "Show, don't tell. Code over prose."

**agent-writer.md (target ~130 lines):**

Opening: "Agent writer agent for AI coding assistants (Claude Code, Copilot, Cursor). Generates machine-optimized documentation with explicit constraints and structured data."

- **Role**: Specialized writer for the agents audience. Generates SYSTEM_MAP.md, CONVENTIONS.md, GOTCHAS.md, TESTING.md.
- **Inputs**: Follow TEMPLATE.md inputs section. templates_dir points to `{TEMPLATES_DIR}/agents/`.
- **Documents**: SYSTEM_MAP, CONVENTIONS, GOTCHAS, TESTING.
- **Process**: Follow TEMPLATE.md process section. Add agent-specific steps: (1) Add YAML frontmatter to each generated document with metadata (tool/project name, purpose, last_generated timestamp, source files). (2) Use absolute paths for all file references -- never relative paths. (3) Verify every heading name is unique across the document (prevents embedding overlap).
- **Agent-Specific Conventions** (from CONTEXT.md locked decisions):
  - Markdown with YAML frontmatter -- 15-16% more token-efficient than JSON/YAML for context.
  - Explicit over implicit: "MUST use absolute paths" not "paths should be absolute."
  - Consistent terminology: use exact names from codebase, not synonyms or pronouns.
  - Tables for structured data: component registries, config options, file lists.
  - Unique heading names: avoids embedding overlap in RAG systems.
  - Separate sections for distinct topics: prevents chunking problems.
  - Constraint blocks: group MUST/SHOULD/MUST NOT together with clear labels.
  - Action-oriented: "Run `command`" not "You might want to run..."
  - Follows "Codified Context" three-tier architecture (arXiv:2602.20478): L1 system identity, L2 domain knowledge, L3 operational context.
- **Principles**: Follow TEMPLATE.md principles plus: "Machines parse structure, not nuance. Prefer tables over paragraphs, constraints over suggestions."

**devops-writer.md (target ~120 lines):**

Opening: "DevOps writer agent for operators who deploy, monitor, and troubleshoot in production. Generates runbook-structured documentation with copy-paste-ready commands."

- **Role**: Specialized writer for the devops audience. Generates OPERATIONS.md, TROUBLESHOOTING.md.
- **Inputs**: Follow TEMPLATE.md inputs section. templates_dir points to `{TEMPLATES_DIR}/devops/`.
- **Documents**: OPERATIONS, TROUBLESHOOTING.
- **Process**: Follow TEMPLATE.md process section. Add devops-specific steps: (1) For every deployment procedure, write a matching rollback section. (2) For every command, include expected output on success AND failure. (3) Validate that no command uses unexplained `<placeholder>` syntax.
- **DevOps-Specific Conventions** (from CONTEXT.md locked decisions):
  - Runbook structure: alert/trigger -> severity -> pre-checks -> steps -> verification -> escalation.
  - Concrete commands with full syntax -- no abbreviated flags, no assumed aliases.
  - Decision trees and checklists over prose.
  - Every deployment includes matching rollback procedure.
  - Copy-paste-ready: every command runnable as-is, no `<placeholder>` without explaining what to substitute.
  - ASCII diagrams only (no image references).
  - Prerequisite checklist before each procedure.
  - Environment awareness: specify which environment (dev, staging, prod) each procedure applies to.
  - Include expected output after every command (both success and failure cases).
  - Backed by PagerDuty, Google SRE Book, AWS Well-Architected practices.
- **Principles**: Follow TEMPLATE.md principles plus: "Every procedure is written for 3am with no prior context."
