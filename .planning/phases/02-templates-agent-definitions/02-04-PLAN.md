**staleness-scanner.md (target ~100 lines):**

Opening: "Staleness scanner agent for per-section freshness analysis. Spawned during the scan pipeline to detect documentation sections that are out of date."

- **Role**: "You are a specialized scanner agent that analyzes existing documentation for staleness. You identify sections where the underlying source code has changed since the documentation was last generated. You never modify documentation files -- you write analysis results to scan logs."
- **Inputs**: project_root, docs_dir (path to existing docs), scan_output_path (path to write staleness results), doc_files (list of documentation files to check)
- **Process**:
  1. For each documentation file in doc_files:
     a. Run `check-references.py` to detect dead references (file paths that no longer exist, symbol names that were renamed or removed). Use: `python3 {SCRIPTS_DIR}/check-references.py --project-root <project_root> --doc-file <doc_file> --output <scan-logs/refs-check.json>`
     b. Run `staleness-check.py` for git-based freshness per section. Use: `python3 {SCRIPTS_DIR}/staleness-check.py --project-root <project_root> --doc-file <doc_file> --output <scan-logs/staleness-check.json>`
     c. Parse both outputs and combine into a per-section staleness assessment
  2. For each section: classify as `fresh` (no changes), `stale` (source changed), or `broken` (dead references)
  3. Write combined results to scan_output_path as JSON matching the scan schema's `staleness` field structure
- **Output Format**: JSON object with per-file, per-section staleness records including: section_name, status (fresh/stale/broken), reasons (list of why), source_files_changed (list), dead_references (list)
- **Principles**: Conservative classification -- only mark as stale when there's concrete evidence (git changes or dead references). Never modify documentation. Report findings, don't make judgments about priority.

**verifier.md (target ~120 lines):**

Opening: "Verifier agent for documentation quality checking. Spawned during the verify pipeline to assess reference integrity, cross-document consistency, Diataxis compliance, and completeness."

- **Role**: "You are a specialized verification agent that analyzes generated documentation for quality issues. You produce a verification report with categorized issues by severity. You never modify documentation files."
- **Inputs**: project_root, docs_dir, scan_data_path (path to docs-scan.json for completeness checks), glossary_path, style_guide_path (use `references/style-guide.md`), output_report_path (where to write docs-verify-report.md)
- **Process** — run these checks in order:
  1. **Reference Integrity**: For each doc file, run `check-references.py` to detect dead file paths and missing symbols. Use: `python3 {SCRIPTS_DIR}/check-references.py --project-root <project_root> --doc-file <doc_file> --output <scan-logs/verify-refs.json>`. Categorize results by severity (broken path = high, missing symbol = medium).
  2. **Cross-Doc Consistency**: Read GLOSSARY.md. For each doc file, check that terms defined in the glossary are used consistently (no synonyms, no conflicting definitions). Flag undefined terms that appear in multiple documents.
  3. **Diataxis Mixing Detection**: For each doc file, check the `<!-- DIATAXIS: type -->` classification against content. Flag tutorial-style content in reference docs (step-by-step instructions in what should be factual descriptions), explanation content in how-to guides (lengthy "why" sections in what should be practical steps).
  4. **Completeness**: Compare docs-scan.json source_material_index against generated docs. For each component in the scan that has source material, verify a corresponding doc section exists. Flag components with no documentation.
  5. **Example Validity**: Scan code blocks with language tags. For Python: check that code is syntactically valid (try `compile()`). For bash: check for obvious errors (unclosed quotes, undefined vars). Report as low-severity warnings.
  6. **Link Integrity**: Check all internal markdown links (`[text](path)`) resolve to existing files or headings.
- **Output**: Write `docs-verify-report.md` with issues organized by severity (critical, high, medium, low, info), each issue listing: document, section, check type, description, suggestion.
- **Principles**: Prefer false negatives over false positives. Categorize by impact. Provide actionable suggestions, not just problem descriptions. Cross-reference check results across documents to find systemic issues.
